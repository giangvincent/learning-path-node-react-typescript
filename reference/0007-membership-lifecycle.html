Reference 07 · the four questions lesson 06 raised

Joining, leaving, and the last owner

Membership looks like a row. It behaves like a lifecycle: people join by invitation, leave by choice, and change what they may do — and every one of those transitions has a state the system must never reach.

Used by: Lesson 07 Requires: Reference 06 Vocabulary: GLOSSARY.md

1. When 404 becomes the wrong answer

Reference 06 said: a non-member gets 404, never 403, because a 403 confirms the family exists. That rule is not a law — it is a decision about who is entitled to know a resource exists. It becomes the wrong answer in six recognisable situations.

Situation Right answer Why 404 is wrong
No session at all 401 A 404 tells the client "gone" instead of "log in". Different action.
Inside the family, but not allowed to do this 403 You already know it exists. Hiding it is a lie that costs you a debuggable error.
Allowed, but the request conflicts with current state 409 "Last owner cannot leave" is not a permission failure. Retrying after adding an owner will succeed.
Existence is already public Honest status Hiding a public family tree's existence protects nothing and confuses everyone.
A collection that is legitimately empty 200 + [] A family with no people is not a missing family. This is the most common 404 bug in REST APIs.
Yours to debug Distinguish in the log The collapse is for the client. Your server must still record which branch it took.
The rule underneath all six

Collapse on the wire, distinguish in the logs. One status code and one body go to the caller; the server logs family_missing versus not_a_member. The security property lives in the response, not in your observability — and a 404 that is also your only signal for a broken slug is a 404 you will spend an afternoon on.

There is also a genuine argument the other way, worth knowing because an interviewer will raise it: for an authenticated caller, 403 is arguably more honest, and the enumeration risk is smaller than it looks — an attacker needs a valid account, and the family slug is not a secret you can enumerate cheaply if it is not sequential. KinLink chose uniform 404 for :slug. The thing to be able to say is which you chose, why, and that you applied it consistently — not that one is correct.

2. Invitations: the token that stands in for membership

Lesson 06 closed the join-by-slug hole by making registration create your own family. That leaves exactly one legitimate way into someone else's: a token the family issued to you. An invitation is a bearer credential for a membership that does not exist yet, which is why it is designed like a password reset, not like a URL. 

model Invitation {
  id        String    @id @default(uuid())
  familyId  String    @map("family_id")
  role      FamilyRole @default(member)   // never above the inviter's own
  email     String?                        // set = targeted; null = shareable link
  tokenHash String    @unique @map("token_hash")  // store the HASH, like a password
  expiresAt DateTime  @map("expires_at")
  usedAt    DateTime? @map("used_at")
  createdBy String    @map("created_by")

  family Family @relation(fields: [familyId], references: [id], onDelete: Cascade)

  @@index([familyId])
  @@map("invitations")
}
Store the hash, not the token

The token appears in a URL, which means it lands in browser history, in the email provider's logs, and in any Referer header the destination site sends. Treat it exactly like a password: the server keeps only a hash, so a database leak does not hand over live invitations. The OWASP Forgot Password Cheat Sheet is the right template — same credential, same rules: "generated using a cryptographically secure random number generator… long enough to protect against brute-force attacks… linked to an individual user… invalidated after they have been used… stored in a secure manner."

Two more from the same sheet, both about links: add Referrer-Policy: no-referrer on the page the token lands on (or the token leaks to any third-party asset on that page), and never build the invite URL from the Host header (host-header injection).

How it changes registration

The important design move is to not put the token in the register call. Keep two endpoints: 

POST /api/invitations/:token/accept     // authenticated. Joins the family.
POST /api/auth/register                 // unchanged: creates your own family

Why the split matters: the invitee is often already a user. Your aunt has an account; she is joining a second family. If accepting an invite were part of registration, the feature would only work for brand-new accounts — the single most common way this gets built wrong. Accept is also where the "you're already in this family" (409) case lives.

The part that is genuinely hard: consuming the token once

// WRONG: check then write. Two clicks, two memberships.
const invite = await findInvite(token);
if (invite.usedAt) return 409;
await createMembership(...);
await markUsed(invite.id);

// RIGHT: one conditional write decides. The database arbitrates.
const claimed = await tx.invitation.updateMany({
  where: { tokenHash, usedAt: null, expiresAt: { gt: new Date() } },
  data: { usedAt: new Date() },
});
if (claimed.count !== 1) return 409;      // someone else won, or it expired

const membership = await tx.familyMember.create({            // same transaction
  data: { userId, familyId: invite.familyId, role: invite.role },
});

updateMany with usedAt: null in the where is a compare-and-set: MySQL returns the number of rows it actually changed, and count !== 1 means you lost the race. Note it also folds the expiry check into the same statement, so an expired invite is indistinguishable from a used one — which is the right amount of information to give a stranger holding a stale link. Both writes share one transaction, so a failure cannot consume the token without creating the membership.

Two authorisation rules for invitations

  • You cannot mint authority you do not have. If an admin can create an invite with role: "owner", the role system is decorative — they promote themselves by proxy. The granted role must be ≤ the inviter's rank.
  • The acceptor's identity comes from the session, never the body. userId is never a parameter. An invite that names the user it creates is a privilege-escalation gadget.

And the reason a targeted invite is allowed to leak existence: the whole point is that the invitee must learn "this family exists and wants you". That is the exception Reference 06 §1 predicted — and it is safe only because the token is what proves the entitlement, not the family's name.

3. Leaving, and the last owner

Where the rule goes

"A family always has at least one owner" is a policy about a transition, so it belongs in the service, checked and written inside one transaction. Not the middleware (that is HTTP), not the model (that is facts), and not a database CHECK — MySQL cannot express "at least one row of this kind" as a constraint, and Prisma has no deferred constraints to lean on either.

Why a transaction is not enough on its own

The MySQL manual, on exactly this shape of problem: "If you query data and then insert or update related data within the same transaction, the regular SELECT statement does not give enough protection. Other transactions can update or delete the same rows you just queried." Two owners demoting each other both read count = 2, both write, and the family is left with zero owners. Counting is a read; you need the write to be serialised behind it: 

await tx.$queryRaw`SELECT id FROM families WHERE id = ${familyId} FOR UPDATE`;
// ...only now is it safe to count owners and then write

FOR UPDATE "locks the rows and any associated index entries, the same as if you issued an UPDATE statement for those rows", and the locks release on commit. The second transaction waits, then re-reads a world where only one owner remains, and refuses. (MySQL 8.0 — Locking Reads.)

The transitions, and their codes

Transition Who may Refusal
Change someone's role Owner 403 if not owner; 409 if it would remove the last owner
Demote yourself Owner, if another owner exists 409 — the request is allowed, the state forbids it
Leave Any member 409 for the last owner, with "transfer ownership first"
Remove someone else Owner 409 if they are the last owner
Delete the family Owner, and it cascades —

409 and not 403, in every "last owner" row. RFC 9110's 409 is the code for a request that "could not be completed due to a conflict with the current state of the target resource" (§15.5.10). The caller in these rows is permitted — the state is not ready. That is the difference between "you may never" and "not like this, not now", and it is the difference between a client that shows an error and one that offers to transfer ownership.

What happens to the data when someone leaves

The membership row is deleted; the person's content is not. That is not an oversight — it falls out of the data model:

  • Person.familyId has no createdBy. A genealogy record belongs to the family, not to the account that typed it. So there is nothing to reassign and no orphan to chase. If you later add createdBy for attribution, you inherit a policy question that this schema currently cannot ask.
  • The session is already safe. It holds only userId, so there is no cached familyId to invalidate. This is lesson 06's "identity in the session, authorisation per request" paying off — the leave is a one-row delete with no session surgery.
  • Make leave idempotent. Deleting a membership that is already gone should answer 204, not 404: the caller's intent ("I am not in this family") is satisfied either way. After that, any further request to /families/:slug/… answers 404 because loadFamily no longer finds a membership — consistent, and no special case.
  • An empty family is a policy question. If the last non-owner leaves, the family is unreachable but intact. Deleting it destroys Person rows through the cascade — which for a genealogy product is data loss, not cleanup. Leave it dormant.

4. When two queries beat one

findMembershipWithFamily is one query on purpose: it makes an unauthorised family unrepresentable. But that is a specific goal, not a universal virtue. It is the wrong shape when:

  • You need to tell the two failures apart. This is the direct inversion, and it is legitimate: an admin console must report "no such family" versus "you are not a member", because the operator is entitled to know and the leak is not a leak. Two queries — or one query plus a typed reason — is correct there. The collapse in Reference 06 is a client-facing decision; it is not a property of the database.
  • The two facts have different lifetimes. A family's name changes yearly; a membership changes rarely; a person's profile changes daily. One join forces one cache entry with the shortest TTL. Split queries let you cache the expensive, stable parts (and skip the membership round trip entirely for a minute) while the hot data stays uncached.
  • You are reading many families, not one. "One query" is not the rule — a number of queries proportional to the page, not to the rows is. A dashboard showing 20 families should be one findMany({ where: { userId, familyId: { in: ids } } }), not 20 joins. That is how you avoid N+1 without contorting the shape.
  • You are about to write. The read-only join is the wrong tool once you need the row locked. You fetch the membership, lock the family, re-read, then act — deliberately several statements, because each has a different job.
  • The join has no natural key. Joining through family.slug costs an extra join or subquery. If the URL carried a familyId (or a cached slug→id map), two lookups would be cheaper and simpler.
What the one query really buys

Unrepresentability, not speed. It is worth its cost only because this codebase has no other enforcement point — nothing else guarantees that a family is fetched together with its membership. Add a scoped repository, a Postgres row-level-security policy, or a lint rule that forbids exporting a family-fetching function from anywhere but membership.model.ts, and two queries become perfectly fine. The invariant is "there is exactly one door to a family, and it needs the membership" — the single query is just today's cheapest way to build that door.
