Reference 12 · the project, folder by folder

The map of KinLink

Twelve folders, two tsconfigs, one manifest. This is the document to open when you have forgotten where something lives — and the one to read the night before an interview, because it is also the answer to "walk me through your architecture". Every file, what it exports, why it exists, and what must never go in it.

Used by: Lesson 14a–14d Companion: Reference 02 (the layers) · Reference 04 (the rules) Vocabulary: GLOSSARY.md

1. The shape, and why it is this shape

KinLink is one website project: a single package.json, a single node_modules, one command (npm run dev) that starts both halves. Not a monorepo, not a workspace, no workspace:*. The two server and client programs share exactly one thing — shared/contracts/, a folder of types that both tsconfigs include. There is no runtime code there and no nested manifest. 

kinlink/
├── package.json          one manifest: scripts, deps, no workspaces
├── tsconfig.json         server + shared  (NodeNext, strict)
├── vite.config.ts        client build; proxies /api to :4000
├── docker-compose.yml    MySQL 8.0 in a container
├── prisma7.config.ts     Prisma: where the schema and migrations live
├── prisma/               schema.prisma + migrations/
├── client/               React + TypeScript      ← presentation
├── server/               Express + TypeScript    ← data, rules, permissions
└── shared/contracts/     types both sides compile against
Two programs, two tsconfigs, one type system

tsconfig.json (root) compiles server/src and shared with types: ["node"]. client/tsconfig.json compiles client/src with the DOM lib and types: ["vite/client"] — and deliberately no Node types. That asymmetry is a security property, not an accident: if a component could reference process or fs, someone would. See lesson 14 for what it costs a client-side check script.

2. Folder by folder

Root — configuration, no application code

FileWhat it is for
package.json One manifest. Scripts: dev, dev:server, dev:client, build, typecheck, db:up/down/migrate/studio/seed, and one check:* per invariant.
tsconfig.json Server + shared compiler options. include: ["server/src", "shared"] — a file outside that list is silently not compiled.
vite.config.ts Client build (root: "client") and the dev proxy that forwards /api to localhost:4000. The proxy is why this project has no CORS configuration at all.
docker-compose.yml mysql:8.0 with a named volume, so data survives restarts. Started with npm run db:up.
prisma7.config.ts Tells the Prisma CLI where schema.prisma and migrations/ are.

prisma/ — the schema and its history

schema.prisma holds four models (Family, Person, User, FamilyMember, Invitation) and two enums (Gender, FamilyRole). It is the one source of truth for the database's shape, and the only thing the Prisma CLI reads.

migrations/ is append-only history. Six applied so far, in order — read them top to bottom and you have the data model's biography:

MigrationWhat it did
add_family_and_personThe first two tables.
change_default_updated_atGave people.updated_at a default.
add_users_tableAccounts, with a family_id column we later removed.
add_family_membersThe join table with a role — and the migration that dropped users.family_id. One user, many families.
add_invitationThe invite table: token_hash, expires_at, used_at.
add_invitation_created_atThe column lesson 12 was missing.

shared/contracts/ — the only shared surface

Five files of pure types. Both sides compile against them, so a change here is a compile error on whichever side has not caught up. That is the point: the contract is where the client and server agree, and the compiler is the enforcement.

auth.tsRegisterRequest, AuthResponse — and note what AuthResponse does not carry: no familyId, since session 6.
person.tsGender, PersonResource.
family.tsFamilyResource — { slug, name, role }, no id.
invitation.tsInvitationResource — email: string | null, dates as ISO strings.

The rule for this folder: components render and ask lib/api.ts for data. They never build a URL, never read a cookie, and never decide what a status code means — that last one is why lesson 14 exists.

server/src/ — the layers

This is the folder that will carry the interview. It is MVC with the layers kept honest: model owns data, view owns the response shape, controller owns the HTTP boundary, and the service owns the rules.

FileExports — what each one is
server.tsThe process: createApp().listen(env.port). Nothing else.
app.tscreateApp(): express → json → sessionMiddleware → /api → errorHandler. Does not listen, which is what lets a check script run the whole stack on an ephemeral port.
config/env.tsenv — a validated port and nodeEnv.
config/database.tsprisma — the one PrismaClient plus the MariaDB adapter.
config/session.tssessionMiddleware — cookie name, httpOnly, sameSite: "lax", rolling. MemoryStore in dev, which is why every save logs you out.
contracts.tsThe server's window on shared/contracts/.
types/express.d.tsThe two declaration merges: SessionData.userId, and Request.{authenticatedUserId, family, membership}. Without this file, ten type errors.

routes/ — the URL table and its order

FileWhat it mounts
index.tsapiRouter. Three bands, in this order: public (/health, /auth) → guard (requireAuth) → protected (/families, /families/:slug, /families/:slug/invitations, /invitations). A route below the guard is protected with no per-route argument; a route above it must be public on purpose.

family.routes.tsfamilyRouter: GET people, PATCH members/:membershipId, POST leave, POST transfer-ownership.
invitation.routes.tsTwo routers. invitationRouter is family-scoped (POST mint, GET list); acceptInvitationRouter is standalone (POST /:token/accept) because the invitee is not yet a member.

generated/prisma/ is Prisma's generated client. It is tracked in git (an unusual choice) and must never be hand-edited; it is regenerated by npm run db:migrate.

4. "Which folder do I touch?"

The table to reach for first. If a change needs two rows of this table, it is a feature, and it goes through every layer in §3.

I want to…Files, in order
add a field to a responseshared/contracts/* → server/src/views/* → the model's query if the column isn't loaded
add an endpoint to an existing resourceroutes/*.routes.ts → controllers/* → service → model → view as needed
add a business ruleservices/* only. If you are editing a controller, stop.
add or change a querymodels/* only. Controllers never import Prisma.
change what the client may seethe view, then the contract. The view is the security boundary.
add a screenclient/src/*.tsx + a named function in client/src/lib/api.ts
change something both sides must agree onshared/contracts/* — let the compiler find the call sites
change the schemaprisma/schema.prisma → npx prisma migrate dev --name … → the model → the view if it crosses the wire
prove something still holdsserver/src/scripts/check*.ts + one line in package.json
mount a new pathserver/src/routes/index.ts — and decide which band it belongs in

5. Invariants, and where each one is enforced

An invariant is a sentence that must stay true no matter what the client sends. Each one lives in exactly one layer, and — this is the part worth knowing — most of them have a runnable proof.

InvariantEnforced inProof
a family keeps at least one owner membership.service, inside lockFamily npm run check:ownership
every family read is scoped to the caller membership.model — where: { userId } npm run check:families
an unguarded route answers 401, never data routes/index.ts band order + authContext's tripwire npm run check:guards
"pending" means claimable, in one place invitation.model.findPendingByFamily npm run check:invites
a token is single-use under concurrency invitation.service.acceptInvitation — one conditional write none yet
the session holds identity only types/express.d.ts + loadFamily per request —
one pending invite per email nowhere — see the warning below none
Two rows the notes got wrong — verified by reading the code

Session 11's notes describe a "mint hardening" with a runnable proof called check:mint. Neither exists. createInvitation in services/invitation.service.ts has no transaction, no lockFamily, and no duplicate-email refusal — it is a plain prisma.invitation.create — and grep -rn "mint" package.json server/src/scripts returns nothing. So "one pending invite per email" is currently an intention, not an invariant: two concurrent mints for the same address both succeed. This is the honest version of the table, and restoring that proof is a debt with a name.

6. The checks — what each one protects, and what it costs to run

ScriptProtectsNeeds MySQL?
npm run check:guards that a protected path answers 401 before any data is read No — the guard rejects before the model
npm run check:ownership the last-owner rule, under a forced interleaving (a gate parks both transactions in the race window) Yes
npm run check:invites the pending filter — a used and an expired invite are both absent; email: null survives as null Yes
npm run check:families that "my families" returns the caller's and not a stranger's, and that the family id does not cross the view Yes
npm run check:session the client's session-end announcement: a 401 about the session ends it, a 401 about sign-in does not, a 500 never does No — it stubs fetch and needs no server at all

The technique is the same in every one: no framework. A script asserts, prints what it saw, and exits non-zero when the claim is false. checkGuards and check:session are the cheap half of the pyramid — no database, no port, milliseconds — which is why they are the two to run on every save.

7. The constitution: one rule per layer

  • Contract — the type both sides compile against. Change here, and the compiler finds the call sites.
  • Route — binds a URL to a controller, and decides which band (public / guarded / family-scoped) it sits in. Nothing else.
  • Middleware — a concern that is not business logic. It must leave a proven fact on the request, and it must fail loudly when mounted wrong.
  • Controller — reads the request context, calls one service, chooses the status code. No business logic, no queries, no req.params.slug re-derivation.
  • Service — the rules. Never sees a Request. Owns transactions, locks and the shape of refusals.
  • Model — the only place Prisma appears. Answers facts ("which rows match this familyId"), never policy. Takes a Db so it can join a caller's transaction.
  • View — a whitelist from row to resource, through an annotated return type the compiler enforces. Never queries.
  • Script — a claim, made runnable.
