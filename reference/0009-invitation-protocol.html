Reference 09 · the invite protocol

Invitations: propose, accept, expire

An invitation is a bearer credential for a membership that does not exist yet. The protocol — propose → accept → expire — is the shape of every "ask to join" flow in KinLink, and the same shape appears in password resets, OAuth flows, and any "someone else must agree" transition.

Used by: Lesson 09 Requires: Reference 07 Vocabulary: GLOSSARY.md

1. The token is a credential, not a URL

The raw token is generated by the server, sent to the client once, then never stored. The server keeps only a hash — same as passwords, same as reset tokens. OWASP Forgot Password Cheat Sheet is the template: CSPRNG generation, length against brute force, linked to a record, invalidated after use, stored as a hash. Two extras for invite links: Referrer-Policy: no-referrer on the page the token lands on, and never build the invite URL from the Host header (host-header injection).

2. The protocol

// Propose — owner-only. Role ≤ inviter's rank.
POST /api/invitations
{ "email": "minh@nguyen.family", "role": "member" }
→ 201 { "token": "raw-token-sent-once" }

// Accept — authenticated. Session proves who claims.
POST /api/invitations/:token/accept
→ 204 on success
→ 409 on used / expired / already-member

Two endpoints, one resource. The split matters because the invitee is often already a user — registration creates your own family, acceptance joins someone else's.

3. Compare-and-set: the single conditional write

The race is on usedAt. The wrong shape: findInvite → check usedAt → createMembership → markUsed. The right shape: one updateMany with usedAt: null in the WHERE clause, expiry in the same statement. MySQL returns how many rows actually changed — count !== 1 means you lost the race. 

const claimed = await tx.invitation.updateMany({
  where: { tokenHash, usedAt: null, expiresAt: { gt: new Date() } },
  data: { usedAt: new Date() },
});
if (claimed.count !== 1) return 409;  // lost the race or expired

const membership = await tx.familyMember.create({
  data: { userId, familyId: invite.familyId, role: invite.role },
});

Both writes share one transaction — a failure cannot consume the token without creating the membership.

4. Two authorisation rules

  • Mint authority ≤ inviter's rank. An admin inviting an owner promotes themselves by proxy. Checked in the service, before the token is created.
  • Identity from the session, never the body. userId is never a parameter. An invite that names the user it creates is a privilege-escalation gadget.

5. Collapse on the wire

expired and used both answer 409 reason: "used". A stale link should not learn "it expired Tuesday" — "this token does not work" is the right amount of information. Distinguish in logs; collapse on wire.

6. The counter-case

Shareable links (no email, no target) let anyone with the link join. The invitation still needs a role — and the rank check — because authority is authority regardless of who clicks. Target invites (email set) leak existence by design: the invitee must learn "this family exists and wants you", which is the exception Reference 07 §1 predicted. Safe only because the token proves the entitlement, not the family's name.
