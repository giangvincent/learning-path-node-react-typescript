Reference 06 · the questions lessons 06–07 answer

Chains, codes and roles

Authentication asks who are you. Authorisation asks what may you do to this particular thing — and the second question has three distinct wrong answers, each with its own status code. This is the compressed version of the four questions asked at the end of lesson 05.

Used by: Lesson 06 Requires: Reference 05 Vocabulary: GLOSSARY.md

1. 401, 403, 404 — one code per question

Question the server asked Answer Whose fault Client does
"Who are you?" — and there was no answer 401 Caller's Show the login form
"Who are you?" — answered, and there is no such family 404 Caller's Show "not found"
"Who are you?" — answered, family exists, you are not in it 404 Caller's Show "not found"
Member, but not allowed to do this 403 Caller's Show "no permission" — do not log out
"This should be impossible" 500 Ours Page an engineer
Why "not a member" is a 404 and not a 403

A 403 says "this exists, and you may not have it". That is a true sentence, and it is an enumeration oracle: an attacker walking /api/families/nguyen, /api/families/tran, /api/families/phan can tell "exists but not mine" (403) from "doesn't exist" (404) and map your customer list without ever being let in.

OWASP's Authorization Cheat Sheet asks the question directly: for a rejected lookup, "will the failure simply be the result of the account not existing, or will it be due to a failed access control check?" If a stranger can tell those apart, you have leaked.

So the third row and the second row are deliberately identical — same status, same body, same timing shape. That is not sloppiness; it is the entire security property. The way to guarantee it is to make the two cases indistinguishable in code, so nobody can accidentally separate them later: 

// The WRONG shape: two facts, and someone must remember to compare them.
const family = await findFamilyBySlug(slug);        // returns a family it should not have
const membership = await findMembership(userId, family.id);
if (!membership) return res.sendStatus(403);        // ← and now the leak is a typo away

// The RIGHT shape: one query that cannot answer without the membership.
const membership = await prisma.familyMember.findFirst({
  where: { userId, family: { slug } },              // the join IS the authorisation
  include: { family: true },
});
if (membership === null) return null;               // "no such family" and "not yours"
                                                    // are the same return value

The second version collapses both failures into one null inside the service, so the middleware that turns null into a response has nothing left to leak. You cannot tell the difference because the difference no longer exists in your program. This is the same move as lesson 03's required familyId argument: make the insecure version unrepresentable rather than remembered.

Order is a security property

The checks must run most-general first: session → family exists → membership → role. Swap membership and role and a non-member with an unprivileged role receives a 403 — which is exactly the oracle above. A chain is not a bag of guards; its order carries meaning.

2. Deny by default, and what the chain looks like

OWASP: "one should not rely entirely on explicitly defined rules for matching all possible requests. For security purposes an application should be configured to deny access by default", and permission checks should "allow for global, application-wide configuration rather than needing to be applied individually to every method or class." That is lesson 05's guard line, extended to a chain: 

apiRouter.use("/auth", authRouter);        // public, on purpose

apiRouter.use(requireAuth);                // identity from here down

apiRouter.use(
  "/families/:slug",
  loadFamily,                              // slug → req.family + req.membership, or 404
  familyRouter,                            // GET /people
);

// later, inside familyRouter, where a role is genuinely needed:
familyRouter.patch("/", requireRole("admin"), renameFamily);

Resolve once, at the boundary

loadFamily reads req.params.slug once and leaves req.family and req.membership behind. Nothing downstream re-reads the raw parameter, so nothing downstream needs a second database query, and nothing downstream can be tempted to trust the string.

The mergeParams trap (measured)

A parameter on a mount path is visible to middleware on that mount, but not to the mounted router unless you opt in: 

api.use("/families/:slug", mw, familyRouter)

mw saw slug = "nguyen"                    // ✓ mount middleware sees it
familyRouter.get("/people", …)            // ✗ req.params.slug === undefined
express.Router({ mergeParams: true })     // ✓ then it is "nguyen"

Verified against Express 5.2.1. It is a real trap — but the better answer is not mergeParams, it is to read req.family. A child router that re-reads the slug is duplicating the lookup, not improving the design.

3. What belongs in the session: identity, not authorisation

Lesson 04 put familyId in the session alongside userId. That was a mirror of the old data model, where a user had exactly one family — and it silently became a bug the moment a user could have two. 

// Session: WHO you are. Stable for the life of the session.
req.session.userId = user.id;

// Per request: WHAT you may do. Derived from the resource you named.
req.authenticatedUserId
req.family          // resolved from :slug + membership
req.membership      // includes .role

The test is simple: if a value depends on which resource is being requested, it cannot live in the session. Authorisation context belongs to the request, because it changes from request to request — the same logged-in person may be an owner of one family and a plain member of another. Put identity in the session, derive authorisation every time.

4. Roles: 403 arrives

403 only becomes available once the caller is known to be inside the boundary. Then a role check is honest and actionable: "you are in this family, and this action is not yours." 

export const ROLE_RANK = { member: 1, admin: 2, owner: 3 } as const;
export type Role = keyof typeof ROLE_RANK;

/** "admin" means admin or above — never a list you can forget to extend. */
export const requireRole = (min: Role): RequestHandler = (req, res, next) => {
  const { membership } = familyContext(req);
  if (ROLE_RANK[membership.role] < ROLE_RANK[min]) {
    res.status(403).json({ message: "Insufficient role" } satisfies ApiErrorBody);
    return;
  }
  next();
};
Rank, not string equality

membership.role === "owner" forces every call site to enumerate the roles above it, and someone will write ["owner", "admin"] and forget admin when a new role lands between them. A rank map makes "or above" a comparison, so adding a role cannot silently narrow or widen an existing check.

Where the role lives, and why

The role belongs to the relationship, not to the user and not to the family: family_members(user_id, family_id, role). Same person, owner here and member there. This is exactly the model OWASP now recommends over plain RBAC — relationship-based access control, where access derives from the relationship between a subject and a resource and "role" is merely one attribute of that relationship. KinLink is a ReBAC product wearing an RBAC costume; say it that way in an interview.

Two constraints do the real work:

  • @@unique([userId, familyId]) — membership is one fact, not a set of rows. Without it, a user acquires three memberships, two of them stale, and "what is my role" becomes a query with an arbitrary answer.
  • The last-owner invariant — you must not be able to demote or remove the final owner, or the family becomes permanently unmanageable. That is a business rule enforced inside a transaction (count owners, refuse if one), not a hope. It is also the answer to "where do transactions matter here?"

And the rule that never changes: the client never sends its own role, and never sends a familyId it expects to be trusted. The URL may name a family; only the membership row may authorise it.

5. When the exception case is a bug: throw or respond?

This is the question that is hardest to answer by intuition, so state it as a rule:

Situation Nature Do
No session cookie Expected. Users log out, cookies expire. 401, written deliberately in requireAuth
Not a member of the named family Expected. Also a possible attack. 404, written deliberately in loadFamily
A protected route reached a controller with no auth context Impossible if the wiring is right. It is our bug. throw — an assertion, not a response 
export function familyContext(req: Request): { userId: string; family: Family; membership: FamilyMember } {
  const { authenticatedUserId, family, membership } = req;
  if (!authenticatedUserId || !family || !membership) {
    // Unreachable when the chain is correct. It is a tripwire for a wiring bug,
    // which is why it is a 500 and not a 401: 401 would blame the caller and hide
    // the defect, and defaulting to some family would serve the wrong rows quietly.
    throw new Error("Route is missing requireAuth/loadFamily");
  }
  return { userId: authenticatedUserId, family, membership };
}

You have already written this exact pattern once, in client/src/main.tsx: if (!container) throw new Error("Missing #root element"). An impossible state made loud is not defensive programming — it is documentation that runs. The refinement in Express is knowing where the throw lands:

  • A synchronous throw inside a handler or middleware is caught by Express and forwarded as next(err).
  • A rejected promise from an async middleware is also forwarded automatically in Express 5 — "those errors will be passed to the error handler as if calling next(err)" (Express 5 migration guide). No try/catch wrapper needed, and RequestHandler returns unknown, so an async middleware typechecks.
  • Either way it meets errorHandler, which answers 500 — with a precise message in development and a generic one in production. Loud where you can act, silent where you cannot. That is the right split, and it is the reason errorHandler gates on NODE_ENV.
The one-line version

Expected outcomes get a status code. Impossible states get an exception. A 401 hides a wiring bug behind a login form; a throw turns it into a 500 with your own message in it. And if you are ever tempted to "just pick a family" instead — that is the data leak, wearing a helpful face.

6. Deriving the guard list from the router — the honest answer

You asked how to derive checkGuards.ts's PROTECTED array from the router instead of maintaining it by hand. The instinct is right, the mechanism does not exist in Express 5 — and this was measured, not assumed: 

$ npx tsx probe.ts          # express 5.2.1, one nested router

route   /health  [get]
router  path=undefined
   route   /login  [post]
mw      name="requireAuth"
router  path=undefined
   route   /  [get]

# and the layer itself:
own keys : handle, keys, name, params, path, slash, matchers, route
path     : undefined          ← for routes AND for mounts
keys     : []
regexp   : undefined          ← Express 4 had this; 5 does not

layer.route.path is recoverable for a declared route, so you can enumerate a router's own routes. The mount path is not: it now lives in an opaque matchers structure. Which means you can list /people and /login, but you cannot reconstruct /api/families/:slug/people — and the guards you care about are mounted in a different router (routes/index.ts) from the routes themselves (routes/family.routes.ts), so "which guards apply here" requires exactly the flattening you cannot do. Libraries that offer this feature read the same internals and inherit the same fragility.

So make the route table the source of truth instead:

export interface RouteDefinition {
  method: "get" | "post" | "patch" | "delete";
  path: string;                 // full path: "/families/:slug/people"
  isPublic?: boolean;           // absent ⇒ protected. Deny by default.
  guards?: RequestHandler[];    // extra guards, after requireAuth
  handler: RequestHandler;
}

// one loop mounts them, and the same array answers the audit question
export const ROUTES: RouteDefinition[] = [ /* … */ ];

for (const route of ROUTES) {
  const chain = route.isPublic ? [] : [requireAuth, ...(route.guards ?? [])];
  apiRouter[route.method](route.path, ...chain, route.handler);
}

Then the checker iterates ROUTES — the same list that built the app — and asserts the invariant that actually matters: every route without isPublic answers 401 to an unauthenticated request. A newly added route is covered automatically, so the list cannot go stale. That is the real gain: not cleverness, coverage.

Two honest caveats

Parameterised paths cannot be fetched literally. You cannot request /families/:slug/people. Substitute a placeholder — /families/__probe__/people — which works precisely because requireAuth rejects before the slug is ever used, so the 401 does not depend on the parameter's value. The moment you need to assert something deeper than 401, you need a real fixture, and the route table alone is no longer enough.

A hand-written list is not dangerous, only annoying. When /api/people was retired, the stale entry made the check fail loudly (404 ≠ 401) rather than pass silently. Safety comes from deny-by-default and the tripwire; the table buys convenience and coverage. Know which of the two you are buying before you pay for it — with three routes it is not worth it yet; with fifteen it is.
