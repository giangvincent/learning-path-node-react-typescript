Why shared/ is not a package

It has no package.json and no build step. It is a folder of types that both tsconfig.json files include. Because everything in it is type-only, it produces no runtime code — the types vanish at build and cannot leak into the browser bundle.

Read it top to bottom in each direction and memorise it. Every layer violation you will ever be asked about in an interview is a shortcut across this diagram.

3. What each layer owns

Layer Owns Must never
routes/ Binding a URL and verb to one controller; the middleware chain for it. Contain logic, or reach past the controller.
middlewares/ Cross-cutting concerns: who you are, which family, is the body valid, what happens on error. Contain business rules.
controllers/ Reading the request, calling one service, choosing the status code. Contain business logic, or touch the database.
services/ Business rules, orchestration, transactions, permission checks. Know that req and res exist.
models/ Data access: how a thing is stored and retrieved. Contain HTTP or business rules.
views/ Turning a domain object into the resource the client may see. Query the database, or fetch anything.
shared/contracts/ The types both sides compile against. Contain runtime code, or any implementation detail.
client/ Presentation and interaction. Decide permissions, or own the truth about who you are.

4. The honest note about "View"

MVC was invented for server-rendered pages, where the View is an HTML template. KinLink is a JSON API with a React client, so there is no template to render. The View layer survives as the thing that decides the shape of the response — some teams call it a serializer, a presenter, or a resource mapper. It is the same seam.

It earns its place by making one thing impossible: a database column leaking into the UI. When the client needs name but the table stores given_name, middle_name and surname, the View is where that decision is made — once, instead of in twelve components.

5. Response shapes

Every successful response, without exception:

{
  "data": { },
  "meta": { }
}

Every failed response, without exception:

{
  "message": "Validation failed",
  "errors": { }
}

One shape means the client has one error path to write instead of one per endpoint. The single place these are produced is middlewares/errorHandler.ts.

6. Conventions

  • One router file per resource: people.routes.ts, never routes.ts.
  • File names are kebab-case; exported symbols are camelCase functions or PascalCase types.
  • createApp() builds; server.ts listens. Tests import the first and never open a port.
  • Anything that can fail asynchronously goes to next(error); the error handler is the only place that writes a 500.
  • The client's only fetch call lives in client/src/lib/api.ts. Components call functions, not URLs.
  • Contracts use import type. With verbatimModuleSyntax on, a type import can never become a runtime import.
  • The server uses module: NodeNext, so its relative imports end in .js even though the files are .ts. The client uses bundler resolution and omits the extension. That difference is intentional: Node really does need the extension at runtime, the bundler does not.

7. Commands

npm run dev          # api on :4000 and vite on :5173, one terminal
npm run dev:server   # express only
npm run dev:client   # vite only
