Changing a column that already has rows — and when a list earns a page

Two questions that arrive the moment data is real. The first: a column you add today must be filled for rows written yesterday, and filling it with "now" is a lie. The second: every list grows, and pagination is the right answer exactly when the growth is unbounded — not before. Both are answered here with the engine's own rules.

Used by: Lesson 13a–13e Requires: Reference 03 Vocabulary: GLOSSARY.md

1. Expand → backfill → contract

The trap is createdAt DateTime @default(now()) added to a table that already has rows. Prisma emits ADD COLUMN created_at … NOT NULL DEFAULT CURRENT_TIMESTAMP(3), and MySQL fills every existing row with the moment the ALTER ran. Every old invite now claims it was created during the deploy. The migration reports success, because it did exactly what it was told — the schema is right and the data is wrong.

Three steps, in this order, and the order is not stylistic:

-- 1. EXPAND — nullable, no default. Existing rows get NULL, not a lie.
ALTER TABLE invitations ADD COLUMN created_at DATETIME(3) NULL;

-- 2. BACKFILL — the best available truth, in bounded batches.
UPDATE invitations
   SET created_at = expires_at - INTERVAL 7 DAY
 WHERE created_at IS NULL
 LIMIT 1000;              -- repeat until "0 rows affected"

-- 3. CONTRACT — only now is NOT NULL a promise the data keeps.
ALTER TABLE invitations
  MODIFY created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3);

MySQL 8.0 makes step 1 cheap and step 3 expensive, which is exactly the right way round — the cheap, reversible step goes first:

StepAlgorithmRebuilds the table?
Adding a nullable column INSTANT, metadata-only (default since 8.0.12) No
Setting a column default INSTANT, metadata-only No
Making a column NOT NULL INPLACE Yes

The manual is blunt about step 3: making a column NOT NULL "rebuilds the table in place… Data is reorganized substantially, making it an expensive operation" — and "the operation fails if the column contains NULL values". That last clause is why the backfill must come first, and why the order is enforced by the engine rather than by taste.

The honest answer when no source exists

Step 2 needs a real value, and sometimes there is none. If the only thing you know is expiresAt and a fixed TTL, then expires_at - INTERVAL 7 DAY is an estimate — write it down as one. If even that is a guess, the honest move is to leave the column NULL and teach the view to render "unknown". A fabricated timestamp is worse than a missing one: it survives review and outlives the memory that it was invented.

Doing it with Prisma. Prisma can only express the schema, not the intermediate state, so you write the migration by hand — the same technique lesson 06 used for the INSERT … SELECT that had to run before DROP COLUMN users.family_id: 

npx prisma migrate dev --create-only --name add_invitation_created_at
# hand-edit the generated migration.sql to the three statements above
npx prisma migrate dev

Prisma's own guide generalises this to a two-migration expand and contract: expand the schema and deploy, run the backfill as a typed data-migration script, then contract in a second migration. For a single column, one hand-edited migration is the shorter version of the same idea.

2. When a list has earned pagination

The question to ask is not "could this get long?" — everything could. It is: is the size bounded by construction? Three natural bounds exist in KinLink's pending-invite list, and each is a real mechanism rather than a hope:

  • invites expire after 7 days, so old rows leave the query by themselves;
  • the mint refuses a second pending invite for the same email, so duplicates cannot accumulate;
  • the number of people a family is inviting in a given week is small, by the nature of the product.

Nothing in that list is a promise. That is the point: pagination is owed when the bound is structural (an event log, a feed, a family's people over years), not when it is merely plausible. Adding a page envelope early costs every caller a cursor, and it does not make anything faster — the query is already limited by family_id.

The shape to reach for when the bound stops holding

A hard take so a data bug cannot become an unbounded response; an index on the columns the query filters; and a meta.nextCursor — which costs nothing to add later, because ApiResponse already carries an optional meta, so no client breaks when it appears. 

return database.invitation.findMany({
  where: { familyId, usedAt: null, expiresAt: { gt: new Date() } },
  orderBy: [{ createdAt: "desc" }, { id: "desc" }],
  take: 200,        // a data bug must not become an unbounded response
});

Note the tiebreaker: id after createdAt. Two invites created in the same millisecond have no defined order without it, and an unstable sort is a pagination bug waiting to be written.

3. When it is unbounded, use a keyset — never OFFSET

The temptation is LIMIT 20 OFFSET 40. It is wrong twice over. It is slow, because SQL defines it as sorting everything and then dropping the first N rows — Winand quotes the standard: "the rows in the derived table are first sorted according to the <order by clause> and then limited by dropping the number of rows specified in the <result offset clause> from the beginning". And it is incorrect, because a row inserted between two page fetches shifts everything down and the reader sees a duplicate.

The seek recipe replaces the count with the last thing seen:

SELECT ...
  FROM invitations
 WHERE family_id = ?
   AND (created_at, id) < (?, ?)     -- the last row of the previous page
 ORDER BY created_at DESC, id DESC
 LIMIT 20;

Same ORDER BY, same index, no drifting. The cost is that you cannot jump to "page 7" — which is fine for "load more", and the reason keyset pagination is the natural partner of infinite scroll.

The verdict for lesson 13

Do not paginate the pending-invites list. It is bounded by expiry and by the mint's one-per-email rule, and its caller is one owner looking at one family. So the code in this project has no cursor, no page envelope and no cap — and that is a decision, not an omission. Add take the day the shape stops being auditable by eye; add the index when the read measures slow; and add meta.nextCursor the day the bound stops holding. The change that will force it is a filter the user drives ("show used invites too"), because that turns a bounded read into an unbounded one.
