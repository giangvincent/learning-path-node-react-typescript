The Prisma data layer

Rules, conventions and commands for the one layer allowed to touch the database.

Used by: Lesson 02 Vocabulary: GLOSSARY.md

1. Versions, pinned

Package Pin Why
prisma 7.10.0 CLI. latest resolves to an 8.0 release candidate.
@prisma/client 7.10.0 Query API. Must match the CLI exactly.
@prisma/adapter-mariadb 7.10.0 Driver adapter that speaks the MySQL wire protocol.

Prisma releases these in lockstep. Mixed versions produce type errors that look like your mistake and are not.

2. Layer rules

  • Only config/database.ts constructs the client. One client, one pool, shared. A new PrismaClient() inside a request handler opens a new pool per request.
  • Only models/ imports from the generated client. If a controller references prisma, the seam is broken.
  • Models re-export the ORM's types. export type Person = PrismaPerson; — so nothing above knows the ORM's name.
  • Models take plain arguments, never a Request. findAll(familyId: string), not findAll(req).
  • Every query is scoped. If a function returns rows belonging to more than one family, it is a data-isolation bug. There is no exception to this.
  • Models do not decide policy. They fetch. The service decides what may be fetched, and for whom.

3. Naming: code vs database

Prisma field      Column            Rule
──────────────────────────────────────────────────────────────
familyId      →   family_id         @map

Person        →   people            @@map
createdAt     →   created_at        @map

camelCase in code · snake_case in SQL · one mapping, declared once

4. Schema decisions that are already made

Decision Reason
@default(uuid()) Sequential ids leak volume and invite enumeration.
onDelete: Cascade on Person.family A family's people belong to it. Decide the rule explicitly, every time.
@@index([familyId]) Every query filters by family. Without it, MySQL scans the table.
@db.Date on birth and death dates A birthday is a calendar date, not an instant. Storing it as a timestamp invites timezone bugs.
Enums for gender MySQL enforces the values, so bad data cannot arrive by accident.

5. Commands

npm run db:up                  docker compose up -d
npm run db:down                docker compose down

npx prisma migrate dev --name <change>   create + apply a migration, regenerate
npx prisma migrate status                what has and has not been applied
npx prisma generate                      rebuild the client only
npx prisma studio                        browse the data in a browser

npm run db:seed                          hand-written seed script

6. Migration rules

  • A migration is SQL, committed to git, applied once and in order. It is the version history of your schema.
  • Never edit a migration that has run on any machine but your own. Write a new one.
  • prisma/migrations/ is always committed. server/generated/ never is.
  • prisma migrate dev is for development. Production uses migrate deploy, which applies what is committed and never invents a migration.
  • Adding a nullable column is cheap. Adding a required column to a populated table needs a default or a backfill — plan it in three steps, not one.
  • migrate reset drops everything. It is the right tool when a local migration is wrong and nobody else has it yet, and the wrong tool the moment it has been shared.

7. Known rough edges

  • The connection is configured twice. DATABASE_URL for the CLI, discrete DATABASE_* variables for the runtime adapter. Same information, two places.
  • The generated client lives inside the repo and is picked up by tsc. If it ever produces type errors of its own, exclude it from your tsconfig rather than fighting it.
  • Prisma 8 changes schema authoring and migration planning. When you upgrade, expect a real migration task, not a version bump — see Coming from Prisma ORM 7.
