Reference 10 · identity on the client

The client learns who it is

The session lives on the server. The browser holds a cookie that names it and nothing else, so "am I logged in?" is a question the client can only ask — never remember. This reference is the shape of that question, the read that makes "your family" true, and a defect the compiler was structurally unable to see.

Used by: Lesson 13a–13e Requires: Reference 05 Vocabulary: GLOSSARY.md

1. The session is server state; the client mirrors nothing

The cookie is a pointer, not a claim. It says "this browser's session is kinlink.sid=abc…"; the server's store says who that is. So a client that keeps loggedIn: true in a store is holding a second source of truth that goes stale the moment the session expires, the store restarts, or another tab logs out. Fetch the truth; do not copy it.

GET /api/auth/whoami is the ask. It has exactly three shapes of answer:

AnswerMeansClient renders
200 { data: { userId, email } } a session, and it is valid the app
401 no session — nobody is logged in the login screen
5xx the server failed to answer an error
401 is a state, not a failure

This is the line lesson 05 drew on the server — RFC 9110 §15.5.2, "no valid credentials" — finally consumed on the other side of the wire. Code that lumps 401 in with "the request failed" shows a broken-server message to someone who simply has not logged in. Anonymous is a place the UI has a screen for.

2. The state machine

loading ──200──▶ authenticated ──(session dies)──▶ anonymous
   │                                                   │
   ├──401──▶ anonymous ──(login / register ok)─────────┘
   │              ▲
   └──other──▶ error

Four states, and loading is a real one — it is the state before the server has spoken. Skipping it is how a page flashes a login form at a user who is about to be recognised. 

export type SessionState =
  | { status: "loading" }
  | { status: "anonymous" }
  | { status: "error"; message: string }
  | { status: "authenticated"; user: AuthResponse };

export function useSession(): { state: SessionState; refresh: () => void } {
  const [state, setState] = useState<SessionState>({ status: "loading" });
  const [nonce, setNonce] = useState(0);

  useEffect(() => {
    let live = true;

    getSession()
      .then((user) => {
        if (live) setState({ status: "authenticated", user });
      })
      .catch((cause: unknown) => {
        if (!live) return;
        if (cause instanceof ApiError && cause.status === 401) {
          setState({ status: "anonymous" });
          return;
        }
        setState({
          status: "error",
          message: cause instanceof Error ? cause.message : "Unknown error",
        });
      });

    return () => {
      live = false;
    };
  }, [nonce]);

  const refresh = useCallback(() => setNonce((n) => n + 1), []);

  return { state, refresh };
}

Two details earn their keep. The live flag prevents a resolved request from writing state after unmount — the same "cancel the flight you launched" idea as the alive guard in a data-fetching effect. And refresh is how a successful login turns anonymous into authenticated: the form does not fake a user, it asks the server again.

3. The read that makes "your" true: GET /api/families

register returns { userId, email } and, deliberately, no family slug. Before this route existed there were exactly two ways to learn a slug: query the database, or read it as a registration side effect. A browser can do neither — so the client could not name the family it was looking at. 

GET /api/families
→ 200 { "data": [ { "slug": "nguyen-a1b2c3", "name": "Minh's family", "role": "owner" } ] }

It rides requireAuth alone — not loadFamily. That is not an oversight: there is no :slug to resolve, because answering "which families are mine?" is the whole route. The caller is named by the session and by nothing else, and the query carries where: { userId }, so it inherits the property every family-scoped read has: no version of it returns a family the caller has no membership in.

The view drops the family id and ships the slug. An id the client never sees is an id it cannot hand back to a route that might trust it.

4. A defect the compiler could not see

GET /api/auth/whoami answered 500 while npm run typecheck exited 0. The controller hand-wrote a select naming familyId — a column User has not had since the family_members change. Prisma's excess-property check catches that error only when select is alone; add a where beside it and the check is silently dropped. At runtime: Unknown field 'familyId' for select statement on model 'User'.

ShapetypecheckRuntime
findUnique({ select: { id, familyId } }) TS2353 throws
findUnique({ select: { id, familyId }, where }) silent throws
The fix is not "delete the key"

user.model.ts already exported findById(id) — selecting exactly { id, email }. It was written for whoami, and the controller bypassed it to write its own query. Replacing three lines with userModel.findById(userId) fixes the 500 and removes the class of bug: there is now one definition of "a user's public fields", and no hand-written select left to drift out of date.

Where it belongs in history: its own commit, before the feature. It repairs shipped code, so it should be reviewable on its own and greppable by git log/bisect. Its message should name the mechanism typecheck missed, so the history carries the lesson rather than just the diff. And it must land first, by lesson 05's rule — fix the contract before the consumer: a client identity flow built on a 500 teaches the client that "anonymous" means "broken".
