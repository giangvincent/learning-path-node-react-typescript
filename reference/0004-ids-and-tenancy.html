Reference 04 · the three answers worth memorising

Ids, pools and tenancy

Compressed answers to the questions that come up in every system design interview: how big should the pool be, should ids be guessable, and where does a tenant id come from?

Used by: Lesson 03 Vocabulary: GLOSSARY.md

1. The connection pool

connectionLimit is the maximum number of database connections this process holds open. It is a doorway, not a speed limit: excess requests queue, they do not fail. 

10 queries, pool of 5, 400ms each
───────────────��──────────────────────
req 0-4   ~487ms   ran immediately
req 5-9   ~890ms   queued behind them
wall      898ms

Choosing the number

Input Question to answer
MySQL ceiling max_connections (default 151). Pool × instances must stay under it.
Blocking behaviour Database calls are I/O, so the process idles. Pool > thread count is fine.
Little's Law Concurrency ≈ throughput × latency. 100 req/s × 50ms ≈ 5 connections.

Derive it, then measure it. A pool that is too small degrades gracefully; a pool that is too large turns a queue inside your app into a queue inside MySQL and lets a bad query do far more damage at once.

One client, one pool

Construct PrismaClient exactly once, at module scope. A new PrismaClient() inside a request handler opens a fresh pool per request until MySQL refuses connections.

2. Ids

Choice Wins on Costs you
Auto-increment Insert speed, compact index, short URLs, dense index Enumeration — /people/47 reveals volume
UUID v4 Opacity, no coordination, safe to generate client-side 16 bytes, index fragmentation, 36-char URLs
UUID v7 Opacity and time-ordered, so the index stays dense Must be generated in app code, not as a DB default
The rule that matters most

An opaque id is defence in depth, never authorisation. It makes guessing expensive; it does nothing about a caller who legitimately has an id. Every endpoint still checks membership. UUIDs buy a little for free — they are not the answer to access control.

RFC 9562 §5 covers v4 vs v7: datatracker.ietf.org.

3. Tenancy: where the tenant id comes from

BROKEN   GET /api/people?familyId=...        client picks whose data
BROKEN   fetchAll().filter(p => ...)          correct result, wrong cost
CORRECT  session.familyId → where:{ familyId }  server decides, DB filters

The rule

The tenant id is derived from an authenticated session and never appears in a request the client controls. Not in the path, not in the query string, not in the body — unless the caller genuinely belongs to more than one tenant, in which case the membership check must be explicit.

Make it structurally impossible

// Bad: callable in a way that leaks
export async function findAll(): Promise<Person[]>

// Good: the scoping argument cannot be omitted
export async function findByFamily(familyId: string): Promise<Person[]> {
  return prisma.person.findMany({ where: { familyId }, orderBy: { createdAt: "asc" } });
}

A required parameter turns "did I remember to scope this?" from a code-review question into a compiler question.

Which layer decides

Layer Answers
Model "Which rows match this familyId?" — a fact
Service "Which family is this caller allowed to see?" — a policy
Controller Neither. It does not name a family at all.

Separation of concerns is nearby and worth mentioning. The sharper answer, if pressed, is dependency direction: the model must not depend on the request. That sentence survives a follow-up question; an acronym does not.

4. Errors: log, don't leak

if (!isProduction) console.error(error);

const body = isProduction
  ? { message: "Internal server error" }
  : { message: error instanceof Error ? error.message : "Unexpected error" };

A database error message can carry the host, the username and the failing query. The user learns their request failed. They do not learn your topology.
