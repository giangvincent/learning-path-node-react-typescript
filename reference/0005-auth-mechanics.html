Reference 05 · the four questions, compressed

Cookies, cost factors and timing

The four questions that decide whether authentication merely works or is actually defensible: how expensive a password hash should be, what SameSite=Lax really blocks, where sessions live once there is more than one server, and why comparing a secret with == is a bug.

Used by: Lesson 05 Requires: Lesson 04 Vocabulary: GLOSSARY.md

1. The work factor: why 12

bcrypt's cost parameter is an exponent, not a count. The work it performs is 2^cost iterations of an intentionally slow key schedule, so each increment doubles the time — for you and for an attacker. 

cost  2^cost   old 2GHz core (bcrypt README)   modern core, order of
10    1024     ~10 hashes/sec                   ~60–80 ms
11    2048     ~5 hashes/sec                    ~120–160 ms
12    4096     ~2–3 hashes/sec                  ~250–350 ms
13    8192     ~1 sec/hash                      ~600–700 ms
Right rule, wrong anchor

The bcrypt README gives its table for a 2GHz core — that is a decade-old machine. The numbers in the right-hand column are orders of magnitude, not measurement. Run time on your own hardware. The number you can defend is the one you measured; the number you copied is a rumour.

OWASP's Password Storage Cheat Sheet is the authority, and it says three things worth memorising:

  • A minimum work factor of 10, and "as large as verification server performance will allow".
  • Calculating a hash should take less than one second — "strike a balance between security and performance… there is no golden rule."
  • The work factor is stored in the hash output, which is what makes upgrading possible without knowing anyone's password.

So 12 is not magic. It is the common, defensible 2020s default: comfortably above OWASP's floor of 10, and on current hardware it lands in the tens-to-hundreds of milliseconds — slow enough that offline cracking is expensive, fast enough that a login feels instant. If your measured cost at 12 is under ~50 ms, go to 13; if login latency becomes a problem, drop to 11 and write down why.

The honest footnote

OWASP's current text lists bcrypt under "for legacy systems" and recommends Argon2id (19 MiB, t=2, p=1) for new applications, because bcrypt is CPU-hard but not memory-hard, so GPUs like it. bcrypt is still entirely respectable — it is in every language, has no native build step, and is not on anyone's vulnerability list. But if you were starting greenfield today and did not mind a native dependency, Argon2id is the recommendation. Say that out loud in an interview and you sound current.

Upgrading a cost factor, the good way

Because the cost lives inside the stored string ($2b$12$<salt><hash>), you can re-hash on the next successful login — the only moment you legitimately hold the plaintext. 

import bcrypt from "bcrypt";
const CURRENT_COST = 12;

const ok = await bcrypt.compare(password, user.passwordHash);
if (ok && bcrypt.getRounds(user.passwordHash) < CURRENT_COST) {
  // Not a security fix for the existing hash; it upgrades the next one.
  const upgraded = await bcrypt.hash(password, CURRENT_COST);
  await prisma.user.update({
    where: { id: user.id },
    data: { passwordHash: upgraded },
  });
}

Two limits to know cold: bcrypt only uses the first 72 bytes of the password (and bytes, not characters — emoji count as four each), and it truncates silently. Enforce a maximum length at the boundary, or a "password" and a 200-character novel are the same password.

2. Comparing secrets: ==, compare(), timingSafeEqual

Correct the premise first

bcrypt.compare() is not constant-time. The library's own README says so: "the comparison function is not time safe (constant-time), as it may exit early when a mismatch is found." Believing otherwise is not a harmless simplification — it means the next secret you compare will be compared wrongly, because you learned the lesson in the wrong place.

Here is what is actually true, and it is more interesting:

Comparison Does it short-circuit? Attacker learns
a === b / strcmp on a secret Yes — stops at the first differing byte How many leading bytes were correct. Recover the secret one byte at a time: ~256 guesses per byte instead of 256n.
bcrypt.compare(pw, hash) Yes — may exit early, per the README Nothing usable. It compares digests, and a digest is preimage-resistant: an attacker cannot steer their input toward a longer matching prefix without already knowing the answer.
crypto.timingSafeEqual(a, b) No — always reads both, same length Nothing. This is the tool for raw secrets.

There are two separate reasons bcrypt.compare is safe, and you should be able to state both:

  1. The dominant cost is fixed. Recomputing the hash from the supplied password runs the full 2^cost key schedule. That work is identical whether the password is wrong at byte 1 or byte 30, so the early-exit signal is buried under hundreds of milliseconds of constant work.
  2. The thing being compared is a digest. Even with perfect timing resolution, learning "my computed hash shares 7 bytes with the stored hash" is useless — you cannot invert or incrementally search a bcrypt output. Contrast with a session token, where "your guess shares 7 bytes with the real token" is the secret, one byte at a time. 
// The bug — leaks the token one byte at a time
if (req.headers["x-api-key"] === storedToken) { /* ... */ }

// The fix — for raw secrets, not for password hashes
import { timingSafeEqual } from "node:crypto";

const supplied = Buffer.from(req.headers["x-api-key"] ?? "", "utf8");
const expected = Buffer.from(storedToken, "utf8");
const match =
  supplied.length === expected.length && timingSafeEqual(supplied, expected);

timingSafeEqual throws if the buffers differ in length, so the length check has to come first — and note that the comparison is only constant-time when the lengths match. That is exactly what the && above encodes, and it is why docs insist on equal-length inputs. (Node docs — crypto.timingSafeEqual.)

The side channel your code actually has

Your login handler returns in three different amounts of time: a findUnique that misses, a findUnique that hits plus a bcrypt compare (~250 ms), and success plus a session write. The obvious leak is "this email exists". Mitigate with a generic message, rate limiting, and — if you care a lot — a dummy compare against a fixed hash on the miss path. For a private family app that is optional; for a public login it is table stakes.

3. CSRF and SameSite=Lax

CSRF exists because browsers attach cookies automatically. If evil.com makes the victim's browser send a request to kinlink.com, the session cookie goes along, and the server cannot tell the request was not intentional. The server becomes a confused deputy. (OWASP — CSRF Prevention.)

Value Cookie is sent when… You pay
Strict Only same-site requests. Never cross-site, not even a link click. Clicking a link to your site from an email arrives logged out. Real UX cost, so rarely used for sessions.
Lax Same-site requests, plus cross-site requests that are both a top-level navigation and a safe method (GET/HEAD/OPTIONS). Cross-site POST/PUT/DELETE lose the cookie — which is the defence.
None Always. Requires Secure. No CSRF protection; for genuine cross-site embeds only.

So the mechanism, precisely: Lax is safe not because it blocks "cross-site", but because it blocks unsafe methods. A forged request that changes state has to be a POST, PUT, PATCH or DELETE — and none of those carry the cookie. Meanwhile fetch(), <img>, <script> and iframes from another site never carry it either, because they are not top-level navigations. (MDN — Set-Cookie.)

The trap that turns Lax into a hole

Lax still sends the cookie on a top-level GET. So one state-changing endpoint reachable by URL — GET /api/people/:id/delete, GET /logout — defeats the whole thing. An attacker only has to put <img src="https://kinlink.com/api/people/123/delete"> in a page. This is, per OWASP, "the single most common way SameSite-based defences fail in practice."

Four limitations to have ready

  • Never mutate on a safe method. All state changes are POST (or PUT/PATCH/DELETE). Then Lax is genuinely load-bearing.
  • SameSite is scoped to the registrable domain, not the origin. A cookie set on app.kinlink.com is still "same-site" for a request from anything.kinlink.com. One compromised or dangling subdomain re-opens CSRF — which is why subdomain takeover amplifies SameSite bugs.
  • It is a browser feature. Old browsers, embedded webviews and non-browser clients may not enforce it. Defence in depth, not a guarantee.
  • Client-side CSRF is untouched. If your own JavaScript builds a request out of attacker-controlled input (a URL fragment, a postMessage), the request is same-origin and every cookie policy waves it through.

When Lax is enough, and when it is not

OWASP's "sufficient on its own" checklist is short and strict. All of it:

  1. You share the registrable domain with nothing you do not fully control.
  2. No safe method changes state — no mutating GETs, audited.
  3. The cookie is Strict, or Lax with the __Host- name prefix.
  4. Origin/Referer verification on state-changing endpoints, as backup.
  5. You accept the residual risk for browsers that ignore SameSite.

KinLink today meets 2 and 5, and not 1, 3 or 4. That is a defensible "not yet, and here is the list" — which is a much better answer in an interview than "we set lax so we are fine". 

// The __Host- prefix is the cheap one: it forbids a Domain attribute, requires
// Path=/ and requires Secure, so only the exact host that set it can overwrite it.
// Note it CANNOT be used in dev, because dev is http and Secure cookies are dropped.
name: isProd ? "__Host-kinlink.sid" : "kinlink.sid",

4. Where sessions live when you scale

The cookie never holds the data. It holds one opaque id; the data lives in the store. That is the whole design, and it is why sessions and statelessness are compatible: the server is stateless, the store is not.

MemoryStore is not a store

express-session's default is "purposely not designed for a production environment. It will leak memory under most conditions, does not scale past a single process, and is meant for debugging and developing." Two consequences: a restart logs everyone out, and a second instance knows nothing about sessions created on the first.

(express-session README.)

Two ways to run more than one server

Approach How it works Why it hurts
Sticky sessions Load balancer pins a user to the instance that holds their session. Every deploy evicts live users; one hot instance; the pinning is invisible configuration that breaks silently.
Shared store Any instance can serve any request; they all read the same store. Adds a dependency — and that dependency is now on the critical path for every authenticated request.

Redis is the usual shared store because sessions are exactly key-value with a TTL:

npm install redis connect-redis

// server/src/config/session.ts
import { createClient } from "redis";
import { RedisStore } from "connect-redis";

const redisClient = createClient({ url: process.env.REDIS_URL });
redisClient.connect().catch(console.error);

const sessionConfig: SessionOptions = {
  store: new RedisStore({
    client: redisClient,
    prefix: "kinlink:sess:",   // scopes bulk ops; share one Redis safely
  }),
  resave: false,      // the README calls this "required" with connect-redis:
                      // the store implements touch(), so expiry is refreshed
                      // without rewriting the whole session
  saveUninitialized: false,
  secret: process.env.SESSION_SECRET,
  cookie: { /* unchanged: httpOnly, secure, sameSite: "lax" */ },
};

Read that resave: false comment carefully, because it is the detail people get wrong: a store that implements touch() is what makes resave: false safe. Without it, a store that expires idle sessions would never learn that the user is still active. connect-redis implements it and takes the TTL from the cookie's expires, defaulting to one day.

What changes operationally

  • Redis is now a hard dependency. If it is down, nobody stays logged in — you have not lost data, but you have lost every session at once. Persist it (AOF or RDB) or use a managed instance with a replica.
  • Keep the payload tiny. Store userId and familyId, never the whole user object. Every request does a store lookup; the session is not a cache.
  • Redis does not encrypt by default. The cookie is signed; the session body is plain JSON in Redis. Anything in there is readable by anyone with Redis access. Use TLS and auth in production, and put no secrets in the session.
  • SESSION_SECRET is for signing the id, not encrypting the data. It needs ≥32 bytes of entropy. To rotate it without logging everyone out, pass an array: the first signs, all of them verify.
  • Regenerate on login. req.session.regenerate() before you write userId, and again on logout. Otherwise an attacker who can fix a session id before login keeps using it afterwards — session fixation.
The sentence to remember

A cookie-based session is stateless at the edge and stateful at the store. Scaling out means moving "where is the state" from one process's heap to a shared service — and paying for it with a new dependency. A JWT makes the opposite trade: nothing to look up, but revocation becomes guesswork. Neither is modern; they are two prices.

5. Fail-closed routing: making "forgot the guard" hard

A missing requireAuth is invisible to the type system. There is no compile error, no failing test, no 500 — just every family's data, served to anyone. Since the compiler cannot help, you change the default so that the mistake is not available to make. 

// Opt-in (fragile): forgetting the argument leaks data, silently.
apiRouter.use("/people",    requireAuth, peopleRouter);
apiRouter.use("/families",  requireAuth, familiesRouter);   // ← forget it once

// Default-deny (structural): public routes are declared above the guard,
// everything below it is authenticated without being asked.
apiRouter.use("/auth", authRouter);          // public, deliberately
apiRouter.get("/health", liveness);          // public, deliberately

apiRouter.use(requireAuth);                  // the line that does the work
apiRouter.use("/people",    peopleRouter);   // protected automatically
apiRouter.use("/families",  familiesRouter); // and this one, forever

The ordering is the point, and so is the direction the failure points. Add a public route below the guard and you get a loud, obvious 401 in development — annoying, caught in seconds. Forget the guard the old way and you get a silent data leak found by a customer. Choose the direction your mistakes fail in.

Two more layers, each catching what the last cannot: 

// 2. Fail loud, not open. If a route reaches a controller without the guard
//    having run, refuse — do not guess a family.
export function authContext(req: Request): { userId: string; familyId: string } {
  const { authenticatedUserId, authenticatedFamilyId } = req;
  if (!authenticatedUserId || !authenticatedFamilyId) {
    throw new Error("Route is missing requireAuth");   // a wiring bug, not a 401
  }
  return { userId: authenticatedUserId, familyId: authenticatedFamilyId };
}

// 3. Assert it over HTTP, where the mistake is actually visible.
//    server/src/scripts/checkGuards.ts — no framework, no database:
//    requireAuth rejects before the controller, so no query ever runs.
const PROTECTED = ["/api/people"];
for (const path of PROTECTED) {
  const res = await fetch(`${base}${path}`);   // no cookie
  if (res.status !== 401) throw new Error(`${path} → ${res.status}, expected 401`);
}
Why 401 and not 500

RFC 9110 §15.5.2: 401 means "the request has not been applied because it lacks valid authentication credentials". A missing cookie is a missing credential, so 401 is the correct, machine-readable answer. If your guard funnels its error into a generic 500 handler you have told the client "the server is broken" when you meant "tell me who you are" — and no client can build a login flow on that.

6. Corrections to lesson 04

Three claims in the auth lesson were wrong or imprecise. Reference docs win.

Said Actually
"bcrypt.compare() runs in constant time." It may exit early — the README says it is not time-safe. It is safe for a different reason: it compares preimage-resistant digests, and the fixed 2^cost work dominates. Use timingSafeEqual for raw secrets.
"Modern bcrypt has bundled types." bcrypt@6.0.0 ships no types field and no .d.ts. @types/bcrypt is doing real work — keep it.
"sameSite: "lax" prevents CSRF for GET requests." Inverted. Lax allows top-level GETs and blocks cross-site unsafe methods. A mutating GET is the classic way this defence fails.
