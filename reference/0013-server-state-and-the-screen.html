Reference 13 · a write, a cache, and who owns the truth

Server state and the screen

Lessons 16a–16e added the first full CRUD to KinLink: four verbs for people, a screen that shows them, and a cache that keeps up with writes. This is the compressed version — the path a write takes, the shape it sends and returns, and the rule that decides when a client caches anything at all.

1. A write through every layer

A read and a write travel the same six layers. What changes is who decides the scope and who decides the outcome. 

POST /api/families/nguyen/people   {"name":"Nguyễn Văn A","gender":"male"}
  ▼
routes/index       /families/:slug  →  loadFamily (proves membership, else 404)
routes/family      /people          →  createFamilyPerson
  ▼

                   familyContext(req)         -- the family, already proven
                   addPerson(family.id, input)
                   res.status(201).json({ data: toPersonResource(person) })
  ▼
service            addPerson: wire dates → Date; no HTTP in sight
  ▼
model              create(familyId, …)  -- familyId is a required argument
  ▼
MySQL
  ▲
view               toPersonResource: row → { id, name, living }, a whitelist
  ▲
response           { "data": { "id": "…", "name": "Nguyễn Văn A", "living": true } }
The one line that matters

familyId comes from familyContext(req) — a fact the middleware proved — and never from the body. The contract has no field for it, so a client cannot even ask to write into another family. The type makes the bug unrepresentable, which is stronger than any check.

2. The shapes on the wire

TypeFieldsRule it encodes
CreatePersonRequest name, gender, optional birthDate / deathDate Everything a client may set — and no id, no familyId.
UpdatePersonRequest Partial<CreatePersonRequest> An edit sends only what changed. undefined means "leave it"; null means "clear it".
PersonResource id, name, living What a client may see. living is derived (deathDate === null); gender and dates are withheld until a screen needs them.

The resource intentionally carries no familyId — the same rule FamilyResource follows since lesson 13. A client should never hold an id it cannot safely hand back to a route that might trust it.

3. The four verbs, and what each answers

VerbRouteSuccessRefusals
GET/families/:slug/people200 { data: [...] }401 no session · 404 not a member
POST/families/:slug/people201 { data: {...} }400 bad shape · 404 not a member
PATCH/families/:slug/people/:personId200 { data: {...} }400 bad shape · 404 not this family's person
DELETE/families/:slug/people/:personId204 (no body)404 not this family's person
404 covers two facts, on purpose

"No such person" and "not a person in your family" answer identically, because a 403 would confirm the row exists. The server may still tell them apart in its logs; the wire must not. This is the same collapse lesson 06 chose for families, applied to a child resource.

4. Validation belongs at the boundary

A request body is untrusted input from outside the program. It becomes a typed value in the controller — above the service call, so a malformed body never reaches the database and never becomes a 500.

  • name — a non-empty string, trimmed, at most 200 characters.
  • gender — one of male · female · other · unknown (the Prisma enum).
  • birthDate / deathDate — an ISO-parseable string, or null/"" for "no date".

Two rules are worth internalising. First, a partial edit validates only the fields that are present — an absent field is not a wrong field. Second, the conversion from the wire's "YYYY-MM-DD" string to a Date happens in the service: the model should not know about JSON, and the controller owns HTTP, not domain shape.

This is hand-rolled for exactly two shapes. The trigger to adopt a schema validator (Zod) is a third resource needing the same treatment — then it becomes one parser per resource at the boundary, not one per handler.

5. Server state is not client state

The single question that decides where data lives: who owns the truth? The people in a family live on the server. The client holds a cache of them — a copy with an expiry, not an owner.

Server stateClient state
OwnerThe databaseThis browser, this session
Examplespeople, families, invitations, the sessiontree layout, current selection, form inputs, the edit toggle
Can be stale?Yes — that is the defining problemNo; the client just changed it
ToolTanStack Query (a keyed cache + invalidation)useState, or a store once it is shared and complex
The rule that decides when TanStack Query earns its keep

Adopt it on the first screen where a mutation must invalidate a read. Before that, a cache is a store whose most valuable feature has nothing to invalidate. KinLink's read-only screens (session, families, invitations) still fetch by hand for exactly this reason — and that is a decision with a trigger, not a deferral.

6. The cache model, in four lines

  • Key — peopleKey(slug) = ["people", slug]. A key is a name two components must spell the same way, which is why it is exported, not written inline.
  • Query — useQuery({ queryKey, queryFn }) gives you isPending, isError and data, so no screen re-implements those three states and gets them subtly wrong.
  • Mutation — useMutation({ mutationFn, onSuccess }) runs the write. It takes no key; only reads are keyed.
  • Invalidation — invalidateQueries({ queryKey }) marks matching keys stale and refetches the active ones. One create, edit and delete all end here, because all three change what the read would return.
The shortest version of the whole series

A write does not put the new row in the list. It tells the cache this data is stale and lets every reader re-fetch. Copying the row by hand is correct for one screen and lies to every other — the second tab, the tree, the person's own page.

Two rows have no runnable proof. That is stated rather than hidden: an invariant with no proof is a belief, and lesson 13's whole finding was a belief that had been filed as a fact.
