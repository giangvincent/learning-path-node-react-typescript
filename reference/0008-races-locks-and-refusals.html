Reference 08 · the five questions lesson 07 raised

Races, locks, and refusals a client can act on

All five questions are one question seen from five sides: when two requests collide, who decides? The scheduler, the database, the API shape, the data model, or the client. Each answer below says who decides, and why the alternatives decide worse.

Used by: Lesson 08 Requires: Reference 07 Vocabulary: GLOSSARY.md

1. Fire the race on demand, don't wait for it

A race window is the gap between reading a fact your decision depends on and writing the decision: count the owners → write the demotion. If another transaction can change that fact inside the gap, your decision can be made on a world that no longer exists. That is a lost update, and it is invisible until two requests happen to collide inside the window.

Lesson 07's check fired both demotions with Promise.all and hoped the scheduler would land them in the window. The industry name for that is sampling: every run rolls the dice on thread timing. The alternative is to construct the losing interleaving so the bug's precondition is guaranteed, not lucky. Arkency's write-up of exactly this problem states the acceptance rule in one line: "Write a test that FAILS without the lock and PASSES with it." And its warning against the obvious fix is worth quoting too: "Adding sleep statements makes it worse — slower and flaky."

The two pieces: a seam and a gate

Michael Feathers' definition, as quoted in the same post: "A seam is a place where you can alter behavior in your program without editing in that place." You need one at the race window — between the count and the write — and a gate to park inside it. A gate is two promises: one reports arrival, one releases: 

function gate() {
  let arrive!: () => void;
  let open!: () => void;
  const arrived = new Promise<void>((resolve) => (arrive = resolve));
  const opened = new Promise<void>((resolve) => (open = resolve));
  return {
    afterCount: async () => {
      arrive();
      await opened;
    },
    arrived,
    open: () => open(),
  };
}

Then the test plays the collision like a score, and the order is always the same:

  1. t1 runs to the seam — it has counted but not written — and parks.
  2. t2 runs toward the same seam. If it arrives, both transactions have now decided on the same stale fact. This is the losing interleaving, guaranteed.
  3. Release both. Both write. Observe the damage.
  4. With the lock in place, step 2 can never complete: t2 is blocked before it can count. Assert exactly that.

What the table says about "hope"

Look at the fourth row honestly: Promise.all caught the bug 20/20 here. That is not a defence of it. Arkency ran the same technique against their race and it caught nothing — "it simply didn't match the right timing for the race condition to take place." Same technique, two machines, two answers: that is what schedule dependence means. The forced rows never depend on a schedule — the bug is either constructed or excluded, and the answer is the same on every machine, every run. A regression test must fail for the code's sake, never for the scheduler's.

The seam's price, named

The seam must live somewhere, and every option costs something:

  • An explicit hook (changeRole(input, window?) — KinLink's choice). The production signature carries one testing concern; the hook is typed, visible, and inert when unused.
  • Dependency injection — Arkency's choice: the code already had a seam (an injected projection), so the test stubbed it and production stayed untouched: "No test hooks, no debug flags, no conditional logic." Free only when a seam already exists.
  • A mutable test hook (a module-level setGate()). No signature changes, but a hidden global that production could trip over. The worst of the three for the smallest saving.

The trajectory past all three is systematic concurrency testing: Microsoft Research's CHESS "systematically drives the test along all possible thread interleavings" of a scenario instead of hand-picking one, and at the far end FoundationDB simulates whole clusters deterministically because "Determinism is crucial in that it allows perfect repeatability of a simulated run, facilitating controlled experiments to home in on issues." One seam and one gate is the two-dollar version of the same idea: you decide the schedule.

2. FOR UPDATE or an isolation level?

Both tools make check-then-write safe. They differ in scope, and the scope decides this one.

SELECT … FOR UPDATE Isolation level SERIALIZABLE
Scope One statement, the rows it names Every plain SELECT in every transaction
Where it lives At the call site that needs it Connection or server configuration
Failure mode when two collide The second waits, re-reads, and refuses with 409 Locks escalate; one transaction likely dies with a deadlock error
What it costs Wait time on one family's ownership ops Read paths take locks too; throughput and deadlock rate move

The manual on what SERIALIZABLE actually does: "This level is like REPEATABLE READ, but InnoDB implicitly converts all plain SELECT statements to SELECT … FOR SHARE if autocommit is disabled" — and when to reach for it: "used mainly in specialized situations, such as with XA transactions and for troubleshooting issues with concurrency and deadlocks." Every read in the application — the people list included — would start taking shared locks. Two transactions that both read and then write the same rows then hold S locks and ask for X locks on the rows the other holds: the textbook upgrade deadlock.

A labelled prediction, offered as an exercise

Run the forced check under SERIALIZABLE and predict the output first: the invariant should survive (one transaction is rolled back) but as a deadlock error (MySQL 1213), not a 409. The lock version answers the caller; the isolation version kills the request and asks you to build retries. This session did not measure it — treat it as a prediction until you have looked.

The counter-case, from the manual itself

The same page warns against exactly the pattern lesson 07 wrote: "It is not recommended to mix locking statements … with non-locking SELECT statements in a single REPEATABLE READ transaction, because typically in such cases you want SERIALIZABLE." Non-locking reads see a snapshot; locking statements see the present. KinLink does both — a locking read of the families row, then plain reads of family_members. Why it is nonetheless sound here was measured, not argued (row 2 of the table): t2's plain count read 1, the committed world, because the snapshot is established at the transaction's first consistent read — which, with the lock taken before it, happens only after serialization. The third row is the other half of the proof: move the lock after the count and the same plain reads decide on the stale world again (counted 2).

The rule underneath

The lock protects the read, not the write. The pattern is lock → read → decide → write and the ordering is the protection: the decision must be made from a snapshot created after serialization. A FOR UPDATE placed after the check is decoration. And the pattern rests on one discipline: every writer of ownership-relevant rows takes the same lock first — seed scripts and future endpoints included. The moment a writer skips it, the manual's warning applies and SERIALIZABLE becomes the honest answer.

So: FOR UPDATE + the default REPEATABLE READ is the right tool here — one row lock at one site, a refusal the client can act on, and read paths that never block. SERIALIZABLE is the systemic guarantee for when many sites need check-then-write and you cannot trust each author to remember the locking read. For waits you refuse to take, the manual's other two knobs (covered in Reference 07): NOWAIT and SKIP LOCKED.

3. Ownership transfer: one transition, one transaction

POST /api/families/:slug/transfer-ownership   { "to": "<membershipId>", "keepRole": "member" | "admin" }

One endpoint, one transaction: lock, re-read the caller, find the target, promote the target, demote the caller. The user's intent — "Minh owns this family now" — is one fact, and one fact gets one commit. Both writes land or neither does, so no committed state of the world contains a half-transfer.

The honest answer to "why not two steps?" is more interesting than the usual one. Two steps through KinLink's existing API — promote Minh to owner, then demote yourself — cannot break the invariant, because the last-owner guard makes the dangerous order unrepresentable: demoting yourself first just answers 409. What two steps cost is not safety; it is atomicity of intent:

  • A crash between the steps leaves two owners and a transfer that half happened. The audit trail says "Minh was promoted" and never says who was supposed to stop being owner.
  • Two round trips, two authorisation decisions, two chances for the UI to be left in a state it must reconcile.
  • The client must sequence and retry. With one endpoint the unit is the request.

Three traps in the one endpoint

  1. Transfer to self. Promote-me-then-demote-me on one row is a 204 that reaches zero owners. The repair operation must not be a third way to break what it repairs — reject to === caller before the writes.
  2. The in-flight demotion. The route guard proved the caller was an owner when the request arrived. By the time the transaction runs, another owner may have demoted them. Re-read the caller inside the lock; trusting the middleware's copy would let a demoted owner promote anyone. The refusal is 409 not_owner — a state conflict, not a permission verdict.
  3. Retries. Transfer consumes the caller's authority, so it is not naturally idempotent: if the 204 is lost in transit, the retry arrives from a non-owner and gets a refusal for an action that already succeeded. The general remedy is idempotency keys (roadmap week 8); until then the client should re-fetch state when a transfer response is lost.

The counter-case, because a real product may want it: give the recipient a say ("Minh, accept ownership?"), or allow "promote to co-owner now, step down later" with no deadline. Both are legitimate — and both turn one transition into a protocol with state (propose → accept/expire), which is the shape of an invitation. If KinLink's families want that, build it as such, not as two loose endpoints.

4. The rank lives in code

A role_rank table promises "each family defines its own roles". The promise is bigger than the table:

  • The invariants break first. "A family keeps at least one owner" keys on the name owner. With custom roles, which one is the owner? Every invariant must re-key on a capability ("may manage roles", or rank = max(rank)), and "you cannot mint authority above your own" becomes a per-family comparison. The table moves the order; it does not move the authority shape — and the authority shape is what the rules are written against.
  • A rank cannot express permissions anyway. "May edit events but not people" is not a point on a total order — it is a capability set. Ranks answer "or above" and nothing else. The OWASP Authorization Cheat Sheet makes the same distinction: RBAC approximates; relationship- and attribute-based models (ReBAC/ABAC) express.
  • Rows are unreviewed data; code is a review. The satisfies Record<Role, number> map makes a new role a compile error until someone decides its rank — in a pull request, with the invariants beside it. In a table the same decision is an INSERT, and a family that inserts superowner above owner has silently rewritten every rule that keys on the maximum.

The counter-case, stated properly: a table is right when roles genuinely vary per tenant, when changes must ship without a deploy, when non-engineers administer them, or when there are many of them. If KinLink hears that requirement from real families — twice, not once — the migration is small because the checks funnel through one seam: requireRole and a single rankOf. Move the map behind the function to a query, keep an isOwner-style capability for the invariants, and nothing above the middleware notices. Until then: the closed set in code is honest, total, and checked by the compiler.

5. A 409 the client can act on

"A family must keep at least one owner" is true and useless: the client can only show "no". The refusal must answer three questions — what happened (for a human), why (for code), and what now (the next action, as data). RFC 9457 is the standard shape for exactly this; its own motivating example is a client that cannot complete a purchase and should be able to act: "triggering a transfer of more credit into the account" — with an accounts extension listing where to top up. The last-owner refusal is that example re-skinned. 

HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "/problems/last_owner",
  "title": "A family must keep at least one owner",
  "status": 409,
  "code": "last_owner",
  "detail": "Promote another member or transfer ownership, then try again.",
  "remediation": {
    "action": "transfer_ownership",
    "method": "POST",
    "href": "/api/families/nguyen/transfer-ownership",
    "candidates": [
      { "membershipId": "c1f0…", "email": "minh@example.com" },
      { "membershipId": "9a3e…", "email": "lan@example.com" }
    ]
  }
}
Member Job Rule
type Names the problem category URI reference; when relative, "include the full path" — hence /problems/last_owner, not last_owner
title Short human summary of the type "SHOULD NOT change from occurrence to occurrence"
status Repeats the HTTP status for stored bodies Advisory; "MUST use the same status code in the actual HTTP response"
detail This occurrence, for humans "Consumers SHOULD NOT parse the detail member for information; extensions are more suitable and less error-prone"
code Why, for machines Extension member; the field the client branches on
remediation What now, for machines Extension members; the RFC explicitly anticipates "typed links … that machines can use to resolve the problem"
The contract is code, never the sentence

Put code and the remediation in the shared contract as a discriminated union and the client's recovery branch becomes exhaustive and type-checked: problem.code === "last_owner" opens the transfer dialog with problem.remediation.candidates; anything new is a compile error there rather than a silent "no". Parse detail and the contract is a sentence of English that a copy edit will break without a type error. And forward compatibility is the RFC's rule, not a courtesy: "Clients consuming problem details MUST ignore any such extensions that they don't recognize" — so adding a member later cannot break an old client.

Two design notes. Why the candidates ride in the body: the refusal already knows who could fix it, and shipping the way out with the "no" renders the dialog in one round trip. The factoring alternative — a GET /members the dialog fetches separately — is better the moment a member list gets its own screen; the model function is shared, so moving is cheap. What must never ride in the body: internals. RFC 9457's security section is blunt — vet every detail you emit; a problem body is a great place to leak stack traces, other tenants' ids, or SQL. title, detail, code, and facts the caller is already entitled to see (their own family's members) — nothing else.
