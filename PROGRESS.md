# PROGRESS.md — the weekly evidence log

Hours are an **input**. They are necessary and they are not sufficient. The trap is
that a nice graph of tracked hours feels like proof of progress while teaching you
nothing — you can sit at a keyboard for forty hours and be no more senior than when
you started.

So we track two things, and the second one matters more:

1. **Hours by category** — cheap to collect, useful only for noticing the 40-hour
   commitment quietly becoming a 12-hour one.
2. **Artifacts and capability** — commits, exercises, and whether you can actually
   explain, extend and break the code you wrote.

Fill this in once a week. Five minutes. Do it before you start the next week, not
after — the point is to steer, not to score.

## The three signals (from ROADMAP.md)

Answer these honestly. "Partly" is a fine answer; a false "yes" costs you a week.

- **Can explain** — could I walk through this week's code out loud, without looking?
- **Can extend** — did I try one change nobody asked for, to see if the design held?
- **Can break** — did I predict a failure before running it, and was I right?

## Where the numbers come from

| Category | How it is measured |
|---|---|
| Build (in the editor) | WakaTime, automatically, per project |
| Read / watch / docs | Manual timer — WakaTime cannot see a browser |
| Review, notes, planning | Manual timer |
| Passive audit | ActivityWatch, checked weekly, never optimised for |
