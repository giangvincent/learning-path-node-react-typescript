Lesson 08 · Week 4 · about two hours

Transfer ownership, and fire the race on demand

Lesson 07's 409 ends with advice — "transfer ownership first" — and no such operation exists. Today you build it as one transition, make the race check deterministic instead of lucky, and give the 409 a body the client can act on instead of a sentence it can only display.

Mission: ship KinLink Reference: Races, locks, refusals Requires: Lesson 07
The win

POST /transfer-ownership moves ownership in one transaction — and cannot reach zero owners even if you delete its guards, because you will prove you can't with a check that fails on every single run when the lock is wrong. Not sometimes. Every time. Plus: the 409 now carries code: "last_owner" and its remediation, so the client offers "transfer ownership?" with a person picker instead of saying "no".

The feature is small — one service function, one route. The lesson is in the proving. Lesson 07's check:ownership fired two demotions with Promise.all and hoped they collided; today's version decides the collision itself. Read Reference 08 §1 first if you want the full argument — the build below is its skeleton.

Build it

  1. A seam at the race window

    The race window in changeRole is the gap between counting the owners and writing the demotion. To force a collision inside it, the test needs somewhere to park both transactions. That somewhere is a seam (Feathers: "a place where you can alter behavior in your program without editing in that place") — here, one optional hook:

    server/src/services/membership.service.ts (changes) 
    /**
 * A test seam at the race window: the gap between reading the owner count and
 * writing the decision. checkOwnership parks here to force the losing
 * interleaving. Callers that pass nothing are unaffected.
 */
export interface RaceWindow {
  afterCount?: () => Promise<void>;
}

export type RoleChange =
  | { ok: true }
  | { ok: false; reason: "not-found" }
  | { ok: false; reason: "last-owner"; candidates: MemberCandidate[] };

export async function changeRole(
  input: {
    familyId: string;
    membershipId: string;
    nextRole: Role;
  },
  window: RaceWindow = {},
): Promise<RoleChange> {
  return transact(async (tx) => {
    await membershipModel.lockFamily(input.familyId, tx);

    const target = await membershipModel.findByFamily(
      input.familyId,
      input.membershipId,
      tx,
    );
    if (target === null) return { ok: false, reason: "not-found" };

    if (target.role === "owner" && input.nextRole !== "owner") {
      const owners = await membershipModel.countOwners(input.familyId, tx);
      if (owners <= 1) {
        const candidates = await membershipModel.findOtherMembers(
          input.familyId,
          target.id,
          tx,
        );
        return { ok: false, reason: "last-owner", candidates };
      }
      await window.afterCount?.();
    }

    await membershipModel.updateRole(input.membershipId, input.nextRole, tx);
    return { ok: true };
  });
}

    Two changes beyond the seam, both load-bearing later: RoleChange's refusal now carries candidates (the people this owner could transfer to — the service answers the question while it holds the lock, the view will shape it), and the query itself is findOtherMembers, new in the model:

    server/src/models/membership.model.ts (addition) 
    export interface MemberCandidate {
  membershipId: string;
  email: string;
}

/**
 * Everyone in the family except one membership -- the people a last owner could
 * transfer to. The refusal and its way out travel together, so the client can
 * render "transfer ownership?" in one round trip.
 */
export async function findOtherMembers(
  familyId: string,
  selfMembershipId: string,
  database: Db = prisma,
): Promise<MemberCandidate[]> {
  const rows = await database.familyMember.findMany({
    where: { familyId, id: { not: selfMembershipId } },
    include: { user: { select: { id: true, email: true } } },
  });
  return rows.map((row) => ({ membershipId: row.id, email: row.user.email }));
}

  2. The check that fires the race on demand

    A gate is two promises — one that reports arrival at the seam, one that releases it. The test then plays the collision like a score: t1 counts and parks; t2 is sent toward the same window; if t2 arrives, both transactions have decided on the same stale fact and the damage is guaranteed, not lucky.

    server/src/scripts/checkOwnership.ts (rewritten) 
    import "dotenv/config";
import { randomUUID } from "node:crypto";
import { prisma } from "../config/database.js";
import { changeRole } from "../services/membership.service.js";

// A gate: one promise that reports arrival at the race window, one that
// releases it. The test -- not the scheduler -- decides the interleaving.
function gate(): {
  afterCount: () => Promise<void>;
  arrived: Promise<void>;
  open: () => void;
} {
  let arrive!: () => void;
  let open!: () => void;
  const arrived = new Promise<void>((resolve) => (arrive = resolve));
  const opened = new Promise<void>((resolve) => (open = resolve));
  return {
    afterCount: async () => {
      arrive();
      await opened;
    },
    arrived,
    open: () => open(),
  };
}

// Two owners demote themselves in an interleaving the test chooses. t1 counts
// and parks inside the race window; t2 must be blocked before it can count.
// Both of those are asserted -- remove the lock and this fails every run.
async function main(): Promise<void> {
  const slug = `probe-${randomUUID().slice(0, 8)}`;
  const family = await prisma.family.create({
    data: { slug, name: "Ownership probe" },
  });

  try {
    const makeOwner = async (n: number): Promise<string> => {
      const user = await prisma.user.create({
        data: { email: `${slug}-${n}@probe.invalid`, passwordHash: "x" },
      });
      const membership = await prisma.familyMember.create({
        data: { userId: user.id, familyId: family.id, role: "owner" },
      });
      return membership.id;
    };
    const [ownerA, ownerB] = await Promise.all([makeOwner(1), makeOwner(2)]);

    const g1 = gate();
    const g2 = gate();

    const t1 = changeRole(
      { familyId: family.id, membershipId: ownerA, nextRole: "member" },
      { afterCount: g1.afterCount },
    );
    await g1.arrived; // t1 has counted and parked; it holds the family lock

    const t2 = changeRole(
      { familyId: family.id, membershipId: ownerB, nextRole: "member" },
      { afterCount: g2.afterCount },
    );
    // Did t2 reach the race window while t1 sat in it? With the lock it is
    // blocked at lockFamily and cannot. The 400ms is only how long we listen:
    // the invariant assertion below is what makes this check unable to pass
    // against broken code, whatever the machine.
    const t2InWindow = await Promise.race([
      g2.arrived.then(() => true),
      new Promise<boolean>((resolve) => setTimeout(() => resolve(false), 400)),
    ]);

    g1.open();
    g2.open();
    const results = await Promise.all([t1, t2]);

    const refused = results.filter((r) => !r.ok).length;
    const remaining = await prisma.familyMember.count({
      where: { familyId: family.id, role: "owner" },
    });

    console.log(
      `t2 entered the race window while t1 held the lock: ${t2InWindow ? "yes" : "no"}`,
    );
    console.log(`demotions refused: ${refused}`);
    console.log(`owners remaining:  ${remaining}`);

    if (t2InWindow) {
      throw new Error("RACE NOT SERIALIZED: t2 counted while t1 held the lock");
    }
    if (remaining !== 1) {
      throw new Error(
        `INVARIANT BROKEN: ${remaining} owner(s) remain, expected 1`,
      );
    }
    console.log("\nownership invariant held under forced interleaving");
  } finally {
    await prisma.family.delete({ where: { id: family.id } });
    await prisma.user.deleteMany({ where: { email: { startsWith: slug } } });
    await prisma.$disconnect();
  }
}

main().catch((error: unknown) => {
  console.error(error);
  process.exitCode = 1;
});

  3. One transition: transferOwnership

    The repair operation for the last-owner refusal, with three traps closed: it is one transaction (the intent is one fact), it rejects transfer-to-self (promote-me-then-demote-me is a third way to reach zero owners), and it re-reads the caller inside the lock (another owner may have demoted them while the request was in flight).

    server/src/services/membership.service.ts (addition) 
    export type Transfer =
  | { ok: true }
  | { ok: false; reason: "not-found" | "self" | "not-owner" };

export type KeepRole = Extract<Role, "member" | "admin">;

/**
 * Move ownership to another member as one transition.
 *
 * One transaction because the intent is one fact: "Minh owns this family now."
 * Promote the target, demote the caller -- both writes commit or neither does.
 * No count is needed here: the unit either commits with at least one owner or
 * it never happened. (Transfer to *self* would be promote-then-demote of the
 * same row, so it is rejected below.)
 */
export async function transferOwnership(input: {
  familyId: string;
  callerMembershipId: string;
  toMembershipId: string;
  keepRole: KeepRole;
}): Promise<Transfer> {
  return transact(async (tx) => {
    await membershipModel.lockFamily(input.familyId, tx);

    // Re-read the caller INSIDE the lock. The route guard saw their role when
    // the request arrived; another owner may have demoted it since. Trusting
    // the stale copy would let a demoted owner promote anyone.
    const caller = await membershipModel.findByFamily(
      input.familyId,
      input.callerMembershipId,
      tx,
    );
    if (caller === null || caller.role !== "owner") {
      return { ok: false, reason: "not-owner" };
    }

    const target = await membershipModel.findByFamily(
      input.familyId,
      input.toMembershipId,
      tx,
    );
    if (target === null) return { ok: false, reason: "not-found" };
    if (target.id === caller.id) return { ok: false, reason: "self" };

    await membershipModel.updateRole(target.id, "owner", tx);
    await membershipModel.updateRole(caller.id, input.keepRole, tx);
    return { ok: true };
  });
}

    keepRole is what the outgoing owner becomes — member by default, admin if the family wants grandma to keep editing. That default is a product decision, not a technical one: put it in front of a real family and let them tell you.

    One endpoint or two steps? The honest answer

    Two steps through the existing API — promote Minh, then demote yourself — cannot break the invariant: the last-owner guard makes the dangerous order answer 409. What two steps cost is atomicity of intent — a crash between them leaves two owners and a transfer that half happened, and the audit trail never records "and An stopped being owner". One endpoint makes the intent the unit. The counter-case is real too (recipient should accept? "step down later" without a deadline?) — but that is a protocol with state, which is what lesson 09's invitations are. Full argument: Reference 08 §3.

  4. A 409 the client can act on

    A message is prose; a client needs a contract. Three additions to the shared contract — a machine code, a remediation the client can execute, and the problem shape itself (RFC 9457):

    shared/contracts/api.ts (additions) 
    /** Why the server refused -- the field the client branches on. Never parse detail. */
export type ProblemCode = "last_owner" | "not_owner";

/** The way out of a refusal, as data: what to call, and with whom. */
export interface TransferRemediation {
  action: "transfer_ownership";
  method: "POST";
  href: string;
  candidates: { membershipId: string; email: string }[];
}

/** RFC 9457 problem details plus KinLink's extensions. Served as problem+json. */
export interface ApiProblem {
  type: string;
  title: string;
  status: number;
  code: ProblemCode;
  detail: string;
  remediation?: TransferRemediation;
}

    Errors are output shapes, so they belong to the view layer — the layer that decides what the client is allowed to see:

    server/src/views/problem.view.ts (new) 
    import type {
  ApiProblem,
  ProblemCode,
  TransferRemediation,
} from "../contracts.js";
import type { MemberCandidate } from "../models/membership.model.js";

// One place that turns a refusal into its wire shape. The title belongs to the
// problem TYPE and never changes per occurrence; `detail` is per occurrence.
const TITLES: Record<ProblemCode, string> = {
  last_owner: "A family must keep at least one owner",
  not_owner: "Your role changed while this request was in flight",
};

export function problem(input: {
  code: ProblemCode;
  status: number;
  detail: string;
  remediation?: TransferRemediation;
}): ApiProblem {
  return {
    type: `/problems/${input.code}`,
    title: TITLES[input.code],
    status: input.status,
    code: input.code,
    detail: input.detail,
    ...(input.remediation ? { remediation: input.remediation } : {}),
  };
}

export function lastOwnerProblem(
  slug: string,
  candidates: MemberCandidate[],
): ApiProblem {
  return problem({
    code: "last_owner",
    status: 409,
    detail: "Promote another member or transfer ownership, then try again.",
    remediation: {
      action: "transfer_ownership",
      method: "POST",
      href: `/api/families/${slug}/transfer-ownership`,
      candidates,
    },
  });
}

export async function transferOwner(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const { family, membership } = familyContext(req);
    // Express 5: req.body is undefined when nothing parsed it.
    const body = (req.body ?? {}) as { to?: unknown; keepRole?: unknown };
    const to = body.to;
    const keepRole = body.keepRole ?? "member";

    if (
      typeof to !== "string" ||
      (keepRole !== "member" && keepRole !== "admin")
    ) {
      res.status(400).json({
        message: "to must be a membership id; keepRole must be member or admin",
      });
      return;
    }

    const result = await transferOwnership({
      familyId: family.id,
      callerMembershipId: membership.id,
      toMembershipId: to,
      keepRole,
    });

    if (!result.ok) {
      if (result.reason === "self") {
        res.status(400).json({ message: "You already own this family" });
        return;
      }
      if (result.reason === "not-found") {
        res.status(404).json({ message: "Member not found" });
        return;
      }
      // "not-owner": demoted mid-request. A state conflict, not a verdict on
      // the caller -- so 409, and the client reloads and retries.
      res
        .status(409)
        .type("application/problem+json")
        .json(
          problem({
            code: "not_owner",
            status: 409,
            detail:
              "Your role changed while this request was in flight. Reload and try again.",
          }),
        );
      return;
    }

    res.status(204).end();
  } catch (error) {
    next(error);
  }
}

Defend it: why not an isolation level?

SERIALIZABLE would make check-then-write safe everywhere — so why does this codebase reach for one FOR UPDATE instead? Three reasons, and one counter-case you should be able to say out loud (full version in Reference 08 §2):

  • Scope. The manual: SERIALIZABLE "implicitly converts all plain SELECT statements to SELECT … FOR SHARE if autocommit is disabled" — every read in every transaction, the people list included, starts taking locks.
  • Failure mode. Under SERIALIZABLE both demotions read with shared locks and then write with exclusive ones: one transaction dies in a deadlock error and needs retries (this session's prediction, not a measurement — run it and check). Under FOR UPDATE the second waits and refuses with a 409 the client can act on. The lock turns a concurrency problem into a business answer.
  • Legibility. The lock sits at the exact check it protects. An isolation level hides in configuration.
The counter-case, straight from the manual

"It is not recommended to mix locking statements … with non-locking SELECT statements in a single REPEATABLE READ transaction, because typically in such cases you want SERIALIZABLE." KinLink does mix them — a locking read of the family row, plain reads of the memberships. It is sound because the lock is taken before the first plain read, so the snapshot it decides on is already a serialized world (measured: the second transaction counted 1). The rule to remember: the lock protects the read, not the write — lock → read → decide → write. Every writer of ownership rows must hold it, seed scripts included, or the manual wins the argument.

Defend it: why does the rank live in code?

A role_rank table would let each family define roles. It buys the order and breaks the rules: "a family keeps at least one owner" keys on the name owner, and custom roles turn every such invariant into a capability question the table cannot answer. Ranks also cannot express "may edit events but not people" — that is a capability set, not a position on a total order. What code buys: satisfies Record<Role, number> makes a new role a compile error until a human ranks it in a reviewed change — while a row is an INSERT that can quietly insert superowner and rewrite every rule keyed on the maximum. The escape hatch stays open: all checks funnel through requireRole, so if real families ever demand custom roles, move the map behind that seam and re-key the invariants on capabilities (OWASP's ReBAC section is the next read). Both sides: Reference 08 §4.

Break it on purpose

  1. Delete the lock, run the check ten times. Predict the exact output first. You should get yes / 0 / 0 and INVARIANT BROKEN — identical on all ten runs. That repetition is the lesson: last week's Promise.all version gave you a coin flip; this one gives you the bug every time it exists.
  2. The lock stays in the file — move it after the count. Swap the order so countOwners runs before lockFamily. Predict, then run. The check fails again (t2 counted 2), because the snapshot each transaction decides on is established at its first plain read: before the lock, that is a world the lock never excluded. The lock protects the read.
  3. Transfer to yourself. Delete the target.id === caller.id guard, then as sole owner transfer to your own membership id. The repair endpoint answers 204 — and the family has zero owners. The tool that fixes the invariant must not be able to break it.
  4. Trust the middleware. Use membership.role from familyContext in transferOwnership instead of re-reading the caller. Write down the two-request interleaving (two browser tabs, one demoted mid-transfer) that turns a demoted owner into someone who can promote anyone. Which problem code must the demoted-in-flight request receive?
  5. Erase the machine code. Remove code and remediation from the 409 body and write the client branch that offers "transfer ownership". Now edit detail to say "You cannot leave yet." — the branch broke and no compiler noticed. That is the difference between a contract and prose.
