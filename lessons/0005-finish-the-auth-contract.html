Lesson 05 · Week 4 · about 90 minutes

Finish the auth contract: types, 401, and a guard you can't forget

Lesson 04 made authentication run. It did not make it typecheck, and it did not make an unauthenticated request answer honestly. Both have to be true before a client can be built on top — so this lesson closes the contract, and makes forgetting requireAuth structurally hard.

Mission: ship KinLink Reference: Auth mechanics Requires: Lesson 04
The win

npm run typecheck goes from 10 errors to 0 without a single unsafe cast. An unauthenticated request answers 401 instead of lying with a 500. And a ninth protected resource can be added with one line, because authentication becomes the default rather than an argument you have to remember — backed by a one-command guard check you wrote yourself, with no test framework and no database.

Why this lesson exists

Two reasons, and the first one is not optional.

The compiler is already complaining. Ten errors, all in the auth layer you committed last session:

Read that list again and notice it is not ten problems. It is one problem with ten symptoms: nothing has told TypeScript what you attach to a request. The as unknown as SessionWithUser cast was papering over the missing declaration, which is why the cast exists in the first place — a cast is usually a type you declined to write down.

Why this blocks the client

server/src/middlewares/auth.ts calls req.next(new Error("Authentication required")). That error lands in errorHandler, which answers 500. So today an unauthenticated request is told "the server is broken" when the truth is "you haven't told me who you are". A client cannot build a login flow on that: it can never distinguish 401 → show the login form from 500 → show the crash page. The status code is part of the contract, and the contract is unfinished.

Build it

  1. Declare what you attach — once

    Two things get attached at runtime: userId/familyId onto req.session, and authenticatedUserId/authenticatedFamilyId onto req. Both need a declaration.

    server/src/types/express.d.ts 
    import "express-session";

// express-session declares SessionData inside its own `session` namespace, so
// the merge path is the module. This is the idiom its own docs recommend.
declare module "express-session" {
  interface SessionData {
    userId?: string;
    familyId?: string;
  }
}

// It augments Request from the *global* Express namespace, so this merge path
// is different -- same file, same idea, two different places in the types.
declare global {
  namespace Express {
    interface Request {
      authenticatedUserId?: string;
      authenticatedFamilyId?: string;
    }
  }
}

// Without this the file is a script, and `declare global` is illegal in a
// script. One line, load-bearing.
export {};
    Why two different merge styles, honestly

    Because the two types live in two different places. In @types/express-session, Request is declared at line 10 inside declare global { namespace Express { … } }, while SessionData is declared around line 212 inside declare namespace session — the module's own export. Declaration merging has to target the namespace the interface actually lives in. If you get it wrong you get "no exported member", not a silent no-op, which is a mercy.

    The file must live inside the program

    tsconfig.json includes ["server/src", "shared"], so this file has to be under one of those two. Put it anywhere else — a server/types/ folder beside src, the repo root — and TypeScript never reads it and never says so. No error, no warning: the file is simply not part of the program, so all ten errors stay exactly as they were and you go looking for a bug in the wrong place.

    Ambient declarations do not fail loudly. They fail by doing nothing — which is the same trap as the missing requireAuth, in a different costume.

    The fields are optional on purpose, and the honesty is worth the small cost: they genuinely are absent on public routes. Declaring them as string would be a prettier lie that reintroduces exactly the bug this lesson is about — a value typed as present that is undefined at runtime.

  2. The guard, with no casts and an honest status code

    server/src/middlewares/auth.ts 
    import type { Request, RequestHandler } from "express";
import type { ApiErrorBody } from "../contracts.js";

/**
 * Reject unauthenticated requests. 401, not 500: nothing failed on the server,
 * the caller simply did not present credentials.
 */
export const requireAuth: RequestHandler = (req, res, next) => {
  const { userId, familyId } = req.session;

  if (!userId || !familyId) {
    const body: ApiErrorBody = { message: "Authentication required" };
    res.status(401).json(body);
    return;
  }

  req.authenticatedUserId = userId;
  req.authenticatedFamilyId = familyId;
  next();
};

/**
 * Read the auth context, refusing to guess.
 *
 * Anything mounted below requireAuth will have set these. If they are missing we
 * have a wiring bug -- a route reached a controller without the guard -- and a
 * wiring bug must fail loudly rather than quietly reading the wrong rows.
 */
export function authContext(req: Request): { userId: string; familyId: string } {
  const { authenticatedUserId, authenticatedFamilyId } = req;

  if (!authenticatedUserId || !authenticatedFamilyId) {
    throw new Error("Route is missing requireAuth");
  }

  return {
    userId: authenticatedUserId,
    familyId: authenticatedFamilyId,
  };
}

    Note what disappeared: SessionWithUser, and both casts. The middleware is now eleven lines of obvious code, because the interesting part moved into the declaration from step 1.

  3. Make authentication the default

    This is the answer to the question you asked: how do you make the missing-requireAuth mistake harder to repeat? Your answer — "wrap multiple routes into a group, and add new routes inside the group" — is the right instinct, and Express can make it structural rather than conventional. Declare the public routes, then put the guard in the middle of the file and let everything below it inherit protection.

    server/src/routes/index.ts 
    import { Router } from "express";
import type { ApiResponse } from "../contracts.js";
import { requireAuth } from "../middlewares/auth.js";
import { authRouter } from "./auth.routes.js";
import { peopleRouter } from "./people.routes.js";

export const apiRouter = Router();

// ---------------------------------------------------------------- public ----
// Deliberately reachable without a session. Everything above the guard is a
// decision someone made on purpose.
apiRouter.get("/health", (_req, res) => {
  const body: ApiResponse<{ status: "ok" }> = { data: { status: "ok" } };
  res.status(200).json(body);
});

apiRouter.use("/auth", authRouter);

// ----------------------------------------------------------------- guard ----
// Everything below this line is authenticated. There is no argument to forget
// and no per-route annotation to copy; a new router added down here is
// protected the moment it is mounted.
apiRouter.use(requireAuth);

// ------------------------------------------------------------- protected ----
apiRouter.use("/people", peopleRouter);
    The real principle: choose the failure direction

    Add a public route below the guard by mistake and it returns 401 — loud, obvious, caught in seconds. Forget the guard the old way and every family reads every family's data — silent, caught by a customer. Both are mistakes; only one of them is survivable. Moving the guard to a single line is not just DRY, it converts a silent failure into a noisy one, which is the only kind of failure you actually get to learn from.

  4. The controller stops reaching into the request

    server/src/controllers/people.controller.ts 
    import type { NextFunction, Request, Response } from "express";
import type { ApiResponse, PersonResource } from "../contracts.js";
import { authContext } from "../middlewares/auth.js";
import { listPeople } from "../services/people.service.js";
import { toPersonResource } from "../views/person.view.js";

export async function getPeople(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const { familyId } = authContext(req);
    const people = await listPeople(familyId);

    const body: ApiResponse<PersonResource[]> = {
      data: people.map(toPersonResource),
    };

    res.status(200).json(body);
  } catch (error) {
    next(error);
  }
}

    Delete the local RequestWithAuth interface — it was the thing breaking people.routes.ts, because a handler expecting a narrower request is not assignable where Express expects the general one. With the fields declared globally, req is just Request, and the overload error evaporates.

    authContext(req) is the third layer of defence. The model already makes an unscoped query impossible (lesson 03 gave findByFamily a required argument). This makes the consequence of a missing guard loud: a wiring bug becomes a 500 that says Route is missing requireAuth, not an empty list or someone else's family.

  5. Prove it, with no framework and no database

    A missing middleware is invisible to the compiler, so the compiler can never be the answer. What catches it is a request. You do not need Vitest, Supertest or a running MySQL for this — you need createApp(), an ephemeral port, and fetch.

    server/src/scripts/checkGuards.ts 
    import { createApp } from "../app.js";

// Deliberately no cookie. requireAuth rejects before any controller runs, so
// this script never touches the database -- MySQL does not need to be up.
const PROTECTED = ["/api/people"];

async function main(): Promise<void> {
  // Port 0 asks the OS for a free port, so this never collides with `npm run dev`.
  const server = createApp().listen(0);
  await new Promise<void>((resolve, reject) => {
    server.once("listening", resolve);
    server.once("error", reject);
  });

  const address = server.address();
  if (address === null || typeof address === "string") {
    throw new Error("Expected a TCP address from listen(0)");
  }
  const base = `http://127.0.0.1:${address.port}`;

  const failures: string[] = [];
  for (const path of PROTECTED) {
    const response = await fetch(`${base}${path}`);
    const passed = response.status === 401;
    console.log(`${passed ? "ok  " : "FAIL"} ${path} -> ${response.status}`);
    if (!passed) failures.push(`${path} -> ${response.status}, expected 401`);
  }

  server.closeAllConnections();
  await new Promise<void>((resolve) => server.close(() => resolve()));

  if (failures.length > 0) {
    console.error(`\n${failures.length} guard check(s) failed`);
    process.exitCode = 1;
  } else {
    console.log(`\n${PROTECTED.length} guard check(s) passed`);
  }
}

main().catch((error: unknown) => {
  console.error(error);
  process.exitCode = 1;
});
    package.json (scripts, excerpt) 
    "check:guards": "tsx server/src/scripts/checkGuards.ts"
    npm run check:guards

ok   /api/people -> 401

1 guard check(s) passed
    A note on what this is not

    It is a smoke check, not a test suite — the real pyramid (Vitest, unit vs integration boundaries, coverage you can defend) is week 7, deliberately. What it buys you today is that the guard now has to be checked by doing, and the PROTECTED list is a written-down claim about what you protect. When the list is wrong, the list is wrong on purpose and visible in a diff — which is far better than being wrong invisibly.

  6. Fix the comment, not the code

    Your login handler carries a comment claiming bcrypt.compare() is "constant-time comparison". It is not, and the wrongness matters — see Reference 05. The code is correct; only the claim is wrong. Comments are claims, and a claim that misleads the next reader is a bug in the cheapest place to fix it.

    server/src/controllers/auth.controller.ts (comment only) 
        const match = await bcrypt.compare(password, user.passwordHash);
    if (!match) {
      // compare() may exit early, but it compares digests, so the fixed 2^cost
      // work dominates and an early exit leaks nothing usable. The timing signal
      // that does exist is elsewhere: a hit runs a bcrypt round and a miss does
      // not, so "no such user" and "wrong password" are distinguishable. Keep the
      // message generic and rate limit.
      res.status(401).json({ message: "Invalid credentials" });
      return;
    }

Break it on purpose

Predict the failure before you run it. Every one of these has a specific expected shape, and being wrong is more instructive than being right.

  1. In routes/index.ts, move apiRouter.use("/people", peopleRouter) above apiRouter.use(requireAuth). Predict what npm run check:guards prints, then run it. You should get 500, not a leak — and the server log should say Route is missing requireAuth. Now say out loud why the failure was loud: which layer caught it, and what it would have caught if findByFamily still had no required argument? (That is lesson 03, paying you back.)
  2. Change res.status(401) in requireAuth to res.status(500). Run npm run check:guards. It fails — and this is the lesson's actual thesis: the status code is part of the contract. Then try reverting to the original req.next(new Error(...)) and explain why you get the same 500 with a different message.
  3. Add a second protected router: create routes/family.routes.ts with one GET / handler that returns { data: [] }, and mount it below the guard. Add its path to PROTECTED in checkGuards.ts and run it. Now answer the uncomfortable follow-up: the PROTECTED list is still hand-maintained. What could derive it automatically, and what would that cost you in brittleness?
  4. Delete server/src/types/express.d.ts and run npm run typecheck. Predict the error count before you look. Then restore it. The declaration file is not documentation — it is load-bearing structure, and deleting it re-breaks five files.
  5. Now the quieter version. Move the file up one level to server/types/express.d.ts and run npm run typecheck. Predict what you will see, then look. The answer is nothing about the file — no warning that it is ignored, and all ten errors back. Then move it to a differently-named folder that is included, such as server/src/ambient/, and confirm it still works. Say out loud what actually decides whether a declaration is read: not the folder's name, not the extension — only whether include reaches it.
