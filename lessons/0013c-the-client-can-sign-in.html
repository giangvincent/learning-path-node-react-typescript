Lesson 13c · Week 4–5 · about 60 minutes · one new thing

The client can sign in

The server now answers both questions a browser needs — "who am I?" and "which families are mine?" — and the browser still cannot ask either. This sitting gives the client one transport helper, a session hook with four states, and a login screen. The window is the one the client opens on: it signs in and sees the families the previous sitting made real.

Mission: ship KinLink Requires: Lesson 13b Reference: 10 Practice: Lesson 13e
The win

Four states — loading, anonymous, error, authenticated — and a login form that appears for exactly one of them. Sign up in the browser and the list of your families renders, from a slug the client was given rather than one it guessed.

Build it

  1. The client's one fetch helper

    The old lib/api.ts had a single function that fetched /api/people — not a mounted route. Delete it; people live at /api/families/:slug/people and will get their own function when a screen needs one. In its place, one helper that owns the envelope and the status.

    client/src/lib/api.ts (rewritten) 
    import type {
  ApiResponse,
  AuthResponse,
  FamilyResource,
  InvitationResource,
} from "../contracts";

/**
 * A failed response, carrying the status so callers can tell "you are not logged
 * in" (401) from "the server broke" (500). Lesson 05 drew that line on the
 * server; this is the client finally consuming it.
 */
export class ApiError extends Error {
  constructor(
    readonly status: number,
    message: string,
  ) {
    super(message);
    this.name = "ApiError";
  }
}

/**
 * One fetch, one envelope. Components call named functions with types, never
 * URLs, and nothing here throws for a 401 -- it throws an ApiError, and the
 * caller decides what a 401 means.
 */
async function request<T>(
  path: string,
  options: { method?: "GET" | "POST"; body?: unknown } = {},
): Promise<T> {
  const response = await fetch(path, {
    method: options.method ?? "GET",
    credentials: "include",
    headers:
      options.body === undefined
        ? undefined
        : { "Content-Type": "application/json" },
    body: options.body === undefined ? undefined : JSON.stringify(options.body),
  });

  if (!response.ok) {
    throw new ApiError(
      response.status,
      `${options.method ?? "GET"} ${path} -> ${response.status}`,
    );
  }
  if (response.status === 204) {
    return undefined as T;
  }

  const body = (await response.json()) as ApiResponse<T>;
  return body.data;
}

export function getSession(): Promise<AuthResponse> {
  return request<AuthResponse>("/api/auth/whoami");
}

export function login(input: {
  email: string;
  password: string;
}): Promise<AuthResponse> {
  return request<AuthResponse>("/api/auth/login", {
    method: "POST",
    body: input,
  });
}

export function register(input: {
  email: string;
  password: string;
}): Promise<AuthResponse> {
  return request<AuthResponse>("/api/auth/register", {
    method: "POST",
    body: input,
  });
}

export function getFamilies(): Promise<FamilyResource[]> {
  return request<FamilyResource[]>("/api/families");
}

export function getInvitations(slug: string): Promise<InvitationResource[]> {
  return request<InvitationResource[]>(
    `/api/families/${encodeURIComponent(slug)}/invitations`,
  );
}
    credentials: "include" is load-bearing

    Without it the browser does not attach the session cookie to a cross-origin fetch, and every request here answers 401. In development Vite proxies /api to Express, so the origin is the same and this looks unnecessary — it is not, and it is exactly the kind of thing that survives to production and then breaks there. Set it once, in the helper.

  2. useSession — four states, one question

    The session is server state, so the truth is fetched. This hook is the fetch, plus the only genuinely interesting decision in the client: a 401 is not an error.

    client/src/lib/useSession.ts (new) 
    import { useCallback, useEffect, useState } from "react";
import type { AuthResponse } from "../contracts";
import { ApiError, getSession } from "./api";

export type SessionState =
  | { status: "loading" }
  | { status: "anonymous" }
  | { status: "error"; message: string }
  | { status: "authenticated"; user: AuthResponse };

/**
 * Who is this browser, according to the server?
 *
 * The session lives on the server, so the truth is fetched, never mirrored into
 * a client store. Three outcomes, three states: a 401 is "not logged in" -- an
 * ordinary state the UI renders a login form for -- while anything else is a
 * fault worth showing.
 */
export function useSession(): { state: SessionState; refresh: () => void } {
  const [state, setState] = useState<SessionState>({ status: "loading" });
  const [nonce, setNonce] = useState(0);

  useEffect(() => {
    let live = true;

    getSession()
      .then((user) => {
        if (live) setState({ status: "authenticated", user });
      })
      .catch((cause: unknown) => {
        if (!live) return;
        if (cause instanceof ApiError && cause.status === 401) {
          setState({ status: "anonymous" });
          return;
        }
        setState({
          status: "error",
          message: cause instanceof Error ? cause.message : "Unknown error",
        });
      });

    return () => {
      live = false;
    };
  }, [nonce]);

  const refresh = useCallback(() => setNonce((n) => n + 1), []);

  return { state, refresh };
}

    Two things to notice. The live flag means a response that arrives after unmount cannot write state — the same discipline as ignoring a stale fetch. And refresh is a counter, not a mutation: a successful login does not construct an authenticated user, it asks the server again. One source of truth, one write path.

  3. The login screen — an answer to "no session", not an error page

    client/src/LoginScreen.tsx (new) 
    import { useState } from "react";
import type { FormEvent } from "react";
import { ApiError, login, register } from "./lib/api";

/**
 * The screen the client shows when the server says "I do not know you".
 *
 * Login and register are one form because they are one question -- "who are
 * you?" -- and the only difference is which endpoint answers. Both leave a
 * session cookie behind, which is why success just refreshes the session.
 */
export default function LoginScreen({ onSignedIn }: { onSignedIn: () => void }) {
  const [mode, setMode] = useState<"login" | "register">("login");
  const [email, setEmail] = useState("");
  const [password, setPassword] = useState("");
  const [error, setError] = useState<string | null>(null);
  const [pending, setPending] = useState(false);

  const submit = async (event: FormEvent) => {
    event.preventDefault();
    setPending(true);
    setError(null);
    try {
      await (mode === "login"
        ? login({ email, password })
        : register({ email, password }));
      onSignedIn();
    } catch (cause: unknown) {
      setError(
        cause instanceof ApiError && cause.status === 401
          ? "Wrong email or password."
          : "That did not work. Try again.",
      );
    } finally {
      setPending(false);
    }
  };

  return (
    <main style={{ fontFamily: "system-ui, sans-serif", padding: "2rem" }}>
      <h1>KinLink</h1>
      <h2>{mode === "login" ? "Log in" : "Create your family"}</h2>

      <form onSubmit={submit}>
        <p>
          <input
            type="email"
            value={email}
            onChange={(event) => setEmail(event.target.value)}
            placeholder="email"
            required
          />
        </p>
        <p>
          <input
            type="password"
            value={password}
            onChange={(event) => setPassword(event.target.value)}
            placeholder="password"
            required
          />
        </p>
        <button type="submit" disabled={pending}>
          {pending ? "Working…" : mode === "login" ? "Log in" : "Sign up"}
        </button>
      </form>

      {error && <p role="alert">{error}</p>}

      <p>
        <button
          type="button"
          onClick={() => setMode(mode === "login" ? "register" : "login")}
        >
          {mode === "login" ? "Need an account?" : "Already have an account?"}
        </button>
      </p>
    </main>
  );
}
    Import the event type by name

    import type { FormEvent } from "react" is not decoration. Under verbatimModuleSyntax and jsx: react-jsx there is no React value in scope, so writing React.FormEvent fails with TS2686: 'React' refers to a UMD global, but the current file is a module.

  4. Wire it up, and render your families

    Home is the three states of a session; FamilyList renders only once the session is known, because "which families?" is a question only an identity can answer. The link to each family's invites page is the next sitting's job — today the names render as plain text.

    client/src/App.tsx (rewritten) 
    import { useEffect, useState } from "react";
import { Route, Routes } from "react-router-dom";
import AcceptPage from "./AcceptPage";
import LoginScreen from "./LoginScreen";
import type { FamilyResource } from "./contracts";
import { getFamilies } from "./lib/api";
import { useSession } from "./lib/useSession";

/**
 * The families this session belongs to. Rendered only once the session is
 * known, because "which families?" is a question only an identity can answer.
 */
function FamilyList() {
  const [families, setFamilies] = useState<FamilyResource[] | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    getFamilies()
      .then(setFamilies)
      .catch((cause: unknown) =>
        setError(cause instanceof Error ? cause.message : "Unknown error"),
      );
  }, []);

  if (error) return <p role="alert">Failed to load: {error}</p>;
  if (!families) return <p>Loading…</p>;

  return (
    <main style={{ fontFamily: "system-ui, sans-serif", padding: "2rem" }}>
      <h1>KinLink</h1>
      <ul>
        {families.map((family) => (
          <li key={family.slug}>
            {family.name} — you are {family.role}
          </li>
        ))}
      </ul>
    </main>
  );
}

/** The three states of a session: unknown, absent, present. */
function Home() {
  const { state, refresh } = useSession();

  if (state.status === "loading") return <p>Checking your session…</p>;
  if (state.status === "error") return <p role="alert">{state.message}</p>;
  if (state.status === "anonymous") return <LoginScreen onSignedIn={refresh} />;
  return <FamilyList />;
}

export default function App() {
  return (
    <Routes>
      <Route path="/invite/:token" element={<AcceptPage />} />
      <Route path="/" element={<Home />} />
    </Routes>
  );
}

Two sessions, one browser

A cookie is per browser, not per tab, so you cannot be logged in as two users in two tabs of the same profile. Use one normal window and one private window — the same trick you will need for the invitation flow, where the inviter and the invitee must be different people.
