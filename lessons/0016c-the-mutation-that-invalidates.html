The mutation that invalidates

This is the screen the last three sessions were waiting for: the first place where a write must be reflected in a read. The cache added in 16b finally has something to do — and the reason it is worth a dependency becomes visible in three lines.

Mission: ship KinLink Requires: Lesson 16b References: 13 Practice: Lesson 16f
The win

A small form on the people screen creates a person and the list updates itself. Not because anyone copied the new row into local state, but because the mutation invalidated the key the read uses and the cache re-fetched. One rule, and every reader of that key is correct.

Warm-up: retrieve before rereading

Five minutes, from memory. What key did the people read use, and why is it exported rather than written inline? Answer before you scroll back to Reference 13. Today's whole lesson turns on that key being a name two components share.

  2. The transport learns the write verb

    The private request helper takes a fixed set of methods. A write needs POST added to that union — and since the rest of this series needs the other verbs too, widen it once, to the four this API actually serves.

    Then the named call. Note it is the same request as the reads, so it inherits the envelope and the 401 rule for free: a dead session during a create is announced app-wide, exactly as it would be on a read.

  3. A mutation and its invalidation

    useMutation runs the write. onSuccess is where the cache is told the truth changed. That is the entire mechanism — there is no manual setState of the list, and that absence is the design.

    client/src/PeoplePage.tsx (the form) 
    import { useMutation, useQuery, useQueryClient } from "@tanstack/react-query";
import { useState } from "react";
import type { FormEvent } from "react";
import type { Gender } from "./contracts";
import { ApiError, createPerson, getPeople } from "./lib/api";

const GENDERS = ["male", "female", "other", "unknown"] as const;

function isGender(value: unknown): value is Gender {
  return typeof value === "string" && (GENDERS as readonly string[]).includes(value);
}

function AddPersonForm({ slug }: { slug: string }) {
  const queryClient = useQueryClient();
  const [name, setName] = useState("");
  const [gender, setGender] = useState<Gender>("unknown");
  const [error, setError] = useState<string | null>(null);

  const add = useMutation({
    mutationFn: (input: { name: string; gender: Gender }) =>
      createPerson(slug, input),
    onSuccess: () => {
      setName("");
      setError(null);
      void queryClient.invalidateQueries({ queryKey: peopleKey(slug) });
    },
    onError: () => setError("That did not work. Try again."),
  });

  const submit = (event: FormEvent) => {
    event.preventDefault();
    const trimmed = name.trim();
    if (trimmed === "") {
      setError("A name is required.");
      return;
    }
    add.mutate({ name: trimmed, gender });
  };

  return (
    <form onSubmit={submit}>
      <input
        value={name}
        onChange={(event) => setName(event.target.value)}
        placeholder="Name"
      />
      <select
        value={gender}
        onChange={(event) => {
          if (isGender(event.target.value)) setGender(event.target.value);
        }}
      >
        {GENDERS.map((option) => (
          <option key={option} value={option}>
            {option}
          </option>
        ))}
      </select>
      <button type="submit" disabled={add.isPending}>
        {add.isPending ? "Adding…" : "Add person"}
      </button>
      {error && <span role="alert"> {error}</span>}
    </form>
  );
}

    Why invalidate, and not "just add the row"

    The tempting shortcut is to push the created person into local state. It works for the screen that created it and lies to every other reader — the tree view, a second tab, the person's own page. Invalidating the key says one true thing ("this data is stale") and lets every reader re-fetch. It also handles what the client cannot know: server-set fields, other people's concurrent edits, ordering.

Verify after

npm run typecheck     # exit 0
npm run build:client  # exit 0

Then do it by hand, because this is a behaviour and not just a compile. Sign in, open the family's people screen, add a name, and watch the list grow without a reload. Add two in a row — the input clears after each, and the list keeps up. Now open the same screen in a second tab and add a name in the first: the second tab does not update until it re-focuses or reloads. That is expected, and worth saying out loud — a cache on one client cannot see another client's writes.

Break it on purpose — predict first

Delete the invalidateQueries line from onSuccess. Predict what the screen does after a successful create. Then run it: the person is created — check curl or the next reload — but the list does not move. The write succeeded and the read is stale, and no error tells you. That silent half-truth is the exact bug the cache exists to prevent; put the line back and watch it disappear.

Decisions carried into the next sittings

  • No optimistic update yet. An optimistic update paints the row before the server confirms it, then rolls back on failure. It is the right tool when a round trip is slow enough to see — which this is not, on localhost, with one row. It is also the tool that produces "ghost" rows when the rollback is wrong. Add it when a measured round-trip is annoying, not because it looks clever.
  • Errors are minimal on purpose. The form shows "That did not work" for any failure; the server's sentence ("name must be a non-empty string…") reaches the client in the response body but is not shown yet. That is a real gap, and a small one: ApiError would need to carry the body. Decide whether KinLink shows raw server prose or maps status to its own copy — do not half-do both.
  • The mutation key is not the query key. useMutation needs no key; only the query does. If you find yourself naming a mutation key, check you are not reaching for setQueryData.
