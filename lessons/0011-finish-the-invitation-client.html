House rule (effective from this lesson)

Every lesson that touches code now opens with a Verify paragraph, listing the exact commands that prove green. The author runs them against the lesson's verbatim code shape against main, and the lesson is not considered finished until they exit 0. Three corollaries the lesson-10 mistakes make concrete:

  1. Lesson code that doesn't compile is a bug, not a draft. If the lesson text contains verbatim code blocks and npm run typecheck would error on them, the lesson is wrong — not the runner. Lesson 10's controller had two errors and should never have shipped inside a lesson.
  2. Every new module is named, installed, and verified to resolve. If the lesson says import { useParams } from "react-router-dom", the lesson text must (a) say which package adds the symbol, (b) show the exact install command, and (c) include a Verify step that asserts the import resolves. Lesson 11 does all three.
  3. Stubs are not step bodies. A handler whose body is // ... then createInvitation(...) teaches nothing the reader can run. Either the body is implemented (and is the lesson's working code), or the route is removed.

  2. Mount the router, split the two endpoints

    The two endpoints have different guards, so they live in two different routers on two different paths. Don't merge them: the create route rides on loadFamily (the slug must resolve to a family the caller belongs to); the accept route doesn't (the invitee is not a member yet — by definition).

    server/src/routes/invitation.routes.ts (replace) 
    import { Router } from "express";
import { requireAuth, authContext } from "../middlewares/auth.js";
import { familyContext } from "../middlewares/family.js";
import { requireRole } from "../middlewares/role.js";
import {
  createInvitation,
  acceptInvitation,
} from "../services/invitation.service.js";

// Create rides loadFamily: slug names the family, owner role gates the mint.
export const invitationRouter = Router({ mergeParams: true });

invitationRouter.post("/", requireRole("owner"), async (req, res, next) => {
  try {
    const { family, membership } = familyContext(req);
    const { email, role } = (req.body ?? {}) as {
      email?: unknown;
      role?: unknown;
    };

    if (role !== "member" && role !== "admin") {
      res.status(400).json({ message: "role must be 'member' or 'admin'" });
      return;
    }
    if (email !== undefined && email !== null && typeof email !== "string") {
      res.status(400).json({ message: "email must be a string" });
      return;
    }

    const result = await createInvitation({
      familyId: family.id,
      callerMembershipId: membership.id,
      role,
      email: typeof email === "string" ? email.trim() || null : null,
    });

    if (!result.ok) {
      if (result.reason === "insufficient-role") {
        res.status(403).json({ message: "Insufficient role" });
        return;
      }
      // already-pending: a live credential for this email already exists.
      // Minting a second would leave the first unaccountable.
      res
        .status(409)
        .json({ message: "An invitation is already pending for that email" });
      return;
    }

    res.status(201).json({ token: result.token });
  } catch (e) {
    next(e);
  }
});

// Accept stands alone — the invitee is not yet a member of any family here.
export const acceptInvitationRouter = Router();

acceptInvitationRouter.post(
  "/:token/accept",
  requireAuth,
  async (req, res, next) => {
    try {
      const { userId } = authContext(req);
      const { token } = req.params;
      if (typeof token !== "string" || token.length === 0) {
        res.status(400).json({ message: "Missing token" });
        return;
      }
      const result = await acceptInvitation(token, userId);
      if (result.ok) {
        res.status(204).end();
        return;
      }
      // Collapse on wire: not-found / expired / used / already-member all 409.
      // The same body for every refusal is the right amount of information.
      res.status(409).json({ message: "This invitation cannot be accepted" });
    } catch (e) {
      next(e);
    }
  },
);

    Notice the route no longer trusts membership.role from the request context. It passes callerMembershipId and lets the service decide — step 3 explains why.

  3. Harden the mint: one transaction, one credential

    The route guard saw the inviter's role when the request arrived. Two things can go wrong between then and the write:

    1. The role is stale. Another owner demotes the caller; the request is already in flight and mints an invite anyway. This is exactly the race transferOwnership closes, and the fix is the same: re-read the membership inside the lock.
    2. The mint runs twice. A double-clicked button, or a retried request, submits the same email twice. Two findFirst-then-create calls race, both see "no pending invite", both insert — two live credentials for one person. Lesson 10's note called the mint endpoint out for exactly this; here is the fix.
    server/src/services/invitation.service.ts (replace createInvitation) 
    import { createHash, randomBytes } from "node:crypto";
import type { Db } from "../models/db.js";
import { transact } from "../models/db.js";
import * as membershipModel from "../models/membership.model.js";
import { ROLES, type Role } from "../models/membership.model.js";

export type MintResult =
  | { ok: true; token: string }
  | {
      ok: false;
      reason: "invalid-role" | "insufficient-role" | "already-pending";
    };

const INVITE_TTL_MS = 7 * 24 * 60 * 60 * 1000;

/**
 * Mint an invite, inside one transaction behind the family lock.
 *
 * The route guard saw the inviter's role when the request arrived; another
 * owner may have demoted them since. Re-reading the membership INSIDE the lock
 * is the fix (the same shape as transferOwnership). The lock also serialises
 * mints for one family, so two simultaneous submissions -- a double-clicked
 * button, a retried request -- cannot both pass the pending check below and
 * mint two live credentials for the same person.
 */
export async function createInvitation(input: {
  familyId: string;
  callerMembershipId: string;
  role: Role;
  email?: string | null;
}): Promise<MintResult> {
  if (!ROLES.includes(input.role)) return { ok: false, reason: "invalid-role" };

  return transact(async (tx: Db) => {
    await membershipModel.lockFamily(input.familyId, tx);

    const inviter = await membershipModel.findByFamily(
      input.familyId,
      input.callerMembershipId,
      tx,
    );
    if (inviter === null || RANK[input.role] > RANK[inviter.role]) {
      return { ok: false, reason: "insufficient-role" };
    }

    // Targeted invites are one-per-email while pending. Shareable links
    // (email: null) are deliberately exempt -- minting several is legitimate.
    const email = input.email ?? null;
    if (email !== null) {
      const pending = await tx.invitation.findFirst({
        where: {
          familyId: input.familyId,
          email,
          usedAt: null,
          expiresAt: { gt: new Date() },
        },
      });
      if (pending !== null) return { ok: false, reason: "already-pending" };
    }

    const token = randomBytes(32).toString("base64url");
    await tx.invitation.create({
      data: {
        familyId: input.familyId,
        role: input.role,
        email,
        tokenHash: hashToken(token),
        expiresAt: new Date(Date.now() + INVITE_TTL_MS),
        createdBy: inviter.userId,
      },
    });
    return { ok: true, token };
  });
}

    Keep hashToken, RANK, InvitationResult and acceptInvitation from lesson 09 — only the mint changes. Three details carry the fix:

    • lockFamily is reused, not re-invented. It already exists in membership.model.ts, because "serialise every mutation of one family" is the same need roles had. One lock, one family, every writer.
    • The membership is re-read with the existing findByFamily(familyId, membershipId, tx) — the same model call transferOwnership uses. No new model function is needed.
    • createdBy now comes from inviter.userId, read inside the lock — not from the route's copy. The identity is re-proved, not inherited.

    The runnable proof

    Concurrency logic needs more than a typecheck. Mirror check:ownership: two Promise.all mints for one email, and a demotion between the guard and the read.

    server/src/scripts/checkMint.ts (new) 
    import "dotenv/config";
import { randomUUID } from "node:crypto";
import { prisma } from "../config/database.js";
import { createInvitation } from "../services/invitation.service.js";

// Two submissions, one email, no scheduler involved: Promise.all fires both
// createInvitation calls into the same family. The lock serialises them, so the
// second must see the first's row and refuse. Remove lockFamily and this fails.
async function main(): Promise<void> {
  const slug = `probe-${randomUUID().slice(0, 8)}`;
  const family = await prisma.family.create({
    data: { slug, name: "Mint probe" },
  });
  const email = `${slug}@probe.invalid`;

  try {
    const owner = await prisma.user.create({
      data: { email: `${slug}-owner@probe.invalid`, passwordHash: "x" },
    });
    const ownerMembership = await prisma.familyMember.create({
      data: { userId: owner.id, familyId: family.id, role: "owner" },
    });

    const mint = (): Promise<{ ok: boolean; reason?: string }> =>
      createInvitation({
        familyId: family.id,
        callerMembershipId: ownerMembership.id,
        role: "member",
        email,
      });

    const [a, b] = await Promise.all([mint(), mint()]);
    const succeeded = [a, b].filter((r) => r.ok).length;
    const rows = await prisma.invitation.count({
      where: { familyId: family.id, email },
    });

    console.log(`concurrent mints succeeded: ${succeeded}`);
    console.log(`invitation rows written:    ${rows}`);

    if (succeeded !== 1 || rows !== 1) {
      throw new Error(
        `DUPLICATE MINT: ${succeeded} succeeded, ${rows} row(s) written, expected 1/1`,
      );
    }

    // Demotion race: the guard saw "owner"; by the time the service reads,
    // the inviter is a member. Re-reading inside the lock is what refuses this.
    await prisma.familyMember.update({
      where: { id: ownerMembership.id },
      data: { role: "member" },
    });
    const demoted = await createInvitation({
      familyId: family.id,
      callerMembershipId: ownerMembership.id,
      role: "admin",
      email: `${slug}-late@probe.invalid`,
    });
    console.log(`demoted inviter refused:    ${!demoted.ok}`);

    if (demoted.ok) {
      throw new Error("STALE ROLE TRUSTED: demoted member minted an admin invite");
    }

    console.log("\nsingle-credential invariant held under forced concurrency");
  } finally {
    await prisma.family.delete({ where: { id: family.id } });
    await prisma.user.deleteMany({ where: { email: { startsWith: slug } } });
    await prisma.$disconnect();
  }
}

main().catch((error: unknown) => {
  console.error(error);
  process.exitCode = 1;
});

    import { useParams } from "react-router-dom";
import { useEffect, useState } from "react";

export default function AcceptPage() {
  const { token } = useParams<{ token: string }>();
  const [status, setStatus] = useState<"idle" | "ok" | "err">("idle");

  useEffect(() => {
    if (!token) return;
    fetch(`/api/invitations/${encodeURIComponent(token)}/accept`, {
      method: "POST",
      credentials: "include",
    }).then((r) => setStatus(r.status === 204 ? "ok" : "err"));
  }, [token]);

  if (status === "ok") return <p>You're in — go to the family.</p>;
  if (status === "err") return <p>This link doesn't work.</p>;
  return <p>Accepting…</p>;
}

Defend it

Why re-read the role inside the transaction?

The middleware is a photograph; the database is the world. Between the photograph and the write, an owner can demote the caller. Trusting the snapshot means a demoted admin mints an invite with authority they no longer have. The lock plus the re-read is the same defense as transferOwnership — and it costs one extra query inside a transaction you were opening anyway.

Why does the lock also stop duplicate invitations?

Two findFirst-then-create calls race the same way two owner-counts race. Both read "no pending invite", both insert. The FOR UPDATE lock makes the second wait for the first to commit, then re-read a world where the row exists, and refuse. Measured: with the lock, every run holds at one credential; with lockFamily commented out, 5/5 runs fail — each writes two rows. The lock is the whole mechanism.

Why exempt shareable links from the duplicate check?

A shareable invite (email: null) is a link you may legitimately hand out more than once — one per group, one replacement for a leaked URL. "One pending invite per email" is only meaningful when there is an email. The targeted case is where a duplicate is an accounting problem: two live credentials for one person, one of which nobody will remember minting.

Why 409, not 201-with-the-existing-token?

Because the server cannot re-issue the token — it only ever stored the hash (Reference 09 §1). Re-returning the existing invite is impossible by design, so the honest answer is "one already exists". The client's next move is to list pending invites (lesson 12) or revoke and re-mint.

Why split the router into two mount points?

loadFamily is a 404-by-design gate: it answers the same body whether the family doesn't exist or the caller isn't a member. That gate requires membership, and an invitee by definition is not yet a member. Mounting accept under loadFamily returns 404 for every invite URL before the token is even checked.

Break it on purpose

  1. Unbalance one JSX tag. Change </BrowserRouter> back to <BrowserRouter> and run npm run typecheck. Predict the error before you run it. You should see TS17008 for BrowserRouter, TS17002, and TS1005 — four errors from one missing slash. This is the client half of typecheck earning its keep.
  2. Drop the lock. Comment out lockFamily in createInvitation and run npm run check:mint a few times. 2 succeeded, 2 row(s) written — the duplicate invariant holds only because of the lock.
  3. Trust the route's role again. Pass membership.role and remove the re-read. Demote an owner in one tab, mint in another whose request was already in flight. The stale role wins; the demoted caller mints authority they no longer hold.
  4. Mount the accept route under loadFamily. Every invite URL collapses to 404 — the invitee is not yet a member, so the gate rejects them before the token is checked.
  5. Skip the package install. Delete react-router-dom from node_modules and re-run npm run dev. Vite prints a module resolution error pointing at useParams — what lesson 10's reader would have seen.
