Lesson 15c · Week 5 · ≈ one session · one new thing

Revoke, and resend the only way it can work

The raw token was never stored — storing it would be a plaintext credential at rest — so "resend the link" is impossible. Resend must mean something else: mint a brand-new credential and kill the old one, in one transaction. Today builds that, plus the plain revoke it reuses.

Mission: ship KinLink Requires: Lesson 15b References: 09 · 08 Practice: Lesson 15f
The win

POST /api/families/:slug/invitations/:id/revoke ends a pending invite, and …/:id/resend returns a fresh token while the old one stops working — both owner-only, both inside the family lock. npm run check:resend proves the old token is dead and the new one is live.

Warm-up: why can't resend show the link again?

Answer before reading on. Then state the consequence in one sentence: what must resend actually do instead? (Reference 09 §1 if you are stuck.)

  2. Model: find one invite, and end it

    Add two functions beside the existing ones. Both take the familyId in the WHERE clause, so an id from a URL can never reach a row belonging to another family.

    server/src/models/invitation.model.ts (additions) 
    export async function findById(
  familyId: string,
  invitationId: string,
  database: Db = prisma,
): Promise<Invitation | null> {
  return database.invitation.findFirst({
    where: { id: invitationId, familyId },
  });
}

/** End a pending invite. Returns rows changed: 0 means it was not pending. */
export async function revoke(
  familyId: string,
  invitationId: string,
  database: Db = prisma,
): Promise<number> {
  const result = await database.invitation.updateMany({
    where: { id: invitationId, familyId, usedAt: null, revokedAt: null },
    data: { revokedAt: new Date() },
  });
  return result.count;
}

    Note the shape: revocation is a conditional write, not find-then-set. The usedAt: null, revokedAt: null guard is what makes count !== 1 mean "someone else already ended this" — the same compare-and-set idea as the accept path.

  3. Service: two transitions, one lock

    Both operations re-read the inviter's membership inside the lock. The route's requireRole("owner") ran when the request arrived; an owner demoted since then must not act.

    server/src/services/invitation.service.ts (additions) 
    import * as membershipModel from "../models/membership.model.js";

export type RevokeResult =
  | { ok: true }
  | { ok: false; reason: "not-owner" | "not-pending" };

export type ResendResult =
  | { ok: true; token: string }
  | { ok: false; reason: "not-owner" | "not-pending" | "insufficient-role" };

export interface InviteActionWindow {
  afterLookup?: () => Promise<void>;
}

export async function revokeInvitation(input: {
  familyId: string;
  inviterMembershipId: string;
  invitationId: string;
}): Promise<RevokeResult> {
  return transact(async (tx) => {
    await membershipModel.lockFamily(input.familyId, tx);

    const inviter = await membershipModel.findByFamily(
      input.familyId,
      input.inviterMembershipId,
      tx,
    );
    if (!inviter || inviter.role !== "owner") {
      return { ok: false, reason: "not-owner" };
    }

    const revoked = await invitationModel.revoke(
      input.familyId,
      input.invitationId,
      tx,
    );
    if (revoked !== 1) return { ok: false, reason: "not-pending" };
    return { ok: true };
  });
}

export async function resendInvitation(
  input: {
    familyId: string;
    inviterMembershipId: string;
    invitationId: string;
  },
  window: InviteActionWindow = {},
): Promise<ResendResult> {
  return transact(async (tx) => {
    await membershipModel.lockFamily(input.familyId, tx);

    const inviter = await membershipModel.findByFamily(
      input.familyId,
      input.inviterMembershipId,
      tx,
    );
    if (!inviter || inviter.role !== "owner") {
      return { ok: false, reason: "not-owner" };
    }

    const old = await invitationModel.findById(
      input.familyId,
      input.invitationId,
      tx,
    );
    if (
      !old ||
      old.usedAt !== null ||
      old.revokedAt !== null ||
      old.expiresAt <= new Date()
    ) {
      return { ok: false, reason: "not-pending" };
    }
    // Defense in depth: never reissue a role above the inviter's rank.
    if (RANK[old.role] > RANK[inviter.role]) {
      return { ok: false, reason: "insufficient-role" };
    }

    await window.afterLookup?.();

    const token = randomBytes(32).toString("base64url");
    await invitationModel.revoke(input.familyId, input.invitationId, tx);
    await invitationModel.createInvitation(
      {
        familyId: input.familyId,
        role: old.role,
        email: old.email,
        tokenHash: hashToken(token),
        expiresAt: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000),
        createdBy: inviter.userId,
      },
      tx,
    );
    return { ok: true, token };
  });
}
    Why one transaction, and why the lock

    "Kill the old, mint the new" is one fact. Two concurrent resends would otherwise each mint and each revoke — leaving two live credentials and an emailed link that is already dead. That is lesson 11's duplicate-mint race in a new costume, so the same answer applies: lockFamily first, then read, decide, write.

  4. Routes: two new owner-only actions

    Mount both under the family-scoped router, beside the existing list route, so the slug still names the family and loadFamily still proves access.

    server/src/routes/invitation.routes.ts (additions) 
    invitationRouter.post(
  "/:invitationId/revoke",
  requireRole("owner"),
  async (req, res, next) => {
    try {
      const { family, membership } = familyContext(req);
      const result = await revokeInvitation({
        familyId: family.id,
        inviterMembershipId: membership.id,
        invitationId: req.params.invitationId,
      });
      if (!result.ok) {
        const status = result.reason === "not-owner" ? 403 : 409;
        const message =
          result.reason === "not-owner"
            ? "Insufficient role"
            : "That invitation is no longer pending";
        res.status(status).json({ message });
        return;
      }
      res.status(204).end();
    } catch (e) {
      next(e);
    }
  },
);

invitationRouter.post(
  "/:invitationId/resend",
  requireRole("owner"),
  async (req, res, next) => {
    try {
      const { family, membership } = familyContext(req);
      const result = await resendInvitation({
        familyId: family.id,
        inviterMembershipId: membership.id,
        invitationId: req.params.invitationId,
      });
      if (!result.ok) {
        const status = result.reason === "not-pending" ? 409 : 403;
        const message =
          result.reason === "not-pending"
            ? "That invitation is no longer pending"
            : "Insufficient role";
        res.status(status).json({ message });
        return;
      }
      // Informal body: the client lesson (15e) moves this under { data: … }.
      res.status(201).json({ token: result.token });
    } catch (e) {
      next(e);
    }
  },
);

    409 for "not pending" is the honest code: retrying after the invite is re-minted (or once the clock passes) will succeed. It is not a permission failure, so it is not 403.

  5. Proof: the old token dies, the new one lives

    Add server/src/scripts/checkResend.ts and a check:resend script. It mints an invite, resends it, and asserts the consequence the whole design rests on.

    server/src/scripts/checkResend.ts (new) 
    import "dotenv/config";
import { randomUUID } from "node:crypto";
import { prisma } from "../config/database.js";
import {
  createInvitation,
  resendInvitation,
  acceptInvitation,
} from "../services/invitation.service.js";

async function main(): Promise<void> {
  const slug = `resend-${randomUUID().slice(0, 8)}`;
  const family = await prisma.family.create({
    data: { slug, name: "Resend probe" },
  });
  const ownerEmail = `${slug}-owner@probe.invalid`;
  const inviteeEmail = `${slug}-invitee@probe.invalid`;
  const owner = await prisma.user.create({
    data: { email: ownerEmail, passwordHash: "probe" },
  });
  const invitee = await prisma.user.create({
    data: { email: inviteeEmail, passwordHash: "probe" },
  });

  try {
    const membership = await prisma.familyMember.create({
      data: { userId: owner.id, familyId: family.id, role: "owner" },
    });

    const first = await createInvitation({
      familyId: family.id,
      inviterMembershipId: membership.id,
      role: "member",
      email: "target@probe.invalid",
    });
    if (!first.ok) throw new Error("SETUP: first mint failed");

    const pendingBefore = await prisma.invitation.findFirst({
      where: { familyId: family.id, revokedAt: null, usedAt: null },
    });
    if (!pendingBefore) throw new Error("SETUP: no pending row to resend");

    const resent = await resendInvitation({
      familyId: family.id,
      inviterMembershipId: membership.id,
      invitationId: pendingBefore.id,
    });
    if (!resent.ok) throw new Error(`RESEND REFUSED: ${resent.reason}`);

    const oldRow = await prisma.invitation.findUnique({
      where: { id: pendingBefore.id },
    });
    const pending = await prisma.invitation.count({
      where: {
        familyId: family.id,
        usedAt: null,
        revokedAt: null,
        expiresAt: { gt: new Date() },
      },
    });

    const oldAccept = await acceptInvitation(first.token, invitee.id);
    const newAccept = await acceptInvitation(resent.token, invitee.id);

    console.log(`old token revoked: ${oldRow?.revokedAt !== null}`);
    console.log(`pending row count: ${pending}`);
    console.log(`old token accepted: ${oldAccept.ok}`);
    console.log(`new token accepted: ${newAccept.ok}`);

    if (oldRow?.revokedAt === null) {
      throw new Error("OLD CREDENTIAL ALIVE: resend did not revoke the original");
    }
    if (pending !== 1) {
      throw new Error(`EXPECTED exactly 1 pending row, got ${pending}`);
    }
    if (oldAccept.ok) {
      throw new Error("OLD TOKEN STILL WORKS after resend");
    }
    if (!newAccept.ok) {
      throw new Error("NEW TOKEN REJECTED after resend");
    }

    console.log("\nresend revoked the old credential and issued a live one");
  } finally {
    await prisma.family.delete({ where: { id: family.id } });
    await prisma.user.deleteMany({
      where: { email: { in: [ownerEmail, inviteeEmail] } },
    });
    await prisma.$disconnect();
  }
}

main().catch((error: unknown) => {
  console.error(error);
  process.exitCode = 1;
});

A retry is not safe — say it out loud

A retried resend mints a second credential and revokes the first, so the link the user was emailed is dead. This is lesson 08's non-idempotence again: either the UI never auto-retries, or it needs an idempotency key (week 8's asynchrony thread). Do not quietly retry this endpoint, and do not add a client retry to it later without reading this.
