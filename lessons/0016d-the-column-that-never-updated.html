Lesson 16d · Week 4 · ≈ one session · one new thing

The column that never updated

KinLink has carried a defect since lesson 06: people.updated_at is set once at creation and never again. It is a column named "updated" that does not update. Today an edit screen needs it to tell the truth — so today we repair it, then build the edit.

Mission: ship KinLink Requires: Lesson 16c References: 03 · 11 · 13 Practice: Lesson 16f
The win

updated_at changes on every write, and PATCH /api/families/:slug/people/:personId renames a person scoped to the caller's family. On the screen, a row turns into a form, saves, and the list follows — the same invalidate rule as the create, reused.

Warm-up: retrieve before rereading

Five minutes, from memory. The model's update used updateMany, not update. Why? And what does its count let the controller decide? Say both, then check Reference 13.

Build it

  1. Verify the baseline — and see the defect plainly

    npm run typecheck                       # exit 0
grep -n "updatedAt" prisma/schema.prisma
#   Person.updatedAt   DateTime @default(now()) @map("updated_at")
#   User.updatedAt     DateTime @updatedAt      @map("updated_at")

    Two models, two different declarations, side by side. The bug is that the Person line says @default(now()) — the value is written once, at insert, and never touched again. @updatedAt is the field that Prisma itself refreshes on every write.

  2. Repair first, on its own commit

    This is a repair of shipped code, so it earns an isolated commit ahead of the feature that depends on it — the sequencing rule you set after the whoami fix. Do this step, commit it, and only then start the edit path.

    prisma/schema.prisma (the Person model) 
      createdAt   DateTime  @default(now()) @map("created_at")
  updatedAt   DateTime  @updatedAt @map("updated_at")

    Then let Prisma plan and apply the migration:

    npx --no-install prisma migrate dev --name fix_person_updated_at

    --no-install pins you to the project's own prisma (7.10.0), never a freshly downloaded major. This migration is one statement, and it is worth reading before you accept it:

    prisma/migrations/…_fix_person_updated_at/migration.sql 
    -- AlterTable
ALTER TABLE `people` ALTER COLUMN `updated_at` DROP DEFAULT;

    One line, and metadata-only: dropping a column default is an in-place catalogue change, not a table rebuild. (Making a column NOT NULL is the expensive one — that rebuilds and fails on any remaining NULL, which is why lesson 12's column went in with an expand-and-contract.)

    Is it safe to drop the default?

    Yes, and the proof is in your own schema. Remove the default and the column has none — so every insert must supply a value. Prisma's @updatedAt does: the client stamps it on create and update. The User model is the live demonstration — users.updated_at has been @updatedAt with no default since lesson 04, and registration has worked the whole time.

    Commit the repair on its own now, with a message about the column, not the feature.

  3. The transport learns PATCH

    client/src/lib/api.ts (additions) 
    export function updatePerson(
  slug: string,
  personId: string,
  patch: UpdatePersonRequest,
): Promise<PersonResource> {
  return request<PersonResource>(
    `/api/families/${encodeURIComponent(slug)}/people/${encodeURIComponent(personId)}`,
    { method: "PATCH", body: patch },
  );
}

    Add UpdatePersonRequest to the type import.

  4. A row that becomes a form

    Replace the plain <li> in the list with a PersonRow that can toggle into an edit form. It reuses the exact invalidate pattern from the create — same key, same rule.

    client/src/PeoplePage.tsx (the row) 
    import type { Gender, PersonResource } from "./contracts";
import { ApiError, createPerson, getPeople, updatePerson } from "./lib/api";

function PersonRow({ slug, person }: { slug: string; person: PersonResource }) {
  const queryClient = useQueryClient();
  const [editing, setEditing] = useState(false);
  const [name, setName] = useState(person.name);

  const invalidate = () =>
    queryClient.invalidateQueries({ queryKey: peopleKey(slug) });

  const rename = useMutation({
    mutationFn: (next: string) => updatePerson(slug, person.id, { name: next }),
    onSuccess: () => {
      setEditing(false);
      void invalidate();
    },
  });

  if (editing) {
    return (
      <li>
        <form
          onSubmit={(event) => {
            event.preventDefault();
            rename.mutate(name.trim());
          }}
        >
          <input
            value={name}
            onChange={(event) => setName(event.target.value)}
          />{" "}
          <button type="submit" disabled={rename.isPending}>
            Save
          </button>{" "}
          <button type="button" onClick={() => setEditing(false)}>
            Cancel
          </button>
        </form>
      </li>
    );
  }

  return (
    <li>
      {person.name} {person.living ? "· living" : "· deceased"}{" "}
      <button
        type="button"
        onClick={() => {
          setName(person.name);
          setEditing(true);
        }}
      >
        Edit
      </button>
    </li>
  );
}

    And use it in the list:

    client/src/PeoplePage.tsx (PeopleList body) 
              {query.data.map((person) => (
            <PersonRow key={person.id} slug={slug} person={person} />
          ))}

Verify after

npm run typecheck        # exit 0
npm run check:people     # exit 0 -- the scoped write is unchanged
npm run build:client     # exit 0

Then prove the column actually moves, because that is the whole point of the first commit. Edit a person in the browser, and read the row back: 

npm run db:studio
# open people, edit a name in the UI, watch updated_at change
# (it must differ from created_at after the edit; before this lesson it never did)
Break it on purpose — predict first

Revert the schema line to @default(now()), generate, and edit a person again. Predict what updated_at will show, then look: it is frozen at creation time. The row changed, the timestamp did not, and nothing errored — the worst shape a defect can take. Put @updatedAt back. Then ask the sharper question: why did no test catch this? Because no check compares two columns; check:people proves scoping, not freshness. Name the gap rather than pretending it is covered.

Decisions carried into the next sittings

  • The edit form renames; it does not edit gender or dates. The endpoint accepts the full UpdatePersonRequest — the service and the validator are general — but the screen only offers a name change. Build the richer form when a screen needs it (the profile page), not because the API could. And when you widen PersonResource, do it in the view first and let the compiler find the call sites.
  • One repair, one commit, and it came first. This sitting has two commits and that is correct: a defect repair and the feature that depends on it are different changes with different reasons to exist. The general rule still stands — do not smuggle an unrelated fix into a feature commit.
  • Optimistic editing still declined. Cancelling and re-saving a rename could use an optimistic update; on localhost it would be invisible either way. The trigger from 16c has not fired.
