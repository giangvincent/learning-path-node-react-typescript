Lesson 16e · Week 4 · ≈ one session · one new thing

The row that leaves

The last of the four verbs, and the only one that answers with no body at all. It also raises the question CRUD quietly avoids: when a person is removed from a family tree, what happens to everything that pointed at them?

Mission: ship KinLink Requires: Lesson 16d References: 03 · 13 Practice: Lesson 16f
The win

A person can be removed from the family, and the list agrees. DELETE /api/families/:slug/people/:personId answers 204 No Content on success and 404 for a person who is not in this family — the same scoped-WHERE rule as the update, in a second verb.

Warm-up: retrieve before rereading

Five minutes, from memory. The create and the update both ended by calling invalidateQueries. What exactly does that call do to the cache, and why is it the same call for a write of either kind? Answer before you look at Reference 13.

Build it

  1. Verify the baseline

    npm run typecheck        # exit 0
npm run check:people     # exit 0 -- the scoped delete already exists in the model
grep -n "delete" client/src/lib/api.ts   # no match: the client cannot delete yet

    Note what is already there. personModel.remove and removePerson were written in 16a, and the route was mounted then too — check:people already asserts a cross-family delete is refused. This lesson is the client half plus the button; the server was finished four sittings ago.

  2. The transport learns DELETE and expects no body

    request<T> already returns undefined early for a 204, before it tries to parse JSON. So the delete call types its result as void and reads as an action, not a fetch:

    client/src/lib/api.ts (additions) 
    export function deletePerson(slug: string, personId: string): Promise<void> {
  return request<void>(
    `/api/families/${encodeURIComponent(slug)}/people/${encodeURIComponent(personId)}`,
    { method: "DELETE" },
  );
}
    Why 204 and not the deleted object

    A delete that returns the removed resource pretends the caller still has something to act on. 204 No Content says the true thing: the operation succeeded and there is nothing left to say. It is also why the transport must special-case it — calling response.json() on an empty body throws, and that is exactly the bug this guard prevents.

  3. A button, a confirmation, an invalidation

    client/src/PeoplePage.tsx (PersonRow additions) 
    import { ApiError, createPerson, deletePerson, getPeople, updatePerson } from "./lib/api";
// ...inside PersonRow, beside the rename mutation:

  const remove = useMutation({
    mutationFn: () => deletePerson(slug, person.id),
    onSuccess: () => void invalidate(),
  });
// ...and in the non-editing return, after the Edit button:

      <button
        type="button"
        disabled={remove.isPending}
        onClick={() => {
          if (window.confirm(`Delete ${person.name}?`)) remove.mutate();
        }}
      >
        Delete
      </button>

    The confirmation is not decoration. This is the first destructive action in the product and there is no undo — so the cheapest correct thing is to ask. It is also a boundary: window.confirm blocks, which is fine for a dev-stage UI and is the kind of thing a real design replaces with an inline "Delete? / Cancel".

Verify after

npm run typecheck        # exit 0
npm run build:client     # exit 0

Then walk it by hand, and watch the list, not just the status code: 

# with a valid cookie and a real <id>
DELETE /api/families/<slug>/people/<id>            -> 204
DELETE /api/families/<slug>/people/<id>  (again)   -> 404 {"message":"Person not found"}

In the browser: add a person, delete it, and confirm the row disappears without a reload. Then delete the same person from a second tab and watch the first tab not move until it refetches — the same cross-client blind spot you measured in 16c.

Break it on purpose — predict first

Remove the onSuccess invalidation and delete a person. Predict the screen, then look: the row stays, even though the server answered 204 and the row is gone. Refresh and it vanishes. A successful write with a stale read is the same failure you produced in 16c — which is the point: the invalidation is the feature, and all three verbs depend on the one key. Restore it.

Decisions carried into the next sittings

  • This is a hard delete, and that is a decision to revisit. When relationships arrive, a deleted person must take their edges with them or the graph breaks. And a genealogy product may not want a remembered relative to be gone — a soft delete (deleted_at) keeps the row and hides it, at the cost of every read growing a WHERE. Do not choose now; decide when the first relationship edge exists and the cost is concrete.
  • Only members may delete, same as create and edit. loadFamily is the authorisation. If you later decide deletion is privileged, the change is one requireRole("admin") on the route plus the caller's role on the screen — not a redesign. Decide once, keep client and server in the same commit.
  • The client still shows no server prose. A refused delete (a future rule, a stale id) currently surfaces as "nothing happened". The fix is the same one 16c deferred: let ApiError carry the response body. Do it once, for all three verbs, when a refusal a user can act on actually exists.

Primary sources

Read these against the code

RFC 9110 §15.3.5 — 204 No Content for why the success response carries no body (and what a client must do with it) · RFC 9110 §9.3.5 — DELETE for idempotence, which is exactly why a second delete is a 404 and not an error to fear · TanStack Query — Query Invalidation for the call that makes the list agree.

If the row does not disappear, or a 204 logs a JSON parse error, bring me the console — those are the two failure modes this lesson is built around. Ask about soft deletes, idempotence, or what should happen to a person's relationships — anything unclear is worth the minute.
