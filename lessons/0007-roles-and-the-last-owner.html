Lesson 07 · Week 4 · about two hours

Roles, and the owner who cannot leave

The role column has existed since lesson 06 and nothing has ever read it. Today it becomes load-bearing: a rank instead of a list, the project's first honest 403, and an invariant that has to survive two owners demoting each other at the same instant.

Mission: ship KinLink Reference: Membership lifecycle Requires: Lesson 06
The win

A plain member asking to change a role gets 403; the last owner trying to leave gets 409, and the message tells them to transfer ownership first. Behind that, a family can never reach zero owners — proven by a script that has two owners demote each other concurrently and asserts exactly one survives. Your first real use of SELECT … FOR UPDATE, and your first codebase-level invariant.

Why a rank, and not a list

The tempting shape is a comparison at each call site: membership.role === "owner". It works, and it quietly rots. The day someone adds a role between admin and owner, every one of those comparisons silently means something new — too narrow in some places, too wide in others, and nothing fails to tell you.

A rank makes "or above" a comparison instead of an enumeration: 

const RANK = { member: 1, admin: 2, owner: 3 } as const satisfies Record<Role, number>;
satisfies Record<Role, number> is doing real work

Because the map is typed as total over Role, adding a role to schema.prisma and regenerating the client makes this line a compile error until you decide where the new role sits. That is the whole point: the decision cannot be skipped, and it cannot be skipped silently. A partial map would let it slide.

Build it

  1. The first honest 403

    server/src/middlewares/role.ts (new) 
    import type { RequestHandler } from "express";
import type { ApiErrorBody } from "../contracts.js";
import type { Role } from "../models/membership.model.js";
import { familyContext } from "./family.js";

// A rank, not a list of acceptable strings. "admin" means admin or above, so
// adding a role later cannot silently narrow or widen an existing check. Typed as
// a total map, so a new role is a compile error until it is ranked.
const RANK = { member: 1, admin: 2, owner: 3 } as const satisfies Record<Role, number>;

/**
 * 403, not 404. The caller is inside the family -- loadFamily proved it -- so its
 * existence is not a secret from them. "You may not do this" is the honest answer,
 * and it is actionable in a way that another 404 would not be.
 */
export const requireRole = (minimum: Role): RequestHandler = (req, res, next) => {
  const { membership } = familyContext(req);

  if (RANK[membership.role] < RANK[minimum]) {
    const body: ApiErrorBody = { message: "Insufficient role" };
    res.status(403).json(body);
    return;
  }

  next();
};

    Three things worth noticing. It takes no database query — loadFamily already fetched the membership, role included, which is the payoff of resolving once at the boundary. It calls familyContext, so it inherits the tripwire and fails loudly if someone mounts it without loadFamily. And it returns a function, so a route can say requireRole("owner") and read like the rule it enforces.

  2. The Db type lesson 06 predicted

    Read the comment you left in user.model.ts:

    "…because it is currently the only operation that needs a Prisma transaction handle. When a second one appears, extract a Db type and thread it through the model functions instead of growing this pattern by hand."

    A second one has appeared — an owner leaving needs to lock, count, and delete as one unit. Here is the extraction:

    server/src/models/db.ts (new) 
    import { prisma } from "../config/database.js";
import type { PrismaClient } from "../../generated/prisma/client.js";

/**
 * A Prisma client OR a transaction handle.
 *
 * Threaded through the model functions so a service can compose several writes in
 * one transaction without the model layer knowing who is coordinating. A
 * transaction handle is a PrismaClient without the connection/transaction
 * lifecycle methods, so this Omit is the shape both satisfy.
 */
export type Db = Omit<
  PrismaClient,
  "$connect" | "$disconnect" | "$on" | "$transaction" | "$extends" | "$use"
>;

/**
 * Run several model calls as one unit.
 *
 * This lives in the model layer, not the services, so a service can describe
 * *what* must happen atomically without ever importing Prisma. Model layer owns
 * how we talk to the database; services own what the business requires.
 */
export function transact<T>(work: (tx: Db) => Promise<T>): Promise<T> {
  return prisma.$transaction(work);
}

  3. Model functions that can be composed, and one that locks

    server/src/models/membership.model.ts (additions) 
    import { prisma } from "../config/database.js";
import type { Db } from "./db.js";

// Runtime list of the enum, so validation never hand-writes the three names twice.
export const ROLES = ["member", "admin", "owner"] as const satisfies readonly Role[];

/**
 * Find a membership *within a family*. The familyId is in the WHERE clause, so a
 * membership id taken from a URL can never select a row belonging to another family
 * on its own -- the same shape as the lesson-06 guard, one level down.
 */
export async function findByFamily(
  familyId: string,
  membershipId: string,
  database: Db = prisma,
): Promise<FamilyMember | null> {
  return database.familyMember.findFirst({
    where: { id: membershipId, familyId },
  });
}

export async function countOwners(
  familyId: string,
  database: Db = prisma,
): Promise<number> {
  return database.familyMember.count({ where: { familyId, role: "owner" } });
}

/**
 * Serialise ownership changes for one family.
 *
 * MySQL's manual is explicit about this shape of problem: "If you query data and
 * then insert or update related data within the same transaction, the regular
 * SELECT statement does not give enough protection." Counting owners and then
 * writing is a lost update waiting to happen -- two transactions both read
 * "2 owners" and both write. FOR UPDATE takes an exclusive row lock, so the second
 * waits, then re-counts a world where only one owner is left, and refuses.
 *
 * Locking reads require autocommit to be off, which an interactive transaction
 * already provides.
 */
export async function lockFamily(
  familyId: string,
  database: Db = prisma,
): Promise<void> {
  await database.$queryRaw`SELECT id FROM families WHERE id = ${familyId} FOR UPDATE`;
}

export async function updateRole(
  membershipId: string,
  role: Role,
  database: Db = prisma,
): Promise<void> {
  await database.familyMember.update({ where: { id: membershipId }, data: { role } });
}

export async function deleteById(
  membershipId: string,
  database: Db = prisma,
): Promise<void> {
  await database.familyMember.delete({ where: { id: membershipId } });
}

  4. The invariant, checked and written as one unit

    server/src/services/membership.service.ts (additions) 
    import { transact } from "../models/db.js";

export type RoleChange =
  | { ok: true }
  | { ok: false; reason: "not-found" | "last-owner" };

export type Leave = { ok: true } | { ok: false; reason: "last-owner" };

/**
 * Change a member's role.
 *
 * "A family must keep at least one owner" is policy about a transition, so it lives
 * in the service -- not the middleware (HTTP), not the model (facts), and not a
 * database constraint (MySQL cannot express "at least one row like this"). It is
 * checked and written inside one transaction, behind a family-level lock.
 */
export async function changeRole(input: {
  familyId: string;
  membershipId: string;
  nextRole: Role;
}): Promise<RoleChange> {
  return transact(async (tx) => {
    await membershipModel.lockFamily(input.familyId, tx);

    const target = await membershipModel.findByFamily(
      input.familyId,
      input.membershipId,
      tx,
    );
    if (target === null) return { ok: false, reason: "not-found" };

    if (target.role === "owner" && input.nextRole !== "owner") {
      const owners = await membershipModel.countOwners(input.familyId, tx);
      if (owners <= 1) return { ok: false, reason: "last-owner" };
    }

    await membershipModel.updateRole(input.membershipId, input.nextRole, tx);
    return { ok: true };
  });
}

/**
 * A member leaves. The last owner may not -- the family would lose its only key.
 *
 * Idempotent on purpose: if the membership is already gone, the caller's intent
 * ("I am not in this family") is satisfied, so this is a success, not a 404.
 */
export async function leaveFamily(input: {
  familyId: string;
  membershipId: string;
}): Promise<Leave> {
  return transact(async (tx) => {
    await membershipModel.lockFamily(input.familyId, tx);

    const membership = await membershipModel.findByFamily(
      input.familyId,
      input.membershipId,
      tx,
    );
    if (membership === null) return { ok: true };

    if (membership.role === "owner") {
      const owners = await membershipModel.countOwners(input.familyId, tx);
      if (owners <= 1) return { ok: false, reason: "last-owner" };
    }

    await membershipModel.deleteById(input.membershipId, tx);
    return { ok: true };
  });
}

    Note that leaveFamily re-reads the membership inside the transaction rather than trusting the role the middleware saw. The request may have been in flight while another owner was already demoting them. Inside the lock, the truth is the truth.

  5. Two doors, two different codes

    server/src/controllers/family.controller.ts (new) 
    import type { NextFunction, Request, Response } from "express";
import type { ApiErrorBody } from "../contracts.js";
import { ROLES, type Role } from "../models/membership.model.js";
import { familyContext } from "../middlewares/family.js";
import { changeRole, leaveFamily } from "../services/membership.service.js";

function isRole(value: unknown): value is Role {
  return typeof value === "string" && (ROLES as readonly string[]).includes(value);
}

export async function patchMemberRole(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const { family } = familyContext(req);
    const { membershipId } = req.params;
    // Express 5: req.body is undefined when nothing parsed it, so read defensively.
    const nextRole = (req.body as { role?: unknown } | undefined)?.role;

    if (typeof membershipId !== "string" || !isRole(nextRole)) {
      const body: ApiErrorBody = { message: "role must be owner, admin or member" };
      res.status(400).json(body);
      return;
    }

    const result = await changeRole({
      familyId: family.id,
      membershipId,
      nextRole,
    });

    if (!result.ok) {
      // "no such member in this family" -> 404; "that would orphan the family" -> 409.
      const body: ApiErrorBody =
        result.reason === "not-found"
          ? { message: "Member not found" }
          : { message: "A family must keep at least one owner" };
      res.status(result.reason === "not-found" ? 404 : 409).json(body);
      return;
    }

    res.status(204).end();
  } catch (error) {
    next(error);
  }
}

export async function leave(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const { family, membership } = familyContext(req);

    const result = await leaveFamily({
      familyId: family.id,
      membershipId: membership.id,
    });

    if (!result.ok) {
      const body: ApiErrorBody = { message: "A family must keep at least one owner" };
      res.status(409).json(body);
      return;
    }

    res.status(204).end();
  } catch (error) {
    next(error);
  }
}
    server/src/routes/family.routes.ts 
    import { Router } from "express";
import { leave, patchMemberRole } from "../controllers/family.controller.js";
import { getFamilyPeople } from "../controllers/people.controller.js";
import { requireRole } from "../middlewares/role.js";

// loadFamily already ran at the mount, so requireRole needs no query of its own.
export const familyRouter = Router();

familyRouter.get("/people", getFamilyPeople);

// owner-only: changing who may do what is the most dangerous operation here.
familyRouter.patch("/members/:membershipId", requireRole("owner"), patchMemberRole);

// any member may leave; the refusal case is 409, not 403.
familyRouter.post("/leave", leave);

    Look at the difference between the two refusals, because it is the whole point of this step. A member who is not an owner gets 403 — "you may never do this". The last owner who tries to leave gets 409 — "you are allowed, but not in this state; promote someone else and try again". RFC 9110 calls 409 the code for a request that "could not be completed due to a conflict with the current state of the target resource" (§15.5.10).

  6. The check that proves the lock is not decoration

    This is the interesting part, and it is testable. Two owners demote themselves at the same instant. Without the lock both transactions read count = 2 and both write, leaving a family with zero owners — a state that cannot be repaired through the API at all.

    server/src/scripts/checkOwnership.ts (new) 
    import "dotenv/config";
import { randomUUID } from "node:crypto";
import { prisma } from "../config/database.js";
import { changeRole } from "../services/membership.service.js";

// Two owners demote themselves simultaneously. Exactly one must be refused, and
// exactly one owner must remain -- the invariant that no route can repair if broken.
async function main(): Promise<void> {
  const slug = `probe-${randomUUID().slice(0, 8)}`;
  const family = await prisma.family.create({
    data: { slug, name: "Ownership probe" },
  });

  try {
    const owners = await Promise.all(
      [1, 2].map(async (n) => {
        const user = await prisma.user.create({
          data: { email: `${slug}-${n}@probe.invalid`, passwordHash: "x" },
        });
        const membership = await prisma.familyMember.create({
          data: { userId: user.id, familyId: family.id, role: "owner" },
        });
        return membership.id;
      }),
    );

    const results = await Promise.all(
      owners.map((membershipId) =>
        changeRole({ familyId: family.id, membershipId, nextRole: "member" }),
      ),
    );

    const refused = results.filter((r) => !r.ok).length;
    const remaining = await prisma.familyMember.count({
      where: { familyId: family.id, role: "owner" },
    });

    console.log(`demotions refused: ${refused}`);
    console.log(`owners remaining:  ${remaining}`);

    if (remaining !== 1) {
      throw new Error(`INVARIANT BROKEN: ${remaining} owner(s) remain, expected 1`);
    }
    console.log("\nownership invariant held under concurrent demotion");
  } finally {
    await prisma.family.delete({ where: { id: family.id } });
    await prisma.user.deleteMany({ where: { email: { startsWith: slug } } });
    await prisma.$disconnect();
  }
}

main().catch((error: unknown) => {
  console.error(error);
  process.exitCode = 1;
});

    Why this check exists rather than a unit test

    The bug this guards against is a race, and a race is invisible to a single-threaded unit test that mocks the model layer. It only appears with two real transactions against a real database — which is what this script is. The full pyramid arrives in week 7; this is the smallest thing that actually fails when the lock is removed, and you will need it the moment anyone "simplifies" the transaction.

Break it on purpose

  1. The one that matters. Comment out the lockFamily call in changeRole and run npm run check:ownership. Predict the output first, then look. You should see owners remaining: 0 and an INVARIANT BROKEN error — your family, permanently ownerless, with no API call able to fix it. Restore the lock. Then say out loud what FOR UPDATE did that the transaction alone did not.
  2. Privilege escalation. Delete requireRole("owner") from the PATCH route, log in as the member account, and PATCH your own membership id with {"role":"owner"}. It returns 204 — you have just promoted yourself. This is why the guard is a route argument and not a comment, and why "who may change roles" is the most dangerous rule in the file. Restore it.
  3. Order. Move requireRole("owner") in front of loadFamily (i.e. mount it in routes/index.ts before the /families/:slug mount). Predict, then call the route. It fails with a 500 saying Route is missing requireAuth/loadFamily — the tripwire, telling you the chain is out of order. A 403 here would have been a lie about the caller's role.
  4. Two codes, one mistake. Change the last-owner refusal from 409 to 403 and think about the client: it now cannot tell "you will never be allowed to leave this family" from "promote someone first, then leave". Which of those two messages can a UI act on?
  5. Make it non-idempotent. Change leaveFamily to return { ok: false, reason: "not-found" } when the membership is already gone, and map that to 404. Now a retried request — a dropped connection, a double-click — reports failure for an action that already succeeded. Explain which failure mode you prefer and why.
