  2. Model, service, view — one WHERE clause, one definition

    The query belongs beside findMembershipWithFamily: same table, same "membership joined to family" shape, one row versus many.

    server/src/models/membership.model.ts (addition) 
    /**
 * Every family this user belongs to, oldest first.
 *
 * Same property as findMembershipWithFamily, over many rows instead of one: the
 * userId is in the WHERE clause, so there is no version of this query that
 * returns a family the caller has no membership in. The oldest first is what
 * makes "your family" a stable answer instead of whatever the database returns.
 */
export async function findAllForUser(
  userId: string,
  database: Db = prisma,
): Promise<(FamilyMember & { family: Family })[]> {
  return database.familyMember.findMany({
    where: { userId },
    include: { family: true },
    orderBy: { createdAt: "asc" },
  });
}
    server/src/services/membership.service.ts (addition) 
    /**
 * The families this caller belongs to.
 *
 * A pass-through today -- the query is already scoped to the caller -- so the
 * value is in the naming, not the logic: the controller never touches a model,
 * and "which families are mine" has exactly one definition.
 */
export async function listMyFamilies(
  userId: string,
): Promise<(FamilyMember & { family: Family })[]> {
  return membershipModel.findAllForUser(userId);
}
    server/src/views/family.view.ts (new) 
    import type { FamilyResource } from "../contracts.js";
import type { Family, FamilyMember } from "../models/membership.model.js";

/**
 * The membership as the client may see it: which family, what it is called, and
 * what this caller may do there.
 *
 * The family id never crosses this line. The slug is the handle the client puts
 * in a URL, and an id it never sees is an id it cannot pass back to a route that
 * might trust it.
 */
export function toFamilyResource(
  row: FamilyMember & { family: Family },
): FamilyResource {
  return { slug: row.family.slug, name: row.family.name, role: row.role };
}

  3. The controller, and the route that resolves nothing

    server/src/controllers/family.controller.ts (addition) 
    import { authContext } from "../middlewares/auth.js";
import { toFamilyResource } from "../views/family.view.js";
import { listMyFamilies } from "../services/membership.service.js";
import type { ApiResponse, FamilyResource } from "../contracts.js";

/**
 * Every family the caller belongs to.
 *
 * This is the one family-shaped route that runs with requireAuth alone. There is
 * no :slug to resolve, because answering "which families are mine?" is the whole
 * point -- and the caller is named by the session, never by the request.
 */
export async function getMyFamilies(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const { userId } = authContext(req);
    const memberships = await listMyFamilies(userId);

    const body: ApiResponse<FamilyResource[]> = {
      data: memberships.map(toFamilyResource),
    };

    res.status(200).json(body);
  } catch (error) {
    next(error);
  }
}
    server/src/routes/index.ts (addition, under the guard) 
    // The list of families the caller belongs to. It resolves no :slug -- answering
// "which families are mine?" is the point -- so it rides requireAuth alone.
apiRouter.get("/families", getMyFamilies);

// :slug NAMES a family. Naming is not authorising: loadFamily proves the caller
// belongs to it, or answers 404 as if it did not exist.
apiRouter.use("/families/:slug", loadFamily, familyRouter);

    Note what is not here: no loadFamily. Every other /families/… route carries it, because every other one names a family and has to prove access to it. This route names nothing, so there is nothing to prove — the caller is the userId from the session, and the scoping is the where clause. It is also the first protected route in KinLink to use authContext(req) without familyContext.

  4. The runnable check

    Two users, three families, and one question: does the caller see their two and not the stranger's?

    server/src/scripts/checkFamilies.ts (new) 
    import "dotenv/config";
import { randomUUID } from "node:crypto";
import { prisma } from "../config/database.js";
import { listMyFamilies } from "../services/membership.service.js";
import { toFamilyResource } from "../views/family.view.js";

// Two users, three families. The caller must see their own two and neither of
// the stranger's: the userId is in the WHERE clause, the same property the
// family-scoped routes have, over many rows instead of one.
async function main(): Promise<void> {
  const suffix = randomUUID().slice(0, 8);
  const shared = await prisma.family.create({
    data: { slug: `probe-shared-${suffix}`, name: "Shared probe" },
  });
  const other = await prisma.family.create({
    data: { slug: `probe-other-${suffix}`, name: "Other probe" },
  });
  const strangerFamily = await prisma.family.create({
    data: { slug: `probe-stranger-${suffix}`, name: "Stranger probe" },
  });

  try {
    const me = await prisma.user.create({
      data: { email: `me-${suffix}@probe.invalid`, passwordHash: "probe" },
    });
    const stranger = await prisma.user.create({
      data: { email: `stranger-${suffix}@probe.invalid`, passwordHash: "probe" },
    });

    const t = Date.now();
    await prisma.familyMember.create({
      data: {
        userId: me.id,
        familyId: shared.id,
        role: "owner",
        createdAt: new Date(t - 2000),
      },
    });
    await prisma.familyMember.create({
      data: {
        userId: me.id,
        familyId: other.id,
        role: "member",
        createdAt: new Date(t - 1000),
      },
    });
    await prisma.familyMember.create({
      data: { userId: stranger.id, familyId: strangerFamily.id, role: "owner" },
    });

    const rows = await listMyFamilies(me.id);
    const resources = rows.map(toFamilyResource);
    const slugs = resources.map((r) => r.slug);
    const roles = resources.map((r) => r.role);

    console.log(`families returned: ${resources.length}`);
    console.log(`roles:             ${JSON.stringify(roles)}`);

    if (resources.length !== 2) {
      throw new Error(`EXPECTED 2 families, got ${resources.length}`);
    }
    if (slugs.includes(strangerFamily.slug)) {
      throw new Error("LEAK: another user's family was returned");
    }
    if (!slugs.includes(shared.slug) || !slugs.includes(other.slug)) {
      throw new Error("MISSING: one of the caller's families was not returned");
    }
    if (roles[0] !== "owner" || roles[1] !== "member") {
      throw new Error(
        `ORDER/ROLE WRONG: expected [owner, member], got ${JSON.stringify(roles)}`,
      );
    }
    if (resources.some((row) => "id" in row)) {
      throw new Error("LEAK: the family id crossed the view");
    }

    console.log("\nmy-families scoping, ordering and view mapping all held");
  } finally {
    await prisma.family.deleteMany({
      where: { id: { in: [shared.id, other.id, strangerFamily.id] } },
    });
    await prisma.user.deleteMany({ where: { email: { contains: suffix } } });
    await prisma.$disconnect();
  }
}

main().catch((error: unknown) => {
  console.error(error);
  process.exitCode = 1;
});

Two things to read carefully. The family body carries slug, name and role and no id. And with no cookie the answer is 401 JSON — not the HTML 404 the baseline produced, because the route now exists and the guard now runs.
