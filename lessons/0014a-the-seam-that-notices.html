Lesson 14a · Week 4–5 · about 60 minutes · one new thing

One place to notice a dead session

Log in, delete the session cookie, then click into your family. The client has no idea: it renders "Failed to load: GET /api/families/<slug>/invitations -> 401" while still showing you the logged-in family list. Only one screen in the app knows what a 401 means, and it is not the one that found out. Today moves that knowledge into the transport layer, so any request that discovers a dead session lands the whole app on the login screen.

Mission: ship KinLink Requires: Lesson 13d Reference: 10 · 12 Practice: Lesson 14d
The win

A dead session is noticed once and handled by every screen, for free. The knowledge leaves the one screen that had it and moves into the transport, so the failure mode of a future screen forgetting is gone before the screen is written.

Build it

  1. Verify the baseline, and reproduce the bug

    Both halves, as always — the commands, then the running app.

    npm run db:up
npm run typecheck          # exit 0
npm run check:families     # 2 families, roles [owner, member]

    Now cause it. Start the app, sign in, and then delete the session cookie out from under the running page: 

    npm run dev      # then open http://localhost:5173 and sign in

# DevTools → Application → Cookies → http://localhost:5173
#   delete  kinlink.sid
# then click your family's link (or reload /family/<slug>/invites)

    What you see is the bug. The page reads Failed to load: GET /api/families/<slug>/invitations -> 401 — and if you navigate back to /, the family list still renders, because useSession asked its question once at mount and nobody has asked it since. The app holds two contradictory beliefs: "I am logged in" and "I was just told 401".

    Why deleting the cookie is a fair test

    It is exactly what happens in production when the session expires (maxAge: 24h), when the store restarts, or when a session is invalidated server-side. And it is deterministic, which the alternative — restarting the API and waiting — is not. A bug you can cause on demand is a bug you can prove you fixed.

  2. The seam: one module that knows a session ended

    The transport layer is plain TypeScript. It has no React, and it must not learn any — request() is not a component and must never call useState. So it cannot reach useSession's state directly. It needs a seam. Give it the smallest one that works: a set of listeners, and two functions.

    client/src/lib/session.ts (new) 
    /**
 * The one place a dead session is announced.
 *
 * `request()` is plain TypeScript: it has no React and must not learn any, so it
 * cannot reach `useSession`'s state directly. It publishes here instead, and the
 * session hook subscribes. One request notices; every screen reacts.
 */
type Listener = () => void;

const listeners = new Set<Listener>();

/** Subscribe to "the server says our session is gone". Returns an unsubscribe. */
export function onSessionEnded(listener: Listener): () => void {
  listeners.add(listener);
  return () => {
    listeners.delete(listener);
  };
}

/** Called by the transport layer when a 401 means the session, not the input. */
export function announceSessionEnded(): void {
  for (const listener of listeners) listener();
}

    Twenty lines, no classes, no framework. The Set is the whole "event bus" — and the returned unsubscribe is what stops the listener accumulating every time a component remounts.

  3. The transport announces — but only when the 401 is about the session

    Here is the trap, and it is the whole reason this step is longer than it looks. POST /api/auth/login answers 401 when the password is wrong. That is a verdict on the input, not an eviction — and a transport that treats every 401 as "your session died" will punish a typo by logging the user out of a session they never had.

    client/src/lib/api.ts (addition) 
    import { announceSessionEnded } from "./session";

async function request<T>(
  path: string,
  options: {
    method?: "GET" | "POST";
    body?: unknown;
    /**
     * Does this request carry the caller's session?
     *
     * A 401 answers two different questions and the caller is the only one who
     * knows which was asked: on a session-carrying request it means "your
     * session is gone" -- a fact about the whole app; on a sign-in request it
     * means "those credentials are wrong" -- a verdict on this form's input.
     * Same status code, opposite blast radius.
     */
    expectsSession?: boolean;
  } = {},
): Promise<T> {
  const response = await fetch(path, { /* unchanged */ });

  if (!response.ok) {
    // The transport cannot tell the two 401s apart; the caller opted in above.
    // Announcing here is what makes the fix reach every screen at once instead
    // of each screen growing its own "Failed to load: ... 401" branch.
    if (response.status === 401 && (options.expectsSession ?? true)) {
      announceSessionEnded();
    }
    throw new ApiError(
      response.status,
      `${options.method ?? "GET"} ${path} -> ${response.status}`,
    );
  }
  // ... unchanged

    And the two callers that must opt out, because a wrong password is not a dead session:

    client/src/lib/api.ts (login and register) 
    export function login(input: {
  email: string;
  password: string;
}): Promise<AuthResponse> {
  return request<AuthResponse>("/api/auth/login", {
    method: "POST",
    body: input,
    expectsSession: false,
  });
}

export function register(input: {
  email: string;
  password: string;
}): Promise<AuthResponse> {
  return request<AuthResponse>("/api/auth/register", {
    method: "POST",
    body: input,
    expectsSession: false,
  });
}

    The default is true, which is the right direction to fail in: a new endpoint that forgets the option is treated as session-carrying, so a dead session is still noticed. Only the two sign-in endpoints, which are about being anonymous, opt out.

  4. The session subscribes

    client/src/lib/useSession.ts (addition) 
    import { onSessionEnded } from "./session";

// ... inside useSession(), after the existing fetch effect:

  // Any request, on any screen, can be the one that discovers the session is
  // gone. Subscribe once here so the app lands on the login screen whichever
  // call found out -- and so no screen has to handle a 401 itself.
  useEffect(
    () => onSessionEnded(() => setState({ status: "anonymous" })),
    [],
  );

    One line of subscription, and the effect returns the unsubscribe itself. This is the half that makes the bug go away: Home re-renders on the state change, unmounts FamilyList, and the login screen appears — even though the request that failed came from a different component entirely.
