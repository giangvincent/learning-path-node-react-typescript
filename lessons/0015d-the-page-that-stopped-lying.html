The page that stopped lying

AcceptPage is the last component that talks to fetch directly, and it collapses every failure into "This link doesn't work." But a 401 is not that: it means "sign in first." Today it joins the transport, and learns to tell the two apart.

Mission: ship KinLink Requires: Lesson 15c References: 10 · 06 Practice: Lesson 15f
The win

AcceptPage calls one named function in lib/api.ts. A signed-out visitor reads "Sign in to accept this invitation"; a used or expired link reads "This link doesn't work." grep -rn "fetch(" client/src now matches only the transport.

Warm-up: the third meaning of a 401

You already know two: a wrong password (a verdict) and a dead session (an eviction). The accept route sits under requireAuth, and the person clicking an invite link is often not signed in at all. What does a 401 mean here? Answer before you read the code.

Build it

  1. Verify the baseline

    npm run typecheck       # exit 0
npm run build:client    # builds
npm run check:session   # still green

    Read client/src/AcceptPage.tsx: it calls fetch directly with its own credentials: "include", and maps everything that is not 204 to one message. That single message is the lie.

  2. One named function in the transport

    Add the accept call beside getInvitations. It is expectsSession: false on purpose: a 401 here is not an eviction of an existing session — there may be no session at all — so the transport must not broadcast "your session ended." The page handles this one itself.

    client/src/lib/api.ts (addition) 
    export function acceptInvitation(token: string): Promise<void> {
  return request<void>(
    `/api/invitations/${encodeURIComponent(token)}/accept`,
    { method: "POST", expectsSession: false },
  );
}

    request already sends credentials: "include" and returns undefined on 204, so nothing else is needed.

  3. Rewrite the page: two failures, two messages

    client/src/AcceptPage.tsx (rewritten) 
    import { useEffect, useState } from "react";
import { useParams } from "react-router-dom";
import { ApiError, acceptInvitation } from "./lib/api";

type Status = "idle" | "ok" | "needs-sign-in" | "err";

export default function AcceptPage() {
  const { token } = useParams<{ token: string }>();
  const [status, setStatus] = useState<Status>("idle");

  useEffect(() => {
    if (!token) return;
    acceptInvitation(token)
      .then(() => setStatus("ok"))
      .catch((cause: unknown) => {
        if (cause instanceof ApiError && cause.status === 401) {
          setStatus("needs-sign-in");
          return;
        }
        setStatus("err");
      });
  }, [token]);

  if (status === "ok") return <p>You're in — go to the family.</p>;
  if (status === "needs-sign-in")
    return <p>Sign in to accept this invitation.</p>;
  if (status === "err") return <p>This link doesn't work.</p>;
  return <p>Accepting…</p>;
}

    The 409 stays collapsed — used, expired, revoked and already-member are one fact to a stranger holding a stale link (Reference 09 §5). Only the 401 is split out, because only its fix is different: signing in.

Verify after

npm run typecheck        # expected: exit 0
npm run build:client     # expected: builds
grep -rn "fetch(" client/src
                         # expected: only lib/api.ts matches now

Then cause both cases in the browser (this is the real proof, because the branch is a UI decision):

  1. Signed out. In a fresh private window with no cookie, open /invite/<any-token>. Expected: "Sign in to accept this invitation."
  2. Dead link. Sign in, mint an invite (curl is fine), open its link once to spend it, then open it again. Expected: "This link doesn't work."
Why not announce on the 401 here?

If expectsSession were left at its default true, a signed-out invitee's 401 would announce a dead session to an app that never had one. Defaults fail safe, and this is the caller that must opt out — same reasoning as login in lesson 14a, one route over.
