Defend it out loud

  1. Walk POST /api/families/:slug/people from the URL to the JSON response, naming the decision each of the six layers makes. Say it without looking at a file.
  2. familyId reaches the model from familyContext, never from the request body. Which type makes the alternative unrepresentable, not merely discouraged?
  3. Why does the model use updateMany where a reader would expect update? What does the returned count let the controller decide?
  4. The client caches server data instead of holding it in useState. Give the argument to a sceptic in two sentences, then name the counter-case (when useState really is right).
  5. All three mutations end in the same invalidateQueries call. Why is one call enough for a create, an edit and a delete?
  6. peopleKey is exported and shared. What breaks the day a second screen fetches people under its own literal key?
  7. The updated_at repair went in as its own commit before the edit path. Why does the sequencing matter more than the one-line diff?

Retrieval practice

Break it on purpose

  1. Unscope the update. Drop familyId from the where in person.model.update. Predict, then run check:people. Expected: the cross-family update succeeds and the check exits 1. The scope lived in the WHERE clause and nowhere else.
  2. Silence the create's invalidation. Remove the invalidateQueries from the add form's onSuccess. Predict the screen, then create a person: the row is written and the list does not move. Same drill, same result, on the delete.
  3. Lie about updated_at. Revert the schema to @default(now()), regenerate, edit a person, and read the row. The timestamp is frozen and nothing errors — the worst shape a defect can take.
  4. Return 200 instead of 204 on the delete. Change the handler to res.status(200).end() and delete a person from the screen. Predict first: request<void> now skips its 204 branch and calls response.json() on an empty body, so the delete succeeds on the server and throws on the client. The status code is part of the contract.
  5. Leak the family id from the view. Put familyId back into toPersonResource's return. See whether the compiler or the check catches it first, and note which one is allowed to miss it.
