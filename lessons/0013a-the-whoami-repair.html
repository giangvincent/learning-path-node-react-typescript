Lesson 13a · Week 4–5 · about 45 minutes · one new thing

Repair whoami before anyone depends on it

A shipped endpoint answers 500 while typecheck says everything is fine. Before the client can ask "am I logged in?", the endpoint that answers must work — and the fix is one line, because the function it should have called already exists. This is the first of four sittings; it is a repair, so it gets its own commit and nothing else.

Mission: ship KinLink Requires: Lesson 12 Reference: 10 Practice: Lesson 13e
The win

GET /api/auth/whoami answers 200, fixed by calling the model function that was written for it and used by nothing. One commit, on its own — a repair lands before the feature that depends on it.

Build it

  1. Verify the baseline, and find the defect

    House rule since lesson 11: prove the lesson's claim against main before writing any of it. Start the database and the dev servers, then run the two checks that already exist: 

    npm run db:up
npm run typecheck        # exit 0
npm run check:invites    # rows returned: 2

    Now the defect. Register — after your last file save — and then ask the endpoint this sitting is about, plus the one the next sitting adds: 

    npm run dev        # in one terminal

# in another: register, keeping the cookie jar
curl -sS -i -c /tmp/kinlink.jar -X POST http://localhost:4000/api/auth/register \
  -H 'Content-Type: application/json' \
  -d "{\"email\":\"owner-$(date +%s)@probe.invalid\",\"password\":\"password123\"}"

grep kinlink /tmp/kinlink.jar     # must print a kinlink.sid line

curl -sS -b /tmp/kinlink.jar -i http://localhost:4000/api/auth/whoami
curl -sS -b /tmp/kinlink.jar -i http://localhost:4000/api/families

    Expected, and both are wrong. whoami answers 500 with a Prisma message that names the culprit: Unknown field 'familyId' for select statement on model 'User'. typecheck was green a moment ago. And /api/families answers 404 whose body is HTML, not JSON — that is the missing read lesson 13b builds.

    An unmounted route fails in the wrong content type

    Cannot GET /api/families in <pre> tags is Express's built-in 404 handler. Nothing in this API ever wrote it — which is exactly why it is HTML. An API contract that says "errors are {"message": "…"}" is only as good as the routes that answer; the fall-through answers in its own language. A client that does response.json() on every failure throws a parse error here, and that is where the confusing bug report comes from.

    Two more traps, unchanged from lesson 12. 1. The session store is in memory and the dev server runs under tsx watch: every save restarts the process and kills every session. Register last, not first. 2. Do not diagnose a cookie with whoami until it is fixed — a 500 tells you nothing about your session. Use the list endpoint: 401 is a dead cookie, 404 is a slug that is not yours.

  2. Fix whoami — one line, its own commit

    The controller hand-wrote a select asking for familyId, a column User has not had since the family_members change. Prisma's excess-property check catches a bad select only when select is alone — with a where beside it, the check is silently dropped, so typecheck never saw it.

    server/src/controllers/auth.controller.ts (whoami) 
    // before — a hand-written query that bypassed the model layer
const user = await prisma.user.findUnique({
  select: { id: true, email: true, familyId: true },
  where: { id: userId },
});

// after — the function that already exists for this
const user = await userModel.findById(userId);
    Why this is not "delete the key"

    user.model.ts already exported findById(id), selecting exactly { id, email } — and grep -rn "findById" server/src shows it was used by nothing. It was written for whoami and the controller went around it. The fix removes the class of bug, not just the instance: one definition of "a user's public fields", and no hand-written select left to drift.

    Commit it alone, before anything else in this series. A reviewer should be able to see "this repairs a shipped 500" without reading four hundred lines of new client code, and the message should carry the mechanism the compiler missed, because that is the part worth remembering: 

    git add server/src/controllers/auth.controller.ts
git commit -F - <<'EOF'
Fix GET /api/auth/whoami answering 500

whoami hand-wrote select { id, email, familyId } on User, which has had
no familyId since the family_members change. Prisma's excess-property
check is dropped when select has a sibling key, so typecheck was green.
Call userModel.findById, which already selects the public fields.

Typecheck alone could not have caught this.
EOF

    This is lesson 05's rule again — fix the contract before the consumer. The whole identity flow the next three sittings build calls whoami; building it on a 500 would teach the client that "not logged in" means "the server is broken".

Verify (after)

npm run typecheck        # exit 0
npm run check:invites    # rows returned: 2

# restart the dev server (the save killed the session), re-register if the jar is stale
curl -sS -b /tmp/kinlink.jar -i http://localhost:4000/api/auth/whoami
# 200 {"data":{"userId":"…","email":"…"}}

whoami is 200 where it was 500. /api/families is still the HTML 404 — that is the next sitting's whole job. You are done when whoami answers and the repair is committed on its own.

Ask your teacher

Ask where the whoami fix belongs in the commit history — answers are in Lesson 13e. Ask whether typecheck should have caught this, and exactly when Prisma's excess-property check is dropped. And ask what else in the tree might be hiding behind the same blind spot.
