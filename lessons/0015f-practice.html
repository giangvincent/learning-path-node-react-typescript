Defend it out loud

  1. An invitation can end three ways. Name all three columns, and the one place that decides "pending".
  2. Why does the lock have to be taken before both the pending lookup and the insert?
  3. Why can't resend simply show the original link again, and what does it do instead?
  4. Why is a retried resend dangerous, and where have we seen that same non-idempotence before?
  5. A signed-out visitor opens an invite link and gets a 401. Why must that not end the session app-wide?
  6. Why did the mint route have to change when the client started using the transport?

Retrieval practice

Break it on purpose

  1. Remove lockFamily from the mint. Predict, then run check:mint. Expected: the second gate is reached, and two creates can succeed — exit 1.
  2. Drop revokedAt: null from the accept claim. The list still hides the row, but a revoked token is claimed anyway. Which definition lied?
  3. Drop revokedAt: null from the list. Now the list shows a withdrawn invite that accept will refuse. Which direction is worse, and why?
  4. Make resend skip the revoke. Run check:resend. Expected: the old token still works — the one property the whole design exists to guarantee.
  5. Return a bare { token } from the mint. Mint from the UI. Predict what the screen shows before you look: a link with undefined where the token should be.
