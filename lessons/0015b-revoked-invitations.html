Lesson 15b · Week 5 · ≈ one session · one new thing

The third end-state

An invitation can end three ways: claimed, expired, or withdrawn by its sender. The first two already have a shape. Today adds the third — a revokedAt column — and, crucially, keeps the two places that decide "pending" from drifting apart.

Mission: ship KinLink Requires: Lesson 15a References: 11 · 09 Practice: Lesson 15f
The win

revokedAt exists, and "pending" means three conditions — usedAt: null, revokedAt: null, and expiresAt > now — in both the list and the accept claim. A withdrawn invite disappears from the list and can no longer be claimed; npm run check:invites grows a fifth row and proves it.

Warm-up: two definitions of one word

From memory: which two places in the code decide whether an invitation can still be used? Name both. The whole risk of today's change is that they drift.

Build it

  1. Verify the baseline

    npm run db:up
npm run typecheck        # exit 0
npm run check:mint       # from 15a: one success, one refusal, one row
npm run check:invites    # 2 rows; pending filter and view mapping held

    No revoked_at column exists, and no code mentions revocation. Confirm that in the schema before you start.

  2. Add the column — nullable, and truthful as NULL

    "Not revoked" is a real value for every existing row, so NULL is honest rather than a placeholder. Adding a nullable column is INSTANT in MySQL 8.0 (metadata only), so there is nothing to backfill — unlike lesson 12's createdAt, which needed a real value for old rows. One statement, one migration, one thing.

    prisma/schema.prisma (Invitation, addition) 
      usedAt    DateTime? @map("used_at")
  revokedAt DateTime? @map("revoked_at")
  createdBy String    @map("created_by")
    terminal 
    npx prisma migrate dev --name add_invitation_revoked_at

    Read the generated migration.sql before applying it. It should be a single ALTER TABLE … ADD COLUMN revoked_at DATETIME(3) NULL; — no default, no rebuild.

  3. Move both definitions together

    Two places decide "can this invitation still be used": the list (findPendingByFamily) and the accept path (the compare-and-set in acceptInvitation). If you teach only the list about revocation, a revoked link still joins the family — the list lies and the token still works. Update both.

    server/src/models/invitation.model.ts 
        where: {
      familyId,
      usedAt: null,
      revokedAt: null,
      expiresAt: { gt: new Date() },
    },
    server/src/services/invitation.service.ts (claim in acceptInvitation) 
        const claimed = await tx.invitation.updateMany({
      where: {
        tokenHash: hashToken(token),
        usedAt: null,
        revokedAt: null,
        expiresAt: { gt: new Date() },
      },
      data: { usedAt: new Date() },
    });

    The model's own comment already warns that these two must not drift. Today is that warning coming true: three conditions, two places, one meaning.

  4. Grow the proof: a revoked invite is absent

    checkInvites.ts seeds four invitations and asserts that exactly the claimable two survive. Give the seed a revokedAt, add a fifth row that is revoked, and assert it is gone — from the list at least.

    server/src/scripts/checkInvites.ts (seed helper, addition) 
        const seed = async (input: {
      email: string | null;
      usedAt: Date | null;
      revokedAt: Date | null;
      expiresAt: Date;
      createdAt: Date;
    }): Promise<void> => {
      await prisma.invitation.create({
        data: {
          familyId: family.id,
          role: "member",
          email: input.email,
          tokenHash: `${slug}-${randomUUID()}`,
          createdAt: input.createdAt,
          expiresAt: input.expiresAt,
          usedAt: input.usedAt,
          revokedAt: input.revokedAt,
          createdBy: "probe",
        },
      });
    };

    Add revokedAt: null to the four existing seeds, then add the fifth and a matching assertion:

    server/src/scripts/checkInvites.ts (fifth seed and assertion) 
        await seed({
      email: "revoked@probe.invalid",
      usedAt: null,
      revokedAt: past,
      expiresAt: future,
      createdAt: new Date(t),
    });

    // ... after the existing checks:
    if (emails.includes("revoked@probe.invalid")) {
      throw new Error("NOT PENDING: a revoked invite was listed");
    }

    The count assertion stays 2 — five rows seeded, three of them ended (used, expired, revoked), two still claimable.

Break it once — and feel the drift

Delete revokedAt: null from the accept claim only, then walk a revoked token through acceptInvitation. Predict first: the list still hides the row (it kept its condition), but the token is claimed anyway — ok: true. That is the failure this step exists to prevent: two definitions of one word, and only one of them updated. Restore the line.
