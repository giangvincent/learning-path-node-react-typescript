The screen and its cache

A screen that fetches with useEffect and useState works — until a second screen needs the same data, or a write changes it. Today the client adopts a cache for state it does not own: the server's.

Mission: ship KinLink Requires: Lesson 16a References: 10 · 13 Practice: Lesson 16f
The win

/family/:slug/people renders the family's people, read through TanStack Query. The component names a key and a function; the library owns loading, error and cached data — the three states every hand-rolled fetch re-implements and gets subtly wrong.

Warm-up: retrieve before rereading

Build it

  1. Verify the baseline, then install the one new module

    The library is not in this project yet, and this lesson is where it arrives. Name it, install it, and prove it resolved before writing a line that imports it. 

    npm run typecheck                       # exit 0
npm ls @tanstack/react-query            # empty: not installed yet
npm i @tanstack/react-query@^5          # resolves to 5.104.2 on this machine
npm ls @tanstack/react-query            # now shows the version
    Why a library, and why this one

    Server state is not client state. It lives somewhere else, it can be stale, and two screens showing it must agree. TanStack Query's whole job is that problem: a keyed cache, stale-while-revalidate, and — the part we will use in the very next lesson — invalidation. It is worth a dependency because the thing it replaces (a store plus hand-written refetch logic) is where the bugs live.

  2. One cache for the whole app

    A QueryClient is the cache. It is created once, outside the component tree, and handed down by a provider. Creating it inside a component would build a new cache on every render.

    client/src/main.tsx 
    import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { BrowserRouter } from "react-router-dom";
import App from "./App";

const container = document.getElementById("root");
if (!container) throw new Error("Missing #root element");

// One cache for the whole app, created once. A component asks for data by key;
// this client is what remembers the answer and, on invalidation, forgets it.
const queryClient = new QueryClient();

createRoot(container).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <BrowserRouter>
        <App />
      </BrowserRouter>
    </QueryClientProvider>
  </StrictMode>,
);

  5. The screen: a key, a function, three states

    Everything that fetches one family's people agrees on one key. Exporting it is what will let the next lesson invalidate it from another component.

    client/src/PeoplePage.tsx (new) 
    import { useQuery } from "@tanstack/react-query";
import { Link, useParams } from "react-router-dom";
import { ApiError, getPeople } from "./lib/api";

/**
 * The key every query and mutation for one family's people shares. A mutation
 * that invalidates this exact key is what turns "the server changed" into "the
 * list re-fetched" -- the whole reason a cache exists.
 */
export const peopleKey = (slug: string) => ["people", slug] as const;

export default function PeoplePage() {
  const { slug } = useParams<{ slug: string }>();
  if (!slug) return <p role="alert">No family in this URL.</p>;
  return <PeopleList slug={slug} />;
}

function PeopleList({ slug }: { slug: string }) {
  const query = useQuery({
    queryKey: peopleKey(slug),
    queryFn: () => getPeople(slug),
  });

  return (
    <main style={{ fontFamily: "system-ui, sans-serif", padding: "2rem" }}>
      <h1>People</h1>
      <p>
        <Link to={`/family/${slug}/invites`}>Invitations</Link>
      </p>

      {query.isPending && <p>Loading…</p>}
      {query.isError && (
        <p role="alert">
          {query.error instanceof ApiError
            ? `Failed to load (${query.error.status}).`
            : "Failed to load."}
        </p>
      )}
      {query.data?.length === 0 && <p>No people yet.</p>}
      {query.data && query.data.length > 0 && (
        <ul>
          {query.data.map((person) => (
            <li key={person.id}>
              {person.name} {person.living ? "· living" : "· deceased"}
            </li>
          ))}
        </ul>
      )}
    </main>
  );
}

    Two details worth dwelling on. The outer component narrows slug to a string and only then renders the inner one — that is why the query function needs no slug! or as string. And query.isPending is the library's name for "no data yet"; v5 renamed the old isLoading, which now means something narrower (a fetch in flight), so copy the names rather than the older tutorials.

Break it on purpose — predict first

Two failures arrive as different status codes, and the client must treat them differently. Predict both, then test both. First delete kinlink.sid in DevTools and reload the people screen: the request answers 401, the transport announces a dead session (lesson 14), and you land on the sign-in form. Now put a wrong slug in the address bar with a valid cookie: the server answers 404 Family not found — an ordinary ApiError, not a session event — so the screen shows Failed to load (404). and stays put. Same component, one status that ends the session and one that does not.

Decisions carried into the next sittings

  • useSession stays hand-rolled — for now. TanStack Query could fetch the identity too, but useSession carries a rule the library does not know: a 401 means anonymous, and any other failure means error. That is session policy, not caching. The trigger to revisit is written down: migrate it when the session needs to be invalidated by a mutation — login and logout are exactly that, so this is a genuine open question, not a settled one.
  • No client store was added. The temptation is a Zustand store named people holding the fetched array. Resist it: the array's owner is the server. A client store filled by a fetch is a stale copy with extra steps. A client store earns its place for client-owned state — the tree's layout, a current selection — not for a cache of someone else's truth.
  • The key is the invalidation contract. Every reader and every writer of "one family's people" must name peopleKey(slug). If a second screen ever fetches people with its own literal key, invalidation will silently miss it. Grep for "people" the day that screen appears.
