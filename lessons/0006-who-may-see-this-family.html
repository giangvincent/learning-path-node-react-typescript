Lesson 06 · Week 4 · about two hours

Who may see this family?

Lesson 04 taught the server who you are. Now it has to answer the harder question: may you see this family? That needs a relationship rather than a column — and it needs three different status codes, because "no such family" and "not your family" must be indistinguishable.

Mission: ship KinLink Reference: Authorisation Requires: Lesson 05
The win

User.familyId — one family per user, a placeholder since lesson 04 — is replaced by a family_members relationship with a role, backfilled by a migration that does not lose a single link. The session stops carrying authorisation data at all. And GET /api/families/:slug/people answers 200 for a member, 404 for a non-member, and 401 with no session — where the 404 is a deliberate lie, and the most important line of code in the lesson.

Why User.familyId has to go

Lesson 03 established the rule: the tenant id comes from the session and never from the request. That rule was correct for the model you had — a user belonging to exactly one family, so the session could remember it and no family needed naming. Three things break it:

  1. A relative will belong to two families. Your mother is in her birth family and the family she married into. One familyId column cannot hold that, and "the current family" stops being a property of the person.
  2. The role has nowhere to live. "Owner" is not a property of a person and it is not a property of a family — it is a property of the relationship between them. The same user is an owner here, a member there.
  3. The URL has to name a family. With two families there is no implicit one, so the request must say which. Which means the old rule needs sharpening rather than abandoning — more on that below.
This is ReBAC, and you should know the word

Access derived from a relationship between a subject and a resource is relationship-based access control, and OWASP's Authorization Cheat Sheet now recommends it over plain RBAC, precisely because roles are "poorly suited" to object-level questions like ours. KinLink is a ReBAC product: everything hangs off this user's relationship to this family. The role is one attribute of that relationship, not a separate system.

Build it

  1. The relationship, and the constraint that makes it a fact

    prisma/schema.prisma (changes) 
    enum FamilyRole {
  owner
  admin
  member
}

model Family {
  id        String   @id @default(uuid())
  slug      String   @unique
  name      String
  createdAt DateTime @default(now()) @map("created_at")

  people      Person[]
  memberships FamilyMember[]

  @@map("families")
}

model User {
  id           String   @id @default(uuid())
  email        String   @unique @map("email")
  passwordHash String   @map("password_hash")
  createdAt    DateTime @default(now()) @map("created_at")
  updatedAt    DateTime @updatedAt @map("updated_at")

  memberships FamilyMember[]

  @@map("users")
}

model FamilyMember {
  id        String     @id @default(uuid())
  userId    String     @map("user_id")
  familyId  String     @map("family_id")
  role      FamilyRole @default(member)
  createdAt DateTime   @default(now()) @map("created_at")

  user   User   @relation(fields: [userId], references: [id], onDelete: Cascade)
  family Family @relation(fields: [familyId], references: [id], onDelete: Cascade)

  @@unique([userId, familyId])
  @@index([familyId])
  @@map("family_members")
}

    Note what User lost: familyId. And what Family gained: memberships, not users. The join table is the domain concept, and both sides point at it.

    @@unique([userId, familyId]) is the load-bearing line. Without it a user can accumulate three membership rows for the same family, two of them stale, and "what is my role" becomes a query with an arbitrary answer. With it, membership is a fact the database enforces — not a convention your service layer remembers.

  2. The migration that must not drop your data

    Here is the trap. The schema change above removes a column that currently holds the only link between a user and their family. Run migrate dev and Prisma will faithfully do what you asked: create the new table, then drop users.family_id, orphaning every existing user. Nothing errors. The users simply stop belonging to anyone.

    So you generate the migration without applying it, put the backfill in the middle, and then apply it: 

    npx prisma migrate dev --create-only --name add_family_members

    Open prisma/migrations/<timestamp>_add_family_members/migration.sql and insert the INSERT … SELECT between the table creation and the drop:

    prisma/migrations/<ts>_add_family_members/migration.sql 
    -- CreateTable
CREATE TABLE `family_members` (
    `id` VARCHAR(191) NOT NULL,
    `user_id` VARCHAR(191) NOT NULL,
    `family_id` VARCHAR(191) NOT NULL,
    `role` ENUM('owner', 'admin', 'member') NOT NULL DEFAULT 'member',
    `created_at` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    UNIQUE INDEX `family_members_user_id_family_id_key`(`user_id`, `family_id`),
    INDEX `family_members_family_id_idx`(`family_id`),
    PRIMARY KEY (`id`)
) DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- Backfill BEFORE the column disappears. Every existing user becomes the owner of
-- the family they were previously attached to; without this, the DROP below
-- silently orphans every account.
INSERT INTO `family_members` (`id`, `user_id`, `family_id`, `role`, `created_at`)
SELECT UUID(), `id`, `family_id`, 'owner', NOW(3) FROM `users`;

-- DropForeignKey / DropColumn
ALTER TABLE `users` DROP FOREIGN KEY `users_family_id_fkey`;
ALTER TABLE `users` DROP COLUMN `family_id`;
    npx prisma migrate dev

    Now prove the backfill landed, because a migration that "succeeded" is not evidence that it preserved anything: 

    docker compose exec mysql mysql -ukinlink -pkinlink kinlink -e "
SELECT (SELECT COUNT(*) FROM users)         AS users,
       (SELECT COUNT(*) FROM family_members) AS memberships;"

    Those two numbers must be equal. If they are not, you have just discovered why --create-only exists — and it is cheaper to discover here than in production, where the same mistake is called an incident.

  3. The session stops guessing

    familyId must come out of the session too, and noticing why is the point of this step. A value belongs in the session only if it is stable for the life of the session. Authorisation context is not: it depends on which resource you named, and it changes request to request. Keeping it there was a mirror of the old model, and the mirror was already lying.

    server/src/middlewares/auth.ts 
    import type { Request, RequestHandler } from "express";
import type { ApiErrorBody } from "../contracts.js";

/** Reject unauthenticated requests. 401, not 500: nothing failed on the server. */
export const requireAuth: RequestHandler = (req, res, next) => {
  const { userId } = req.session;

  if (!userId) {
    const body: ApiErrorBody = { message: "Authentication required" };
    res.status(401).json(body);
    return;
  }

  req.authenticatedUserId = userId;
  next();
};

/** Identity, refusing to guess. Throws only if the chain is wired wrong. */
export function authContext(req: Request): { userId: string } {
  const { authenticatedUserId } = req;

  if (!authenticatedUserId) {
    throw new Error("Route is missing requireAuth");
  }

  return { userId: authenticatedUserId };
}

  4. The one query that cannot forget the membership

    server/src/models/membership.model.ts 
    import { prisma } from "../config/database.js";
import type {
  Family,
  FamilyMember,
  FamilyRole,
} from "../../generated/prisma/client.js";

// The model layer re-exports the ORM's types so nothing above it imports Prisma.
export type { Family, FamilyMember };
export type Role = FamilyRole;

/**
 * The single query that answers "may this user act on this family?".
 *
 * The membership is part of the WHERE clause, so there is no version of this
 * function that returns a family the caller has no relationship with. The
 * tempting alternative -- findFamilyBySlug() then findMembership() -- is two
 * facts, and then the security property rests on somebody remembering to compare
 * them. Make the unsafe version unrepresentable instead.
 */
export async function findMembershipWithFamily(
  userId: string,
  slug: string,
): Promise<(FamilyMember & { family: Family }) | null> {
  return prisma.familyMember.findFirst({
    where: { userId, family: { slug } },
    include: { family: true },
  });
}
    server/src/services/membership.service.ts 
    import * as membershipModel from "../models/membership.model.js";
import type { Family, FamilyMember } from "../models/membership.model.js";

export interface FamilyAccess {
  family: Family;
  membership: FamilyMember;
}

/**
 * Policy: which family is this caller allowed to act on?
 *
 * Returns null for BOTH "no such family" and "not a member of it". That collapse
 * happens HERE, on purpose, so the middleware that turns null into a response has
 * no difference left to leak. One return value, one status code, no oracle.
 */
export async function findFamilyAccess(
  userId: string,
  slug: string,
): Promise<FamilyAccess | null> {
  const row = await membershipModel.findMembershipWithFamily(userId, slug);
  if (row === null) return null;

  return { family: row.family, membership: row };
}

    Three layers, three questions, exactly as lesson 03 set up: the model answers the fact ("which membership row joins this user to this slug"), the service answers the policy ("which family may this caller act on"), and the middleware is about to answer the HTTP question ("what status code does that deserve").

  5. The middleware that deliberately lies

    server/src/middlewares/family.ts 
    import type { Request, RequestHandler } from "express";
import type { ApiErrorBody } from "../contracts.js";
import type { Family, FamilyMember } from "../models/membership.model.js";
import { findFamilyAccess } from "../services/membership.service.js";
import { authContext } from "./auth.js";

/**
 * Resolve :slug to a family this caller belongs to, or answer 404.
 *
 * Both "no such family" and "not a member of it" answer 404 with the same body,
 * because a 403 would confirm the family exists and turn this endpoint into a
 * directory of every family in KinLink.
 *
 * Async middleware: Express 5 forwards a rejection to the error handler, so a
 * database failure becomes a 500 without a try/catch here.
 */
export const loadFamily: RequestHandler = async (req, res, next) => {
  const { userId } = authContext(req);
  const { slug } = req.params;

  if (typeof slug !== "string" || slug.length === 0) {
    const body: ApiErrorBody = { message: "Family not found" };
    res.status(404).json(body);
    return;
  }

  const access = await findFamilyAccess(userId, slug);
  if (access === null) {
    const body: ApiErrorBody = { message: "Family not found" };
    res.status(404).json(body);
    return;
  }

  req.family = access.family;
  req.membership = access.membership;
  next();
};

/**
 * The authorisation context, read from the request rather than re-derived.
 * Throws only when the chain is wired wrong -- an assertion, not a response.
 */
export function familyContext(req: Request): {
  userId: string;
  family: Family;
  membership: FamilyMember;
} {
  const { authenticatedUserId, family, membership } = req;

  if (!authenticatedUserId || !family || !membership) {
    throw new Error("Route is missing requireAuth/loadFamily");
  }

  return {
    userId: authenticatedUserId,
    family,
    membership,
  };
}

    Read the two 404 branches again. They are identical, and that is not duplication to be tidied away — a reviewer who "DRYs" those into one branch per failure reason would reintroduce the oracle. The reason a 404 happened must never reach the client.

    server/src/controllers/people.controller.ts

  req: Request,
  res: Response,

    Delete server/src/routes/people.routes.ts. Two URLs for one collection is two code paths to secure, two to test and two to remember. Once a family is nameable, the session-implied version is redundant, and redundant routes are how audits rot.

  7. Registration stops joining a hardcoded family

    Lesson 04's register looked up the family with slug: "nguyen" — a placeholder that also has a security shape worth naming: if registering into a family were driven by a slug the caller supplied, anybody who guessed a slug could join a family. Registering should therefore create your own family, with you as its owner; joining someone else's family is an invitation problem, and invitations are a later feature.

    That is three inserts that must all succeed or none: a half-created account is worse than a failed request, because a user row with no family can never log in and retrying the same email does not repair it.

    server/src/models/user.model.ts 
    import { randomUUID } from "node:crypto";
import { prisma } from "../config/database.js";
import type { User as PrismaUser } from "../../generated/prisma/client.js";

export type User = PrismaUser;

export async function findByEmail(email: string): Promise<User | null> {
  return prisma.user.findUnique({ where: { email } });
}

export async function findById(
  id: string,
): Promise<{ id: string; email: string } | null> {
  return prisma.user.findUnique({
    where: { id },
    select: { id: true, email: true },
  });
}

/**
 * A new account: the user, the family they own, and the membership linking them.
 *
 * One transaction, because those three rows are one fact. It lives in the model
 * rather than the service because a transaction boundary is a data-integrity
 * boundary and queries belong to this layer -- and because it is currently the
 * only operation that needs a Prisma transaction handle. When a second one
 * appears, extract a `Db` type and thread it through the model functions instead
 * of growing this pattern by hand.
 */
export async function createWithOwnedFamily(input: {
  email: string;
  passwordHash: string;
}): Promise<{ user: User; familyId: string }> {
  const local = input.email.split("@")[0] ?? "family";
  const base =
    local.toLowerCase().replace(/[^a-z0-9]+/g, "-").replace(/^-|-$/g, "") ||
    "family";

  return prisma.$transaction(async (tx) => {
    const family = await tx.family.create({
      data: {
        // A short random suffix makes the slug unique without a retry loop.
        slug: `${base}-${randomUUID().slice(0, 6)}`,
        name: `${local}'s family`,
      },
    });

    const user = await tx.user.create({
      data: { email: input.email, passwordHash: input.passwordHash },
    });

    await tx.familyMember.create({
      data: { userId: user.id, familyId: family.id, role: "owner" },
    });

    return { user, familyId: family.id };
  });
}
    While you are in there: a layering slip to fix

    Lesson 04's register and login call prisma.user.findUnique directly from the controller, which breaks the rule this project has been holding since lesson 02: the model is the only layer allowed to know how data is stored. Moving those lookups to user.model.ts is not busywork — it is what makes "where do I change a query?" answerable, and it is why findByEmail and findById appeared above.

    server/src/controllers/auth.controller.ts (register, new shape) 
    export async function register(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const { email, password }: { email: string; password: string } = req.body;

    const existing = await userModel.findByEmail(email);
    if (existing) {
      res.status(409).json({ message: "Email already registered" });
      return;
    }

    const passwordHash = await bcrypt.hash(password, SALT_ROUNDS);
    const { user } = await userModel.createWithOwnedFamily({ email, passwordHash });

    // Identity only. Which family, and what you may do there, is per request.
    req.session.userId = user.id;

    res.status(201).json({
      data: { userId: user.id, email: user.email } satisfies AuthResponse,
    });
  } catch (error) {
    next(error);
  }
}

    And in login / whoami: delete every req.session.familyId = … line, and drop familyId from AuthResponse in shared/contracts/auth.ts. A field that no longer has one truthful value cannot be left in the contract, and the client is not built yet, so now is the cheapest moment it will ever be.

    Two smaller consequences of the same change: pull const SALT_ROUNDS = 12; out of the function body, since register and the seed script now both need it, and route login through userModel.findByEmail so no controller touches prisma directly.

Steps 3 and 4 are the whole lesson

A member gets their own family. A non-member gets the same response as someone asking for a family that does not exist. Your server has stopped answering "does this family exist?" for people it has not authenticated — which is the property no amount of UUIDs or obscurity could have given you.

Break it on purpose

  1. Change the not-a-member branch in loadFamily from 404 to 403, restart, and re-run steps 3 and 4. The two responses now differ — and you have built an endpoint that maps every family in KinLink for anyone who holds any account. Revert it, then explain out loud why 403 is correct for a role failure and wrong for a membership failure.
  2. Make the leak real. In membership.service.ts, replace the service call with a family lookup that ignores the membership — prisma.family.findUnique({ where: { slug } }) — and return it with a fabricated membership. Predict the response before you run step 3, then run it. You should now receive another family's people. This is the exact bug that findMembershipWithFamily's single where clause makes impossible, and it is worth seeing once, in development, in your own code.
  3. Move apiRouter.use("/families/:slug", …) above apiRouter.use(requireAuth). Predict, then run npm run check:guards. You get a 500 whose message is Route is missing requireAuth — the tripwire from lesson 05, still doing its job one layer down. Now delete the authContext(req) call so the throw cannot fire, and observe what happens to an anonymous request. Which of the two failures would you rather read about in a log?
  4. In family.routes.ts, make the handler read req.params.slug directly and log it. It is undefined. Now create the router as Router({ mergeParams: true }) and it appears. Explain why you are not going to do that, and what a child router would have to re-do (and re-check) if it read the slug itself.
  5. Write down, without looking: why can a 404 from loadFamily not be replaced by a 401? They are both "you cannot have this", and the client would behave almost identically. The answer is about what the two codes tell an attacker, not about the caller's experience.
