Lesson 10 · Week 4–5 · about sixty minutes

Render the invitation client

The server API is done. The client still has no invite UI: owners can't send invites, nobody sees pending invites, and the accept flow only lives in curl. Make the API visible — a dialog for owners, a list for members, a token-in-URL accept page.

Mission: ship KinLink Requires: Lesson 09 Reference: Reference 09
The win

Three things, in one session: an owner's "send invite" dialog (POST /api/invitations), a pending-invites list with expiry, and an /invite/:token page that calls accept.

Build it

  1. Owner sees "send invite" only when their rank allows

    Load the family's memberships via the existing /api/families/:slug/people endpoint (already guarded by loadFamily + requireAuth). Show the dialog only if the caller's membership role is admin or owner. Read the role from the response — don't trust the client.

    client/src/InviteDialog.tsx (new) 
    function InviteDialog({ familySlug }: { familySlug: string }) {
  const [email, setEmail] = useState("");
  const [role, setRole] = useState<"member" | "admin">("member");
  const [pending, setPending] = useState(false);

  const send = async () => {
    setPending(true);
    const r = await fetch(`/api/invitations`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      credentials: "include",
      body: JSON.stringify({ email, role }),
    });
    setPending(false);
    if (r.status === 403) alert("Insufficient role");
    if (r.status === 201) alert("Invite sent — token in response");
  };

  return (
    <form onSubmit={e => { e.preventDefault(); send(); }}>
      <input value={email} onChange={e => setEmail(e.target.value)}
             placeholder="email" required />
      <select value={role} onChange={e => setRole(e.target.value as any)}>
        <option value="member">member</option>
        <option value="admin">admin</option>
      </select>
      <button type="submit" disabled={pending}>Send invite</button>
    </form>
  );
}

  2. Pending invites list with expiry

    The server has no list endpoint yet (Prisma has no index on expiresAt for lookups). Add one:

    server/src/controllers/invitation.controller.ts (new) 
    import { prisma } from "../config/database.js";

export async function listInvitations(
  req: Request,
  res: Response,
  next: NextFunction
): Promise<void> {
  try {
    const { slug } = req.params;
    const family = await prisma.family.findUnique({ where: { slug } });
    if (!family) { res.status(404).json({ message: "Family not found" }); return; }
    const invites = await prisma.invitation.findMany({
      where: { familyId: family.id, usedAt: null, expiresAt: { gt: new Date() } },
      select: { email: true, role: true, expiresAt: true, createdBy: true },
      orderBy: { createdAt: "desc" },
    });
    res.json({ data: invites });
  } catch (e) { next(e); }
}

    Mount at GET /api/families/:slug/invitations under loadFamily. Owner-only or member-visible — your call; the lesson keeps it member-visible (hides sent invites if you want owner-only, change the route guard).

  3. Accept page reads the token from the URL

    The accept flow lands on a page like /invite/<token>. The page extracts the token from the path, calls POST /api/invitations/:token/accept, and renders the result — "joined" or "this link doesn't work". No body, no custom header; the token is the only credential.

    client/src/AcceptPage.tsx (new) 
    function AcceptPage() {
  const { token } = useParams();
  const [status, setStatus] = useState<"idle" | "ok" | "err">("idle");

  useEffect(() => {
    fetch(`/api/invitations/${token}/accept`, {
      method: "POST", credentials: "include",
    }).then(r => setStatus(r.status === 204 ? "ok" : "err"));
  }, [token]);

  if (status === "ok") return <p>You're in — go to the family.</p>;
  if (status === "err") return <p>This link doesn't work.</p>;
  return <p>Accepting…</p>;
}

Three questions from the design

  1. Shareable link or targeted? Both valid. Shareable (email: null) — anyone with the URL joins, doesn't prove the family exists. Targeted (email set) — leaks existence by design. Accept treats both the same: session userId is the only identity, role + rank check regardless of email.
  2. Expiry vs last-owner guard? Different objects. The invite is a credential; the membership is the authority. An expired-unaccepted invite is harmless; an accepted one keeps authority after expiry. The guard operates on memberships, so expiry never undermines it.
  3. Idempotency keys on accept? No — the token itself is the idempotency key: second POST consumes it and returns 409 used, no duplicate membership. What needs idempotency is the mint endpoint (double-submit creates two invites; the schema has no unique constraint on email — add one if you want to close that door).

Retrieval practice

Ask your teacher

Ask how the accept page handles the case where the user is already a member — should it redirect to the family or show "already a member"? Ask whether the pending-invites list should show email or "someone" for shareable links. Ask what happens when the accept page is opened after the invite expires — should the client auto-refresh or show a retry?
