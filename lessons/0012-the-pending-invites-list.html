Lesson 12 · Week 4–5 · about seventy-five minutes

The pending-invites list

An owner mints an invite, gets a token back once, and then — nothing. There is no way to see what is outstanding. Lesson 10 tried to write this endpoint and left two type errors behind. Today: give Invitation the column it was missing, walk one read through every layer the way people does, and prove with a runnable check that the list shows only what can still be claimed.

Mission: ship KinLink Requires: Lesson 11 Reference: Reference 09
The win

GET /api/families/:slug/invitations answers 200 with the family's claimable invites, newest first, owner-only, and the token hash nowhere in the body. Plus a runnable proof — npm run check:invites — that a used invite and an expired invite are both absent, and that a shareable link survives the wire as email: null.

Build it

  1. Verify the baseline (before)

    Lesson 11 left typecheck green and no list route. Prove the absence with a real request. First get a session cookie as an owner (register makes you one): 

    npm run db:up && npm run dev        # in one terminal

# in another — register, keeping the cookie jar
curl -sS -i -c /tmp/kinlink.jar -X POST http://localhost:4000/api/auth/register \
  -H 'Content-Type: application/json' \
  -d "{\"email\":\"owner-$(date +%s)@probe.invalid\",\"password\":\"password123\"}"

    Read the response before going on. You need 201 Created and a Set-Cookie: kinlink.sid=… header. If you see 409 {"message":"Email already registered"}, the jar stays empty and every request after this one answers 401 — which looks exactly like "the lesson is broken" and is not. That is why the email above is unique per run instead of a fixed string. 

    grep kinlink /tmp/kinlink.jar   # must print a kinlink.sid line, not nothing
    The two traps between register and request

    1. The session store is in memory. express-session defaults to MemoryStore, and the dev server runs under tsx watch. Every file save restarts the process and every session dies with it. So while you are still creating files, the cookie you just earned is already dead by the time you curl. Register after your last save. (This is the concrete reason lesson 05's reference reaches for Redis in production — not theory, this exact papercut.)

    2. Do not diagnose the session with /whoami. It is the broken endpoint lesson 12 flagged: it answers 500 on main because it selects a familyId that User no longer has. A 500 tells you nothing about your cookie. Use the list endpoint instead — 401 means no session, 404 means the session is fine but the slug is not a family you belong to.

    The slug is the part that bites. Register does not return it, and — this is a real gap — no endpoint tells you which families you belong to yet. Worse, every register creates a brand-new family: re-registering does not reuse your old one, so a slug you copied from an earlier run now belongs to a different user and answers 404 "Family not found". That 404 is the loadFamily collapse working correctly — the family either does not exist or you are not in it, and you must not be able to tell which.

    Two ways to find yours. The slug is derived, so you can predict it: the email's local part, lowercased with runs of non-alphanumerics replaced by -, then six random characters. So owner-1791449541@probe.invalid owns a family whose slug starts owner-1791449541-. Or just look: 

    npm run db:studio    # browse `families`, copy the slug of the family whose
                     # `name` matches the email you just registered with

    Then ask for the list:

    curl -sS -b /tmp/kinlink.jar -i http://localhost:4000/api/families/<slug>/invitations

    Expected right now: 404. The router is mounted but has no GET route, so Express falls through. That 404 is this lesson's red line. Read the body: a {"message":"Family not found"} here means the slug is wrong (or stale); a {"message":"Authentication required"} means the cookie is gone. Two different problems, two different fixes — do not reach for the wrong one.

    Design gap worth naming now

    A slug the client cannot discover is a slug the client cannot use. The API answers "what is in this family?" but never "which families are mine?", so today the only ways to learn a slug are the database or the registration side effect. The client cannot do either. A GET /api/families returning the caller's families with slugs and roles is the missing read — and it is the first thing lesson 13 needs, because the list UI has to know which family it is rendering.

    Three other statuses are worth capturing while you are here, because the lesson has to keep them: 401 with no cookie, 404 for a family you are not in (the loadFamily collapse), 403 for a member who is not an owner.

  2. Give Invitation the column it was missing

    Lesson 10's controller ordered by createdAt, a column that did not exist. That was not a stray typo: Family, User, FamilyMember and Person all record when they were created, and Invitation does not. A pending-invite list wants to say "sent two days ago", and ordering needs the field, so add it.

    prisma/schema.prisma (addition) 
    model Invitation {
  id        String    @id @default(uuid())
  familyId  String    @map("family_id")
  role      FamilyRole @default(member)
  email     String?
  tokenHash String  @unique @map("token_hash")
  expiresAt DateTime @map("expires_at")
  usedAt    DateTime? @map("used_at")
  createdBy String    @map("created_by")
  createdAt DateTime  @default(now()) @map("created_at")

  family Family @relation(fields: [familyId], references: [id], onDelete: Cascade)

  @@index([familyId])
  @@map("invitations")
}
    terminal 
    npx prisma migrate dev --name add_invitation_created_at
    Two things this migration is honest about

    Existing rows are backfilled with the migration time. @default(now()) on a table with rows means every old invite claims it was created at migration. For a dev database of test invites that is fine; for production you would add the column nullable, backfill a real value, then tighten it. Say the second half out loud in an interview — it is the difference between "migrations ran" and "migrations were reasoned about".

    This migration does one thing. The pending query would like an index on (familyId, usedAt, expiresAt), but at a handful of rows that is unmeasurable and it is a separate change. House rule from lesson 08: a migration should do one thing.

    The cheaper fix, and why it loses

    You could avoid the migration by ordering on expiresAt — today every invite is createdAt + 7 days, so the two orders are identical. It loses on honesty: the ordering silently depends on the TTL being constant, and the list still cannot say when an invite was sent. Adding the missing column is one word of schema and removes the dependence.

  3. The contract: what the client may see

    Both sides compile against shared/contracts/. Define the resource here, before any server code, so the shape is a decision you made rather than a side effect of the query.

    shared/contracts/invitation.ts (new) 
    /** What the client is allowed to see about one invitation. Not a database row. */
export interface InvitationResource {
  id: string;
  /** null = a shareable link; the client labels it, it does not invent a name. */
  email: string | null;
  role: "owner" | "admin" | "member";
  /** ISO-8601. JSON has no Date type, so the wire carries strings. */
  createdAt: string;
  expiresAt: string;
}
    server/src/contracts.ts (addition) 
    export type { InvitationResource } from "../../shared/contracts/invitation.js";
    The answer to the open question

    Shareable links show email: null, and the client labels that "Anyone with the link". Not "someone". "Someone" implies a person was chosen and their identity is being withheld; a shareable link has no addressee at all — it is a door left open. The owner needs to tell the two apart precisely so they can revoke the right one, so the distinction travels in the contract as null, not as a display string.

  4. The model: one definition of "pending"

    Lesson 09 and 10 put the invitation queries in the service, because the lock and the compare-and-set are the transaction's business. A plain read has no such excuse: it goes through the model layer like every other read in KinLink.

    server/src/models/invitation.model.ts (new) 
    import { prisma } from "../config/database.js";
import type { Invitation } from "../../generated/prisma/client.js";
import type { Db } from "./db.js";

// The model layer re-exports the ORM's types so nothing above it imports Prisma.
export type { Invitation };

/**
 * Pending = not claimed and not expired.
 *
 * The same pair of conditions the accept path checks, in the same transaction
 * that consumes a token. If the two ever drift, the list starts offering
 * invitations the accept endpoint will refuse.
 */
export async function findPendingByFamily(
  familyId: string,
  database: Db = prisma,
): Promise<Invitation[]> {
  return database.invitation.findMany({
    where: { familyId, usedAt: null, expiresAt: { gt: new Date() } },
    orderBy: { createdAt: "desc" },
  });
}

  5. The service

    One function, and it is a pass-through today. That is the point: the controller is not allowed to touch the database, and pending is a policy word that deserves a name in the layer where policy lives.

    server/src/services/invitation.service.ts (addition) 
    import * as invitationModel from "../models/invitation.model.js";
import type { Invitation } from "../models/invitation.model.js";

/**
 * The invitations a family can still act on, newest first.
 *
 * "Pending" is a policy word, so it lives here rather than in the query the
 * controller could have written: one definition of claimable, in one place.
 */
export async function listPendingInvitations(
  familyId: string,
): Promise<Invitation[]> {
  return invitationModel.findPendingByFamily(familyId);
}

  6. The view: the hash never crosses this line

    server/src/views/invitation.view.ts (new) 
    import type { InvitationResource } from "../contracts.js";
import type { Invitation } from "../models/invitation.model.js";

/**
 * The row as the client may see it.
 *
 * The token hash never crosses this line -- there is no field for it to travel
 * in. The two dates become ISO strings because JSON has no Date, and the view
 * is the only place that decision is made.
 */
export function toInvitationResource(row: Invitation): InvitationResource {
  return {
    id: row.id,
    email: row.email,
    role: row.role,
    createdAt: row.createdAt.toISOString(),
    expiresAt: row.expiresAt.toISOString(),
  };
}

    This is a whitelist, not a filter. If someone later adds a notes column to Invitation, it does not appear on the wire by accident — the view has to name it.

  7. The controller and the route

    server/src/controllers/invitation.controller.ts (new) 
    import type { NextFunction, Request, Response } from "express";
import type { ApiResponse, InvitationResource } from "../contracts.js";
import { familyContext } from "../middlewares/family.js";
import { listPendingInvitations } from "../services/invitation.service.js";
import { toInvitationResource } from "../views/invitation.view.js";

/**
 * The invitations a family can still act on.
 *
 * The controller names no family and does not read the session. It asks for the
 * family the request was authorised against -- loadFamily already proved the
 * caller belongs to it. The slug is never re-read from the URL here; the proof
 * is the middleware's, and the id is the only trustworthy handle it left behind.
 */
export async function getFamilyInvitations(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const { family } = familyContext(req);
    const invitations = await listPendingInvitations(family.id);

    const body: ApiResponse<InvitationResource[]> = {
      data: invitations.map(toInvitationResource),
    };

    res.status(200).json(body);
  } catch (error) {
    next(error);
  }
}
    server/src/routes/invitation.routes.ts (addition) 
    import { getFamilyInvitations } from "../controllers/invitation.controller.js";

// Owner-only: the list carries invitees' emails and the roles they were offered.
invitationRouter.get("/", requireRole("owner"), getFamilyInvitations);

    requireRole("owner") matches the mint route beside it. One deliberate inconsistency to notice: lesson 10's client renders the invite dialog for admin or owner, but the server allows only owners to mint. That is a product decision — "may admins manage invitations?" — and it should be made once, on purpose, then applied to both routes together. Lesson 13 tightens the client to match until you decide.

  8. The runnable check

    A filter is logic. Seed four invitations in four states and assert the list shows exactly the claimable ones.

    server/src/scripts/checkInvites.ts (new) 
    import "dotenv/config";
import { randomUUID } from "node:crypto";
import { prisma } from "../config/database.js";
import { listPendingInvitations } from "../services/invitation.service.js";
import { toInvitationResource } from "../views/invitation.view.js";

// Four invitations, four states. The list must show exactly the claimable two:
// a used invite is not pending, an expired invite is not pending, and the
// shareable row (email: null) must survive the wire as null, not as "".
async function main(): Promise<void> {
  const slug = `probe-${randomUUID().slice(0, 8)}`;
  const family = await prisma.family.create({
    data: { slug, name: "Pending probe" },
  });

  try {
    const future = new Date(Date.now() + 86_400_000);
    const past = new Date(Date.now() - 86_400_000);

    const seed = async (input: {
      email: string | null;
      usedAt: Date | null;
      expiresAt: Date;
      createdAt: Date;
    }): Promise<void> => {
      await prisma.invitation.create({
        data: {
          familyId: family.id,
          role: "member",
          email: input.email,
          tokenHash: `${slug}-${randomUUID()}`,
          createdAt: input.createdAt,
          expiresAt: input.expiresAt,
          usedAt: input.usedAt,
          createdBy: "probe",
        },
      });
    };

    const t = Date.now();
    await seed({ email: "old@probe.invalid", usedAt: null, expiresAt: future, createdAt: new Date(t - 2000) });
    await seed({ email: null, usedAt: null, expiresAt: future, createdAt: new Date(t - 1000) });
    await seed({ email: "used@probe.invalid", usedAt: past, expiresAt: future, createdAt: new Date(t) });
    await seed({ email: "stale@probe.invalid", usedAt: null, expiresAt: past, createdAt: new Date(t) });

    const rows = await listPendingInvitations(family.id);
    const resources = rows.map(toInvitationResource);
    const emails = resources.map((r) => r.email);

    console.log(`rows returned:  ${resources.length}`);
    console.log(`emails:         ${JSON.stringify(emails)}`);
    console.log(`newest first:   ${emails[0] === null}`);

    if (resources.length !== 2) {
      throw new Error(`EXPECTED 2 pending, got ${resources.length}`);
    }
    if (!emails.includes(null)) {
      throw new Error("SHAREABLE HIDDEN: the email:null row is missing");
    }
    if (emails.includes("used@probe.invalid") || emails.includes("stale@probe.invalid")) {
      throw new Error("NOT PENDING: a used or expired invite was listed");
    }
    if (emails[0] !== null) {
      throw new Error("ORDER WRONG: expected the newest first");
    }
    const sample = resources[0];
    if (
      typeof sample?.createdAt !== "string" ||
      typeof sample?.expiresAt !== "string"
    ) {
      throw new Error("VIEW WRONG: dates must cross the wire as ISO strings");
    }

    console.log("\npending filter, ordering and view mapping all held");
  } finally {
    await prisma.family.delete({ where: { id: family.id } });
    await prisma.$disconnect();
  }
}

main().catch((error: unknown) => {
  console.error(error);
  process.exitCode = 1;
});

What typecheck does not catch (measured)

While probing this lesson I wrote prisma.user.findUnique({ select: { id: true, familyId: true } }) on a model with no familyId. Two results, same session:

  • select alone → error TS2353: 'familyId' does not exist in type 'UserSelect'.
  • the same select with a where beside it → no error at all.

At runtime the query throws Unknown field 'familyId' for select statement on model 'User'. So the excess-property check that protects a bare select is lost as soon as the object has a second key. This is not hypothetical: server/src/controllers/auth.controller.ts line 121 selects exactly that shape in whoami, so GET /api/auth/whoami answers 500 — with a green typecheck. The lesson: typecheck proves the code parses; only running it proves it works. Both halves of every Verify block exist for this reason.

Defend it

Why is "pending" defined in one place?

The list and the accept handler must agree on what claimable means. If the list is written from a different definition — say it forgets the expiry check — the owner sees invitations the invitee cannot use, and the bug looks like an accept failure. One definition, referenced twice.

Why does the controller not read req.params.slug?

Lesson 10's version did, and that is where one of its two type errors came from. The deeper problem is not the type: re-reading the slug means re-deriving an authorisation fact that loadFamily already proved. familyContext(req).family.id is the id of the family the request was authorised against — the only handle worth trusting.

Why is the list owner-only?

It carries invitees' email addresses and the roles they were offered. That is administrative data about membership, and membership changes are owner business today. If the product says admins invite people, move requireRole("owner") to "admin" on both the list and the mint route in the same commit.

What are the three refusal statuses here?

401 no session — requireAuth, before anything family-shaped is read. 404 not a member — loadFamily collapsing "no such family" and "not your family" into one body. 403 member but not owner — requireRole, and legitimately honest about it, because the caller is inside the boundary and already knows the family exists.

Break it on purpose

  1. Drop the expiry condition. Change the where clause to where: { familyId, usedAt: null }. Run npm run check:invites. Predict first: the stale invite reappears — rows returned: 3. Measured with both conditions removed: rows returned: 4, and the check throws EXPECTED 2 pending, got 4.
  2. Return the raw rows and skip the view. Put res.json({ data: invitations }) in the controller. The response now carries tokenHash — a credential, on a list endpoint. This is the mistake the view exists to make impossible.
  3. Move the guard to "member". Any member now reads every pending invitee's email address. The 403 is the only thing standing between a member and the family's invitation book.
  4. Trust the bare select. Add familyId: true to a select that also has a where, and run npm run typecheck. It is green. Then call the endpoint. It is a 500. Typecheck is half a proof.

Retrieval practice

Ask your teacher

Ask how to backfill created_at for real production rows instead of stamping them with the migration time. Ask whether the pending list should paginate before it can ever be long. Ask for the one-line fix to the whoami 500, and where it belongs in the commit history. Ask what the client does when it has no session at all — there is still no login screen.
