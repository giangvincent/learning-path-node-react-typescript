Lesson 04 · Week 4 · about two hours

Who are you? Authentication

Replace the hardcoded CURRENT_FAMILY_ID with a real session: register, log in, have the server prove it, and verify that nobody else can read your data.

Mission: ship KinLink Vocabulary: session, cookie Requires: Lesson 03
The win

You will go from a server that trusts nothing to one that knows exactly who is asking. A new users table is created via Prisma migration, passwords are hashed with bcrypt, an HTTP-only session cookie replaces the placeholder constant, and /api/people returns only the rows that belong to the logged-in user's family.

Why sessions, not JWTs

Your spec mentions JWT as one possibility. There are good reasons to start with a session instead:

Concern Session (cookies) JWT
XSS attack surface httpOnly + secure = unreadable by JS Stored in localStorage if used → readable by XSS
Revocation Delete the session record; done Need a blocklist or very short expiry + refresh token
Distributed systems Shared store needed (Redis, DB); adds complexity Signed, self-contained; easier scale-out
Family app reality You are one domain, one server. Start with what fits. Introduce later when you need cross-origin.

Sessions are not "worse". They are simply the wrong choice when the architecture demands distribution. Right now it does not. Choose for the problem you have, not the one you hope for.

Build it

  1. Install dependencies

    npm install express-session bcrypt
npm install -D @types/express-session @types/bcrypt

    express-session manages the cookie and stores the session payload. bcrypt hashes passwords. Both are industry-standard, both well-tested, both used in production apps of all sizes. No crypto shortcuts here.

    Note: @types/bcrypt ships with bcrypt 6.x under the same package name (@types/bcrypt@6.0.0). If you were using an older major version, you would need @types/bcrypt. Modern bcrypt has bundled types.

  2. Add the users table

    One addition to schema.prisma. Everything above the model layer stays unchanged until the moment the database requires otherwise.

    prisma/schema.prisma (append this model) 
    model User {
  id           String    @id @default(uuid())
  email        String    @unique @map("email")
  passwordHash String    @map("password_hash")
  familyId     String    @map("family_id")
  createdAt    DateTime  @default(now()) @map("created_at")
  updatedAt    DateTime  @updatedAt @map("updated_at")

  family Family @relation(fields: [familyId], references: [id], onDelete: Cascade)

  @@map("users")
}

    Notice the design choices:

    • Email is unique, not a PK. The user's identifier is opaque (the UUID), but their contact point is their email. Separating identity from identification is a principle worth remembering.
    • passwordHash, not password. The column name tells you everything: this is a hash. Never call a field password in code, never store plaintext passwords anywhere.
    • The family link belongs on the user, not inside family_members. For Phase 1 MVP the user IS a member. More complex setups arrive later when multiple people can share one account (unlikely in a private family context). 
    npx prisma migrate dev --name add_users_table

  3. Configure the session

    Session config lives in its own file because it touches many concerns: cookie flags, lifetime, secret, storage medium. Changing any one of these has real security implications, and they should be visible together.

    server/src/config/session.ts 
    import type { RequestHandler } from "express";
import session from "express-session";
import type { SessionOptions } from "express-session";
import "dotenv/config";

const isProd = process.env.NODE_ENV === "production";

const sessionConfig: SessionOptions = {
  // Secret rotates signatures. In production this MUST be a 32-character random string
  // stored in the environment, never in source control.
  secret: process.env.SESSION_SECRET ?? "change-me-in-production",
  resave: false,                          // do not save unmodified sessions back to storage
  saveUninitialized: false,               // do not create sessions until something is stored
  proxy: isProd,                          // trust reverse proxy headers in production
  cookie: {
    httpOnly: true,                       // JavaScript cannot read the cookie
    secure: isProd,                       // send only over HTTPS in production
    sameSite: "lax",                      // CSRF-safe: allows GET from same-site navigation
    maxAge: 24 * 60 * 60 * 1000,          // 24 hours
  },
  name: "kinlink.sid",                    // custom cookie name instead of connect.sid
  rolling: true,                          // renew expiry on each request
};

export const sessionMiddleware: RequestHandler = session(sessionConfig);

    Five decisions worth pausing on:

    1. sameSite: "lax". This prevents CSRF for GET requests and allows normal navigation from other domains. It means POST requests from another domain will fail to include the cookie — which is the correct security posture. Set "strict" once you implement CSRF tokens for forms.
    2. secure: isProd. In development, cookies are sent over plain HTTP (localhost). In production, they require HTTPS. Browsers silently drop secure cookies on non-HTTPS connections, so leaving it always-on breaks local development.
    3. rolling: true. Without this, the cookie expires after the last explicit login. With rolling, every page view renews the countdown — as long as the user is active, their session stays alive. Idle users time out naturally.
    4. name: "kinlink.sid". The default name is connect.sid. Changing it avoids accidentally colliding with another Express session running on the same domain. Not a security decision, but it prevents hard-to-debug issues.
    5. resave: false, saveUninitialized: false. These are the most misunderstood options in express-session. resave: false means "don't write back to storage unless the session changed." saveUninitialized: false means "don't create empty sessions for visitors who haven't logged in." Together they reduce disk writes and prevent session fixation attacks on anonymous users.
    .env (add SESSION_SECRET) 
    # Run once to generate: node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
SESSION_SECRET="your-32-character-random-here"

    Never reuse a SESSION_SECRET. Rotate it periodically in production. Anyone who knows it can forge sessions for anyone.

  4. Add the session middleware to the app pipeline

    This is a small change with a large effect: from this line onward, every incoming request carries a req.session object. Where it sits in the pipeline matters.

    server/src/app.ts 
    import express from "express";
import { errorHandler } from "./middlewares/errorHandler.js";
import { apiRouter } from "./routes/index.js";
import { sessionMiddleware } from "./config/session.js";

// Builds the application but does NOT listen. That separation is what lets a
// test exercise the whole stack without opening a port.
export function createApp() {
  const app = express();

  app.use(express.json());
  app.use(sessionMiddleware);                // ← add before routes
  app.use("/api", apiRouter);
  app.use(errorHandler);

  return app;
}

    Order matters: middleware runs top-to-bottom. express.json() must come before route handlers that parse bodies. sessionMiddleware must come before routes that read req.session. Error handler goes last because it catches errors thrown by everything above it.

  5. The authentication routes

    Four endpoints in one router. Keep them narrow: register, login, logout, whoami. Each does exactly one thing and has exactly one response shape.

    shared/contracts/auth.ts 
    /** Payload sent when registering a new user */
export interface RegisterRequest {
  email: string;
  password: string;
}

/** What follows the user home after login */
export interface AuthResponse {
  userId: string;
  familyId: string;
  email: string;
}

/** Consistent error envelope */
export interface ApiErrorBody {
  message: string;
}

    Wait — this changes the contract. Lesson 01 says the contract is the boundary between client and server. Adding fields to the API means the contract grows. That's fine; contracts grow organically, not in bulk. The rule is: only the minimum necessary data crosses the boundary, and every field earns its place.

    server/src/controllers/auth.controller.ts 
    import type { NextFunction, Request, Response } from "express";
import bcrypt from "bcrypt";
import { prisma } from "../config/database.js";
import type { AuthResponse } from "../../shared/contracts/auth.js";

/**
 * Register a new user. Creates the account, hashes the password, assigns the
 * user to the specified family, and logs them in immediately.
 *
 * In production you would separate registration from login: create the account,
 * send an email confirmation, then let them log in separately. For this lesson
 * we combine both steps to keep the loop tight.
 */
export async function register(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const { email, password }: { email: string; password: string } = req.body;

    // 1. Check uniqueness before hashing — cheap failure
    const existing = await prisma.user.findUnique({ where: { email } });
    if (existing) {
      res.status(409).json({ message: "Email already registered" });
      return;
    }

    // 2. Hash the password (cost factor 12 is recommended for modern hardware)
    const saltRounds = 12;
    const passwordHash = await bcrypt.hash(password, saltRounds);

    // 3. Look up the target family (you could also auto-create during invite flow)
    // For this lesson: look up by slug to establish family membership.
    const family = await prisma.family.findFirst({
      where: { slug: "nguyen" },       // replace with user selection in future
    });
    if (!family) {
      res.status(404).json({ message: "Family not found" });
      return;
    }

    // 4. Create user with session association
    const user = await prisma.user.create({
      data: {
        email,
        passwordHash,
        familyId: family.id,
      },
    });

    // 5. Log them in
    req.session.userId = user.id;
    req.session.familyId = family.id;

    res.status(201).json({
      data: {
        userId: user.id,
        familyId: family.id,
        email: user.email,
      } satisfies AuthResponse,
    });
  } catch (error) {
    next(error);
  }
}

/** Login with email and password */
export async function login(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const { email, password }: { email: string; password: string } = req.body;

    const user = await prisma.user.findUnique({ where: { email } });
    if (!user) {
      res.status(401).json({ message: "Invalid credentials" });
      return;
    }

    const match = await bcrypt.compare(password, user.passwordHash);
    if (!match) {
      // Constant-time comparison on the hash, but timing still leaks that the
      // email exists (user not found ≠ wrong password). Preventing user enumeration
      // requires more care (rate limiting, generic messages). Acknowledge the leak.
      res.status(401).json({ message: "Invalid credentials" });
      return;
    }

    req.session.userId = user.id;
    req.session.familyId = user.familyId;

    res.status(200).json({
      data: {
        userId: user.id,
        familyId: user.familyId,
        email: user.email,
      } satisfies AuthResponse,
    });
  } catch (error) {
    next(error);
  }
}

/** Destroy the session */
export async function logout(
  _req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    req.session.destroy((err) => {
      if (err) {
        next(err);
        return;
      }
      res.clearCookie("kinlink.sid");
      res.status(204).end();
    });
  } catch (error) {
    next(error);
  }
}

/** Return the authenticated user's info (no sensitive data) */
export async function whoami(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const userId = req.session.userId;
    if (!userId) {
      res.status(401).json({ message: "Not authenticated" });
      return;
    }

    const user = await prisma.user.findUnique({
      select: { id: true, email: true, familyId: true },
      where: { id: userId },
    });
    if (!user) {
      res.status(401).json({ message: "Session invalid" });
      return;
    }

    res.status(200).json({
      data: {
        userId: user.id,
        familyId: user.familyId,
        email: user.email,
      } satisfies AuthResponse,
    });
  } catch (error) {
    next(error);
  }
}
    server/src/routes/auth.routes.ts 
    import { Router } from "express";
import { register, login, logout, whoami } from "../controllers/auth.controller.js";

export const authRouter = Router();

authRouter.post("/register", register);
authRouter.post("/login", login);
authRouter.post("/logout", logout);
authRouter.get("/whoami", whoami);

    Notice that login uses bcrypt.compare(), not equality. bcrypt generates a random salt per hash, so identical passwords produce different hashes. compare() extracts the salt from the stored hash and recomputes to check equality. Always use compare; never hash-and-compare.

    Timing attack awareness

    bcrypt.compare() runs in constant time, so it doesn't leak how many characters matched. But the overall response time still differs slightly between "user not found" and "wrong password" because finding a user takes a DB query. Mitigation: use rate limiting, or return the same generic message for both cases ("Invalid credentials"). For a private family app, the risk is low. For anything public, fix it.

  6. Replace the placeholder — auth middleware

    This is the piece that removes CURRENT_FAMILY_ID. An auth middleware intercepts every request, checks the session, and either forwards the request (authenticated) or rejects it (unauthenticated). When authenticated, it attaches the user's info to req.user so downstream code never needs to touch the session again.

    server/src/middlewares/auth.ts 
    import type { RequestHandler } from "express";

interface SessionWithUser extends Express.MutatedSession {
  userId?: string;
  familyId?: string;
}

/** Attach user info from the session, reject if absent. */
export const requireAuth: RequestHandler = (req, _res, next) => {
  const session = req.session as unknown as SessionWithUser;
  if (!session.userId || !session.familyId) {
    req.next(new Error("Authentication required"));
    return;
  }

  req.authenticatedUserId = session.userId;
  req.authenticatedFamilyId = session.familyId;
  next();
};

    The middleware reads from the session once, then puts values on req for downstream code to use. This is intentional: controllers and services should read from req.authenticatedFamilyId, not from req.session. That is dependency direction in action: the service depends on the request wrapper, not on session internals.

    server/src/controllers/people.controller.ts 
    import type { NextFunction, Request, Response } from "express";
import type { ApiResponse, PersonResource } from "../contracts.js";
import { listPeople } from "../services/people.service.js";
import { toPersonResource } from "../views/person.view.js";

interface RequestWithAuth extends Request {
  authenticatedUserId: string;
  authenticatedFamilyId: string;
}

export async function getPeople(
  req: RequestWithAuth,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const people = await listPeople(req.authenticatedFamilyId);
    const body: ApiResponse<PersonResource[]> = {
      data: people.map(toPersonResource),
    };

    res.status(200).json(body);
  } catch (error) {
    next(error);
  }
}
    server/src/services/people.service.ts 
    import * as personModel from "../models/person.model.js";
import type { Person } from "../models/person.model.js";

/** Forward the call through to the model. The model enforces scoping. */
export async function listPeople(familyId: string): Promise<Person[]> {
  return personModel.findByFamily(familyId);
}

    The controller now reads req.authenticatedFamilyId (set by middleware) instead of a magic constant. The service passes it straight to the model. The model filters the query. Three layers, one value, no gaps.

    server/src/routes/index.ts 
    import { Router } from "express";
import type { ApiResponse } from "../contracts.js";
import { authRouter } from "./auth.routes.js";
import { peopleRouter } from "./people.routes.js";
import { requireAuth } from "../middlewares/auth.js";

export const apiRouter = Router();

apiRouter.get("/health", (_req, res) => {
  const body: ApiResponse<{ status: "ok" }> = { data: { status: "ok" } };
  res.status(200).json(body);
});

apiRouter.use("/auth", authRouter);
apiRouter.use("/people", requireAuth, peopleRouter);

    Notice requireAuth runs before peopleRouter. It is part of the routing chain, not applied inside individual route handlers. This is the pattern: apply auth at the route group level, not manually in every handler.

    # Step 1: see the endpoint reject without auth
curl -s http://localhost:4000/api/people | json_pp

# Step 2: register

# Step 3: login (extract the Set-Cookie header)
curl -si -X POST http://localhost:4000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"correcthorsebatterystaple"}' > /tmp/login.txt 2>&1
grep -i 'set-cookie' /tmp/login.txt

# Step 4: make a protected request WITH the cookie
curl -s -b '/tmp/login.txt' http://localhost:4000/api/people | json_pp

# Step 5: verify the other family's data is invisible
docker compose exec mysql mysql -ukinlink -pkinlink kinlink \
  -e "SELECT display_name FROM people WHERE family_id != (SELECT family_id FROM users WHERE email='test@example.com');" 
curl -s -b '/tmp/login.txt' http://localhost:4000/api/people | grep displayName

# Step 6: logout clears the session
curl -s -X POST http://localhost:4000/api/auth/logout -b '/tmp/login.txt' -v
curl -s http://localhost:4000/api/people | json_pp # should fail now

    Step 1 should return {"message": "Authentication required"}. Steps 2–6 should demonstrate register → login → access → isolation → logout → reject. If any step fails, the error message is your teacher. Read it, understand it, fix it.

Verify

  • Without a session cookie, GET /api/people returns {"message": "Authentication required"}.
  • Register creates a user, hashes the password, and sets req.session.userId.
  • Login finds the user, verifies with bcrypt.compare(), and reuses the existing session.
  • POST /auth/logout destroys the session, clears the cookie, and subsequent requests are rejected.
  • Two users in different families cannot see each other's data through the API.

Break it on purpose

  1. Remove req.session.httpOnly = true (which doesn't exist — that's a compiler error, good). Instead, remove httpOnly: true from the cookie config, then try to read document.cookie in the browser console. If you see kinlink.sid=..., the cookie was exposed. Fix it. Then ask: if someone steals a cookie like this, what can they do? (Answer: everything your user can do.)
  2. Delete requireAuth from apiRouter.use("/people", ...). Now call /api/people without logging in. Isolation is gone. The bug is invisible in the controller code — the fix lives one line above it in the router. How do you make that harder to forget?
  3. Register with the same email twice. What happens? Now delete the resave config option. How does behaviour change? Write down what resave and saveUninitialized actually do in one sentence each.
  4. Try bcrypt.compare(wrongPassword, validHash) vs bcrypt.compare(wrongPassword, nonexistentHash). Measure the response times. The difference is sub-millisecond and indistinguishable at human scale, but it exists. Does preventing this matter for a private family app? For a public SaaS? Answer for both.
