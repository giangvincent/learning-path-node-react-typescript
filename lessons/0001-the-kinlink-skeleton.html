Lesson 01 · Week 1 · about three hours

The KinLink skeleton: one folder, two architectures

Stand up the real project — React + TypeScript client, Express + TypeScript server organised as MVC — and push one request through every layer until a relative's name appears in the browser.

Mission: ship KinLink Reference: Express MVC Vocabulary: GLOSSARY.md
The win

One project folder. One command — npm run dev — starts Express on port 4000 and Vite on port 5173. The browser shows a person that travelled from the model, through the service, shaped by the view, returned by the controller, and typed at both ends by a single contract. /api/people exists because you built all six layers, not because you copied a snippet.

Why this shape

You asked for MVC on the server, and that is what we build — but it is worth being precise about why the layers exist, because "MVC" gets repeated a lot without people being able to justify it.

Each layer exists to make one kind of change cheap. A new response field is a view change. A new business rule is a service change. A new URL is a route change. A new column is a model change. When the layers are respected, none of those four edits touch the same file. When they are not, every change touches everything — which is exactly what a two-hundred-line server.ts feels like after a month. 

browser ──▶ vite proxy ──▶ ROUTE ──▶ MIDDLEWARE ──▶ CONTROLLER
                                                        │
                                                      SERVICE
                                                        │
                                                       MODEL
                                                        │
                                                       MySQL
                                                        │
                                                       VIEW ──▶ JSON ──▶ React

Today the model holds an array instead of MySQL. That is deliberate: it keeps the seam visible before Prisma arrives in lesson 02 and hides it behind a generated client. Nothing above the model will change when the database does — and at the end of this lesson you will prove that claim by breaking it on purpose.

    Why these live where they do

    express, react and react-dom are runtime dependencies — they ship. Everything else is a development dependency: TypeScript, the bundler, the dev runner, and all the type definitions. Vite bundles only what the client actually imports, so nothing from the server ends up in the browser bundle.

  3. The contracts — the types both sides compile against

    The client needs to know the shape of what the server returns. Most single-folder projects solve this by writing the type twice and letting it drift. We solve it with one folder both sides include.

    shared/contracts/api.ts 
    export interface ApiResponse<T> {
  data: T;
  meta?: Record<string, unknown>;
}

export interface ApiErrorBody {
  message: string;
  errors?: Record<string, string[]>;
}
    shared/contracts/person.ts 
    export type Gender = "male" | "female" | "other" | "unknown";

/** What the client is allowed to see. Not the same as a database row. */
export interface PersonResource {
  id: string;
  familyId: string;
  name: string;
  living: boolean;
}

    Note PersonResource has name, but the model will have displayName, and the eventual table will have given_name and surname. Three different shapes for three different audiences — that is not duplication, that is the point of the View layer.

  4. The server: config and the contract seam

    server/src/contracts.ts 
    export type { ApiErrorBody, ApiResponse } from "../../shared/contracts/api.js";
export type { Gender, PersonResource } from "../../shared/contracts/person.js";

    Three lines that save you from ../../../.. everywhere. Note the .js extension on a .ts file — that is not a typo. The server compiles with module: NodeNext, and Node's ESM resolver requires the real file extension at runtime. TypeScript understands you mean api.ts.

    tsconfig.json (server + shared) 
    {
  "compilerOptions": {
    "target": "ES2022",
    "lib": ["ES2022"],
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "types": ["node"],
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "verbatimModuleSyntax": true,
    "rootDir": ".",
    "outDir": "dist",
    "skipLibCheck": true
  },
  "include": ["server/src", "shared"]
}
    One line worth staring at: "lib": ["ES2022"]

    No DOM. The server is not allowed to know that document, window or fetch-in-a-tab exist. Type that into a server file and the compiler stops you. The client tsconfig will do the exact opposite. This is how the type system enforces the architectural boundary between the two halves of your website.

    server/src/config/env.ts 
    function readPort(): number {
  const raw = process.env.PORT ?? "4000";
  const port = Number(raw);

  if (!Number.isInteger(port) || port <= 0) {
    throw new Error(`PORT must be a positive integer, received "${raw}"`);
  }

  return port;
}

export const env = {
  port: readPort(),
  nodeEnv: process.env.NODE_ENV ?? "development",
} as const;

    Configuration is validated once, at startup, and re-exported as a typed object. If PORT is garbage the process refuses to boot instead of failing mysteriously on the first request — a rule you will appreciate much more once there are database URLs and secrets in here.

  5. The four layers, in the order a request hits them

    Model — the only layer allowed to know how data is stored.

    server/src/models/person.model.ts 
    import type { Gender } from "../contracts.js";

export interface Person {
  id: string;
  familyId: string;
  displayName: string;
  gender: Gender;
  birthDate: string | null;
  deathDate: string | null;
}

// The Model layer. Lesson 02 replaces this array with Prisma queries --
// and nothing above this file will need to change.
const people: Person[] = [
  {
    id: "p_1",
    familyId: "f_1",
    displayName: "Nguyễn Văn An",
    gender: "male",
    birthDate: "1948-03-02",
    deathDate: null,
  },
  {
    id: "p_2",
    familyId: "f_1",
    displayName: "Trần Thị Bình",
    gender: "female",
    birthDate: "1952-07-19",
    deathDate: null,
  },
];

export async function findAll(): Promise<Person[]> {
  return people;
}

    Service — where rules live. Note the signature: no Request, no Response, nothing from Express. That is what makes it testable and reusable from a background job later.

    server/src/services/people.service.ts 
    import * as personModel from "../models/person.model.js";
import type { Person } from "../models/person.model.js";

export async function listPeople(): Promise<Person[]> {
  return personModel.findAll();
}

    View — domain object in, resource out. The one place that decides what the outside world may see.

    server/src/views/person.view.ts 
    import type { PersonResource } from "../contracts.js";
import type { Person } from "../models/person.model.js";

export function toPersonResource(person: Person): PersonResource {
  return {
    id: person.id,
    familyId: person.familyId,
    name: person.displayName,
    living: person.deathDate === null,
  };
}

    Controller — HTTP in, HTTP out. It reads nothing from the request today, calls exactly one service, and picks the status code.

    server/src/controllers/people.controller.ts 
    import type { NextFunction, Request, Response } from "express";
import type { ApiResponse, PersonResource } from "../contracts.js";
import { listPeople } from "../services/people.service.js";
import { toPersonResource } from "../views/person.view.js";

export async function getPeople(
  _req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const people = await listPeople();
    const body: ApiResponse<PersonResource[]> = {
      data: people.map(toPersonResource),
    };

    res.status(200).json(body);
  } catch (error) {
    next(error);
  }
}

    Route — a URL and a verb bound to a controller. Nothing else belongs in this file, ever.

    server/src/routes/people.routes.ts 
    import { Router } from "express";
import { getPeople } from "../controllers/people.controller.js";

export const peopleRouter = Router();

peopleRouter.get("/", getPeople);
    server/src/routes/index.ts 
    import { Router } from "express";
import type { ApiResponse } from "../contracts.js";
import { peopleRouter } from "./people.routes.js";

export const apiRouter = Router();

// A liveness check has no business rules and touches nothing, so it does not
// deserve a controller. Inline is the honest choice here.
apiRouter.get("/health", (_req, res) => {
  const body: ApiResponse<{ status: "ok" }> = { data: { status: "ok" } };
  res.status(200).json(body);
});

apiRouter.use("/people", peopleRouter);

  6. The error handler, the app, and the port

    server/src/middlewares/errorHandler.ts 
    import type { ErrorRequestHandler } from "express";
import type { ApiErrorBody } from "../contracts.js";

// The last line of defence. Every error the application can produce ends
// here, so the client always receives the same shape.
export const errorHandler: ErrorRequestHandler = (error, _req, res, _next) => {
  const message = error instanceof Error ? error.message : "Unexpected error";
  const body: ApiErrorBody = { message };

  if (process.env.NODE_ENV !== "production") {
    console.error(error);
  }

  res.status(500).json(body);
};
    server/src/app.ts 
    import express from "express";
import { errorHandler } from "./middlewares/errorHandler.js";
import { apiRouter } from "./routes/index.js";

// Builds the application but does NOT listen. That separation is what lets a
// test exercise the whole stack without opening a port.
export function createApp() {
  const app = express();

  app.use(express.json());
  app.use("/api", apiRouter);
  app.use(errorHandler);

  return app;
}
    server/src/server.ts 
    import { createApp } from "./app.js";
import { env } from "./config/env.js";

createApp().listen(env.port, () => {
  console.log(`kinlink api listening on http://localhost:${env.port}`);
});

    The same seam as the server, minus the .js extensions. The client bundles with moduleResolution: bundler, which resolves extensionless imports itself.

    client/src/lib/api.ts 
    import type { ApiResponse, PersonResource } from "../contracts";

// Components call functions with names and types, never URLs.
export async function getPeople(): Promise<PersonResource[]> {
  const response = await fetch("/api/people");

  if (!response.ok) {
    throw new Error(`GET /api/people failed with status ${response.status}`);
  }

  const body = (await response.json()) as ApiResponse<PersonResource[]>;
  return body.data;
}
    Be suspicious of that as

    response.json() returns any — the compiler has no idea what the wire carries, and no amount of TypeScript can change that. The honest posture is: one place asserts the shape, and everything downstream trusts it. Lesson 03 replaces this single as with Zod validation at the boundary, which is where the assertion becomes a real check instead of a promise.

    client/src/App.tsx 
    import { useEffect, useState } from "react";
import type { PersonResource } from "./contracts";
import { getPeople } from "./lib/api";

export default function App() {
  const [people, setPeople] = useState<PersonResource[] | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    getPeople()
      .then(setPeople)
      .catch((cause: unknown) => {
        setError(cause instanceof Error ? cause.message : "Unknown error");
      });
  }, []);

  if (error) return <p role="alert">Failed to load: {error}</p>;
  if (!people) return <p>Loading…</p>;

  return (
    <main style={{ fontFamily: "system-ui, sans-serif", padding: "2rem" }}>
      <h1>KinLink</h1>
      <ul>
        {people.map((person) => (
          <li key={person.id}>
            {person.name} — {person.living ? "living" : "remembered"}
          </li>
        ))}
      </ul>
    </main>
  );
}

  8. Run the whole website

    npm run dev

    Two processes, one terminal: api in cyan, web in magenta. Open http://localhost:5173 and you should see both names.

    Now trace it by hand, out loud: the browser asked Vite for /api/people → Vite forwarded it to :4000 → Express matched the route → the controller called the service → the service called the model → the view shaped two resources → the controller sent JSON → React rendered it. If you can say that without looking, you already understand more of your own stack than most juniors do.

Verify

  • npm run typecheck passes for both tsconfigs.
  • curl http://localhost:4000/api/people returns the two people.

Break it on purpose

Predict the failure before you run it, then check whether you were right. This is where the architecture stops being a diagram.

  1. In shared/contracts/person.ts, rename name to fullName. Predict which files the compiler complains about, then run npm run typecheck. Did it catch both sides? Now revert it.
  2. In person.view.ts, add birthDate: person.birthDate to the resource. Which files must change for the browser to show it? Which files must not? Explain the shape of that answer out loud.
  3. Delete the proxy block from vite.config.ts and restart. Read the console error. Now say, in one sentence, what the proxy was doing for you.
  4. Move res.status(200).json(body) out of the controller and into the service. Make it work, then delete it and explain in two sentences why it was wrong even though it ran.
