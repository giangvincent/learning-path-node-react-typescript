Invitations: propose, accept, expire

Lesson 08 closed the last-owner guard with transfer — one atomic transition. But transfer requires the recipient to already be a member. How does someone get in? An invitation is a bearer credential for a membership that does not exist yet, and its protocol — propose → accept → expire — is the shape of every "ask to join" flow in KinLink.

Mission: ship KinLink Reference: Membership lifecycle Requires: Lesson 08
The win

A real invite flow: POST /api/invitations creates a single-use token (hashed, expiring), POST /api/invitations/:token/accept consumes it in one conditional write inside the same transaction as the membership row — and a race to claim the same token answers 409 to the loser. No second membership, no stale invite, no orphaned token.

The design lives in Reference 09 §2; today you write it as code and prove the race is handled. Read that section first if you want the full argument — the build below is its skeleton.

Build it

  1. The schema

    An invitation is a credential, not a URL. The token appears in a URL, which means browser history, email logs, and Referer headers — treat it like a password: the server keeps only a hash.

    prisma/schema.prisma (addition) 
    model Invitation {
  id        String    @id @default(uuid())
  familyId  String    @map("family_id")
  role      FamilyRole @default(member)   // never above the inviter's own
  email     String?                        // set = targeted; null = shareable
  tokenHash String  @unique @map("token_hash")
  expiresAt DateTime @map("expires_at")
  usedAt    DateTime? @map("used_at")
  createdBy String    @map("created_by")

  family Family @relation(fields: [familyId], references: [id], onDelete: Cascade)

  @@index([familyId])
  @@map("invitations")
}

    Three decisions in the schema:

    • role defaults to member. An admin invites a member; an owner can invite admin. The granted role must be ≤ the inviter's rank — enforced in the service, not the schema.
    • email is nullable. Set it for a targeted invite ("Minh, join the Nguyens"); leave it null for a shareable link anyone can use. The accept handler checks it anyway — the invitee's session must match.
    • tokenHash, not token. The raw token is generated by the server, sent to the client once, then never stored. A database leak does not hand out live invitations.

  2. Two endpoints

    Keep them separate. The invitee is often already a user — your aunt has an account, joining a second family. If accepting were part of registration, the feature only works for brand-new accounts.

    server/src/routes/invitation.routes.ts (new) 
    import { Router } from "express";
import { requireAuth, authContext } from "../middlewares/auth.js";
import { familyContext } from "../middlewares/family.js";
import { requireRole } from "../middlewares/role.js";
import {
  createInvitation,
  acceptInvitation,
} from "../services/invitation.service.js";

export const invitationRouter = Router({ mergeParams: true });

// Owner-only. The granted role must be ≤ the inviter's rank.
invitationRouter.post(
  "/",
  requireRole("owner"),
  async (req, res, next) => {
    const { family, membership } = familyContext(req);
    const { email, role } = req.body as { email?: string; role?: string };
    // ... validation, then createInvitation({ familyId: family.id, ... })
  },
);

// Authenticated. The session's user claims the token — userId never from body.
invitationRouter.post(
  "/:token/accept",
  requireAuth,
  async (req, res, next) => {
    const { userId } = authContext(req);
    const { token } = req.params as { token: string };
    // ... acceptInvitation(token, userId)
  },
);

    Mounting: the create route needs loadFamily (it reads familyContext), but accept must not — the invitee is not a member yet. Mount create under /api/families/:slug/invitations and accept at /api/invitations/:token/accept — one router cannot serve both correctly.

  3. The hard part: consuming the token once

    The race is on usedAt. Two clicks, two memberships — that's the wrong shape. One conditional write decides:

    server/src/services/invitation.service.ts (new) 
    import { createHash, randomBytes } from "node:crypto";
import { prisma } from "../config/database.js";
import type { Db } from "../models/db.js";
import { transact } from "../models/db.js";
import { ROLES, type Role } from "../models/membership.model.js";

export type InvitationResult =
  | { ok: true }
  | { ok: false; reason: "not-found" | "expired" | "used" | "already-member" };

/** SHA-256 hex. Raw token sent once, only the hash stored. */
function hashToken(token: string): string {
  return createHash("sha256").update(token).digest("hex");
}

const RANK = { member: 1, admin: 2, owner: 3 } as const satisfies Record<Role, number>;

/**
 * Mint an invite. Granted role must be <= inviter's rank, else the role
 * system is decorative (admin mints owner, promotes self by proxy).
 */
export async function createInvitation(input: {
  familyId: string;
  role: Role;
  inviterRole: Role;
  createdBy: string;
  email?: string | null;
}): Promise<{ token: string }> {
  if (!ROLES.includes(input.role)) throw new Error("Invalid role");
  if (RANK[input.role] > RANK[input.inviterRole]) throw new Error("Insufficient role");
  const token = randomBytes(32).toString("base64url");
  await prisma.invitation.create({
    data: {
      familyId: input.familyId,
      role: input.role,
      email: input.email ?? null,
      tokenHash: hashToken(token),
      expiresAt: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000),
      createdBy: input.createdBy,
    },
  });
  return { token };
}

/**
 * Accept an invitation in one transaction.
 *
 * The compare-and-set: updateMany with usedAt: null in the WHERE clause.
 * MySQL returns how many rows actually changed — count !== 1 means
 * someone else won, or it expired. The expiry check is in the same
 * statement, so a stale invite is indistinguishable from a used one
 * (the right amount of information for a stranger holding a stale link).
 */
export async function acceptInvitation(
  token: string,
  userId: string,
): Promise<InvitationResult> {
  return transact(async (tx: Db) => {
    // One conditional write decides the race.
    const claimed = await tx.invitation.updateMany({
      where: {
        tokenHash: hashToken(token),
        usedAt: null,
        expiresAt: { gt: new Date() },
      },
      data: { usedAt: new Date() },
    });

    if (claimed.count !== 1) {
      // Distinguish in logs, collapse on wire.
      return { ok: false, reason: "used" };
    }

    const invite = await tx.invitation.findFirst({
      where: { tokenHash: hashToken(token) },
    });
    if (!invite) return { ok: false, reason: "not-found" };

    // Already a member of this family? Claim was consumed; clean up.
    const existing = await tx.familyMember.findFirst({
      where: { userId: userId, familyId: invite.familyId },
    });
    if (existing) return { ok: false, reason: "already-member" };

    await tx.familyMember.create({
      data: {
        userId,
        familyId: invite.familyId,
        role: invite.role,
      },
    });

    return { ok: true };
  });
}
    Why compare-and-set, not check-then-write

    The wrong version: findInvite → check usedAt → createMembership → markUsed. Two clicks, two memberships — the race window is between the check and the mark. The right version: updateMany with usedAt: null in the WHERE clause is atomic — MySQL returns the number of rows it actually changed, and count !== 1 means you lost the race. Both writes share one transaction, so a failure cannot consume the token without creating the membership.

  4. The two authorisation rules

    1. You cannot mint authority you do not have. If an admin can create an invite with role: "owner", the role system is decorative — they promote themselves by proxy. The granted role must be ≤ the inviter's rank. Checked in the service, before the token is created.
    2. The acceptor's identity comes from the session, never the body. userId is never a parameter. An invite that names the user it creates is a privilege-escalation gadget. The session proves who is accepting.

Defend it

Why hash the token?

The token appears in a URL. URLs land in browser history, email provider logs, and Referer headers. OWASP's Forgot Password Cheat Sheet is the template: CSPRNG generation, length against brute force, linked to a record, invalidated after use, stored as a hash. The two extras for invite links: Referrer-Policy: no-referrer on the page the token lands on, and never build the invite URL from the Host header.

Why not put the token in the register call?

Registration creates your own family. An invitee is often already a user — your aunt has an account; she is joining a second family. If accepting were part of registration, the feature only works for brand-new accounts. Accept is also where "you're already in this family" (409) lives.

What does "expired" mean on the wire?

Same answer as "used" — 409 with reason: "used". An expired invite is indistinguishable from a used one, and that is the right amount of information for a stranger holding a stale link. The caller learns "this token doesn't work", not "it expired on Tuesday".

Break it on purpose

  1. Comment out the usedAt check in the updateMany where clause. Click accept twice with the same token. Predict the output first, then run. Two memberships for one invite — the compare-and-set is the guard, and removing it breaks the invariant instantly.
  2. Set expiresAt to the past. Accept should answer 409, not 200. The expiry check is inside the same statement — a stale invite is indistinguishable from a used one.
  3. Let an admin invite an owner. Remove the rank check in createInvitation. The role system is decorative — the admin promotes themselves by proxy.
  4. Pass userId in the accept body. An invite that names the user it creates is a privilege-escalation gadget. The session must be the only identity source.
