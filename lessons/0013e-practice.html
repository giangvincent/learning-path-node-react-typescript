Defend it

What does the client do when it has no session at all?

It shows the login form — not an error, and not an empty page. That is the whole content of the anonymous state, and it is why 401 must not be treated as a failure. The distinction is RFC 9110's: 401 means "no valid credentials", which is a perfectly ordinary thing to be. A client that routes 401 into "something went wrong" shows a broken-server message to a new visitor, and the visitor has no way to recover.

Where does the whoami fix belong in the commit history?

Its own commit, first. Three reasons, in order of importance: it repairs code that is already shipped, so it should be reviewable alone; the message must record why typecheck missed it, because that is the durable lesson and a diff cannot hold it; and git log/bisect should land on it directly rather than inside four hundred lines of new client code. The sequencing is lesson 05's rule — fix the contract before the consumer — and it is not bookkeeping here: the client calls whoami on every load.

How do you backfill created_at for real production rows?

You do not stamp them with the migration time. You split it into three steps — expand, backfill, contract — and the order is enforced by the engine rather than chosen for style: MySQL makes adding a nullable column an INSTANT, metadata-only operation, but making a column NOT NULL "rebuilds the table in place" and "fails if the column contains NULL values". So: add it nullable, write the true value in bounded batches, then tighten. Prisma cannot express the middle state, so you write the migration with --create-only and edit the SQL by hand — exactly the technique lesson 06 used for the backfill that had to run before DROP COLUMN. And when there is no source for the true value, expires_at - INTERVAL 7 DAY is an estimate to be labelled as one; NULL and an "unknown" label is braver than a fabricated timestamp, because a fabricated one survives review. Full detail, with the engine's own rules: Reference 11 §1.

Should the pending list paginate before it can ever be long?

No. The test is not "could this get long?" but "is the size bounded by construction?" Three real mechanisms bound this list: invites expire after seven days, the mint refuses a second pending invite for the same email, and one owner is looking at one family. So today the project has no cursor, no page envelope and no cap — and that is a decision, not an oversight. When it does earn one, it earns a keyset and not an OFFSET: the standard defines offset as sorting everything and dropping the first N rows, which is both slow and wrong, because a row inserted between two page fetches shifts the page and the reader sees a duplicate. The change that will force the issue is a filter the user drives — "show used invites too" — because that is what turns a bounded read into an unbounded one. Reference 11 §2–3.

Why does the client fetch the session instead of storing it?

The cookie is a pointer, not a claim; the server's store says who the session is. A client store holding loggedIn: true is a second source of truth that goes stale the moment the session expires or the store restarts — and MemoryStore restarts on every file save, which you have now felt. Fetch it, and let one write path (refresh) update it.

Why does GET /api/families skip loadFamily?

Because there is no :slug to resolve — answering "which families are mine?" is the route. loadFamily exists to turn a named family into a proven one; naming nothing, there is nothing to prove. The security property is unchanged and lives one layer down, in where: { userId }: no version of the query returns a family the caller has no membership in.

Why does an unmounted route answer in HTML, not JSON?

Because nothing in the API answered it at all. Cannot GET /api/families came from Express's built-in fall-through handler, which predates this API and speaks HTML. That is why the baseline in lesson 13a could not tell a client "this route does not exist yet" in the language every other endpoint uses — and why the same request answers 401 JSON once the route exists and the guard runs.

Break it on purpose

  1. Drop the where clause. Delete where: { userId } from findAllForUser and run both halves of Verify. Predicted: typecheck stays green — the userId parameter is merely unused, and no noUnusedParameters rule exists to notice. Measured: npm run typecheck → exit 0, and check:families → families returned: 7, roles: ["owner","member","owner","owner","owner","member","owner"], then Error: EXPECTED 2 families, got 7. Seven, because the dev database held four other memberships. That is a cross-tenant leak that the compiler was never able to see — the whole argument for the runtime half of every Verify block.
  2. Skip the view. Return res.json({ data: memberships }) from the controller. The response now carries each family's id — an internal identifier the client was never meant to hold. The "id" in row assertion in check:families is what would have caught it, and it is why the view is a whitelist rather than a filter.
  3. Mount the route above the guard. Move apiRouter.get("/families", getMyFamilies) to sit with /health, above apiRouter.use(requireAuth). Predict first: requireAuth never runs, so req.authenticatedUserId is undefined, authContext throws Route is missing requireAuth, and the error handler turns it into a 500. Loud, and loud is the point — the tripwire makes a misplaced route fail immediately instead of quietly serving another family's data.
  4. Let the slug be invented. In App.tsx, replace the family list with a hardcoded <Link to="/family/probe-1234/invites">. It renders perfectly for you and 404 Family not found for everyone else, because loadFamily collapses "no such family" and "not your family" into the same body. Guessing an identifier is the mistake; asking GET /api/families is the fix.
  5. Collapse 401 into anonymous. In useSession, replace the whole catch body with setState({ status: "anonymous" }). Now revert the whoami fix so it 500s again, and reload. The app shows a login form, the user types a correct password, and it does nothing — forever. A broken server now presents as a login loop, which is the single most confusing bug in this series' family.

Retrieval practice

Ask your teacher

Ask whether useSession should be replaced by TanStack Query now, and what exactly it buys beyond this hook. Ask what should happen when a session dies mid-use — the tab is open, the cookie expires, and some unrelated request answers 401. Ask why PersonResource still ships familyId when today's view drops the family id on the argument that a client should never hold an id it cannot safely hand back. And ask how "resend this invite" can work at all when the raw token was never stored.
