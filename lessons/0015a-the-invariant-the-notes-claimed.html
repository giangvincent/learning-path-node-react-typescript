The invariant the notes claimed

The notes say two invitations for the same email cannot be pending at once. The code says otherwise. Today, make that sentence true under concurrent requests, then make the database prove it on demand.

Mission: ship KinLink Requires: Lesson 14d References: 08 · 09 · 12 Practice: Lesson 15f
The win

An owner cannot create a second active invitation for the same database-equal non-null email in one family, even when two requests collide. The mint rule is enforced inside the transaction, after a family lock and a fresh role read; npm run check:mint forces and checks that race.

Warm-up: retrieve before rereading

Five minutes, from memory. In what order does the ownership service take the lock, read the fact, decide, and write? What does its check assert while the second transaction waits? Compare with Reference 08 only after you have answered.

  2. State exactly what “one per email” means

    For this build, the rule is: within one family, at most one unexpired, unclaimed invitation with the same non-null email value. A shareable invitation (email: null) has no recipient to deduplicate. “Pending” currently means usedAt: null and expiresAt > now; revocation is not in this sitting.

    The lookup uses the database's email comparison rules; this lesson adds no case-folding or whitespace normalization. Decide canonical email handling at the request boundary in a separate change, rather than implying this query normalizes addresses.

  4. Make mint one serialized decision

    The route's owner check is necessary, but it ran before this write. An owner can be demoted after the request passes that middleware. Re-read the membership inside the lock, then check for a pending duplicate, then insert — all in one transaction. Update createInvitation in the service to this shape:

    server/src/services/invitation.service.ts (mint changes) 
    import * as membershipModel from "../models/membership.model.js";

export type CreateInvitationResult =
  | { ok: true; token: string }
  | {
      ok: false;
      reason: "not-owner" | "insufficient-role" | "duplicate-email";
    };

export interface MintWindow {
  afterDuplicateCheck?: () => Promise<void>;
}

export async function createInvitation(
  input: {
    familyId: string;
    inviterMembershipId: string;
    role: Role;
    email?: string | null;
  },
  window: MintWindow = {},
): Promise<CreateInvitationResult> {
  if (!ROLES.includes(input.role)) throw new Error("Invalid role");

  return transact(async (tx) => {
    await membershipModel.lockFamily(input.familyId, tx);

    const inviter = await membershipModel.findByFamily(
      input.familyId,
      input.inviterMembershipId,
      tx,
    );
    if (!inviter || inviter.role !== "owner") {
      return { ok: false, reason: "not-owner" };
    }
    if (RANK[input.role] > RANK[inviter.role]) {
      return { ok: false, reason: "insufficient-role" };
    }

    const email = input.email ?? null;
    if (
      email !== null &&
      (await invitationModel.findPendingByEmail(input.familyId, email, tx))
    ) {
      return { ok: false, reason: "duplicate-email" };
    }
    await window.afterDuplicateCheck?.();

    const token = randomBytes(32).toString("base64url");
    await invitationModel.createInvitation(
      {
        familyId: input.familyId,
        role: input.role,
        email,
        tokenHash: hashToken(token),
        expiresAt: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000),
        createdBy: inviter.userId,
      },
      tx,
    );
    return { ok: true, token };
  });
}

    Keep InvitationResult for acceptance; mint has a different result type. Add the membership-model namespace import and remove the service's direct prisma import. Keep randomBytes, createHash, hashToken, RANK, ROLES, and transact. The membership id and creator id now come from the proven family context and locked database read — not a stale role snapshot or caller-supplied user id.

    Why the hook is here

    afterDuplicateCheck is an inert-by-default seam. The check parks the first transaction after its read, then proves the second cannot reach the same point while the lock is held. Without the hook, a race test would hope the scheduler hits the vulnerable gap; with it, the check chooses the interleaving.

  5. Pass the membership and render each refusal honestly

    In invitation.routes.ts, destructure { family, membership } from familyContext(req). Remove the old Insufficient role catch branch: role refusals are now values returned by the service. Keep the outer try/catch that forwards unexpected failures to next(e). Handle the result before sending success:

const { email, role } = req.body as { email?: string; role?: string };
if (role !== "member" && role !== "admin") {

  familyId: family.id,
  inviterMembershipId: membership.id,
  role,
  email: email ?? null,
});

if (!result.ok) {
  const status = result.reason === "duplicate-email" ? 409 : 403;
  const message =
    result.reason === "duplicate-email"

    409 means “not in this state yet”: the existing invite must be accepted, expire, or be revoked before another is minted. 403 means the caller is authenticated but no longer has mint authority. The client can distinguish them using ApiError.status; neither is a session-ending 401.

  6. Restore the proof: force the collision

    Add this complete server/src/scripts/checkMint.ts. It uses the same gate technique as checkOwnership.ts: the first mint parks after finding no duplicate, and the second must remain blocked before it can make that same observation.

    server/src/scripts/checkMint.ts (new) 
    import "dotenv/config";
import { randomUUID } from "node:crypto";
import { prisma } from "../config/database.js";
import { createInvitation } from "../services/invitation.service.js";

function gate(): {
  afterDuplicateCheck: () => Promise<void>;
  arrived: Promise<void>;
  open: () => void;
} {
  let arrive!: () => void;
  let open!: () => void;
  const arrived = new Promise<void>((resolve) => (arrive = resolve));
  const opened = new Promise<void>((resolve) => (open = resolve));
  return {
    afterDuplicateCheck: async () => {
      arrive();
      await opened;
    },
    arrived,
    open: () => open(),
  };
}

async function main(): Promise<void> {
  const slug = `mint-${randomUUID().slice(0, 8)}`;
  const email = `${slug}@probe.invalid`;
  const family = await prisma.family.create({
    data: { slug, name: "Mint probe" },
  });
  const user = await prisma.user.create({
    data: { email, passwordHash: "probe" },
  });

  try {
    const membership = await prisma.familyMember.create({
      data: { userId: user.id, familyId: family.id, role: "owner" },
    });
    const firstGate = gate();
    const secondGate = gate();
    const input = {
      familyId: family.id,
      inviterMembershipId: membership.id,
      role: "member" as const,
      email: "same@probe.invalid",
    };

    const first = createInvitation(input, {
      afterDuplicateCheck: firstGate.afterDuplicateCheck,
    });
    await firstGate.arrived;

    const second = createInvitation(input, {
      afterDuplicateCheck: secondGate.afterDuplicateCheck,
    });
    let timer: ReturnType<typeof setTimeout>;
    const secondReachedCheck = await Promise.race([
      secondGate.arrived.then(() => true),
      new Promise<boolean>((resolve) => {
        timer = setTimeout(() => resolve(false), 400);
      }),
    ]);
    clearTimeout(timer!);

    firstGate.open();
    secondGate.open();
    const results = await Promise.all([first, second]);
    const pending = await prisma.invitation.count({
      where: {
        familyId: family.id,
        email: input.email,
        usedAt: null,
        expiresAt: { gt: new Date() },
      },
    });
    const successes = results.filter((result) => result.ok).length;
    const duplicates = results.filter(
      (result) => !result.ok && result.reason === "duplicate-email",
    ).length;

    console.log(`second reached check while locked: ${secondReachedCheck}`);
    console.log(`successful mints: ${successes}`);
    console.log(`duplicate refusals: ${duplicates}`);
    console.log(`pending matching rows: ${pending}`);

    if (secondReachedCheck) {
      throw new Error("RACE NOT SERIALIZED: second mint passed the family lock");
    }
    if (successes !== 1 || duplicates !== 1 || pending !== 1) {
      throw new Error(
        `INVARIANT BROKEN: successes=${successes}, duplicates=${duplicates}, rows=${pending}`,
      );
    }

    await prisma.familyMember.update({
      where: { id: membership.id },
      data: { role: "member" },
    });
    const demoted = await createInvitation({
      ...input,
      email: "after-demotion@probe.invalid",
    });
    if (demoted.ok || demoted.reason !== "not-owner") {
      throw new Error("STALE AUTHORITY: demoted inviter minted an invitation");
    }

    console.log("\nmint invariant held; demoted inviter refused");
  } finally {
    await prisma.family.delete({ where: { id: family.id } });
    await prisma.user.delete({ where: { id: user.id } });
    await prisma.$disconnect();
  }
}

main().catch((error: unknown) => {
  console.error(error);
  process.exitCode = 1;
});

    Add "check:mint": "tsx server/src/scripts/checkMint.ts" to the root manifest. This asserts both the forced race and the transaction's fresh authority check; fixture cleanup runs even when an assertion fails.

The notes were not wrong because of a typo

They described a transaction, lock, duplicate refusal, and check as finished facts. The service had none of them and the manifest had no check:mint. A design recorded in past tense is still only a design until its code exists and its proof runs. The debt was the missing invariant and the missing evidence; this build closes both.

Decisions carried into the next sittings

  • revokedAt comes first. Give the nullable column its own migration before writing resend; existing rows truthfully remain NULL. Resend later updates the one pending definition to also require revokedAt: null.
  • AcceptPage should use a named function in lib/api.ts. It is the only live component that bypasses the transport. InviteDialog also calls fetch, but it is dead and posts to a nonexistent mint route; delete or rebuild it as the client work lands.
  • Do not collapse every “no” into the same UI state. 401 means missing/invalid authentication; a session-carrying request announces it app-wide, while login's credential verdict and AcceptPage's sign-in requirement are local exceptions. 403 means authenticated but not permitted; keep the session and show a local permission response. The server's intentional 404/409 collapses remain collapsed in the client.
