Lesson 02 · Week 2 · about three hours

Make the Model real: MySQL 8 + Prisma

Swap the array in person.model.ts for a real MySQL database — and prove the seam held by changing nothing above it.

Mission: ship KinLink Reference: Prisma data layer Requires: Lesson 01
The win

MySQL 8 runs in a container, Prisma owns the schema, and the same /api/people response now comes out of a real table. The only file you edit above the database is person.model.ts — the service, the view, the controller and the route stay byte-for-byte identical, and the JSON still says name instead of display_name. That is the architecture paying you back.

Why the layer boundary is about to be tested

In lesson 01 you built six layers and took it on faith that they were worth the ceremony. Today is the test. You are replacing the entire storage mechanism — no array, no in-memory anything, a different data type for dates, a different naming convention — and the honest measure of the design is how many files have to change.

The answer should be one. If it turns out to be six, we learn that too, and we fix it. Both outcomes are useful; that is the point of doing this early rather than in week six.

Before you start

Lesson 01 must actually run: npm run dev serving /api/people from the in-memory array. If it doesn't, stop and tell me — a lesson that assumes a broken foundation wastes more time than it saves.

Build it

  1. Start MySQL 8 in a container

    Docker is already installed and running on your machine, and port 3306 is free. A container gives you a disposable, reproducible database — no system install to fight, no version drift, and docker compose down -v resets everything when a migration goes wrong.

    docker-compose.yml 
    services:
  mysql:
    image: mysql:8.0
    container_name: kinlink-mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: kinlink
      MYSQL_USER: kinlink
      MYSQL_PASSWORD: kinlink
    ports:
      - "3306:3306"
    volumes:
      - kinlink-mysql-data:/var/lib/mysql

volumes:
  kinlink-mysql-data:

    mysql:8.0 is pinned rather than mysql:8 on purpose: the floating tag can move between minor versions and silently change defaults under you. When your database is the thing holding the family's history, you choose the version and you write it down. 

    docker compose up -d
docker compose ps

    Wait until STATUS reads healthy — starting means the server is still initialising and Prisma will fail if you jump the gun.

  2. Install Prisma 7 — pinned, not latest

    Here is a real decision you are making right now, and it is worth understanding because it will come up in interviews.

    Look before you install latest

    At the time of writing, prisma@latest resolves to 8.0.0-rc.19 — a release candidate. Prisma 8 is a rewrite that changes how schemas are authored and how migrations are planned. Building KinLink on an RC means your foundation can change under you mid-project, and the docs you find online will describe a different API than the one you have.

    So we pin 7.10.0 across every Prisma package. Not because newer is worse, but because the version you choose is a decision, and an unexamined latest is how projects die. 

    npm install @prisma/client@7.10.0 @prisma/adapter-mariadb@7.10.0 dotenv
npm install -D prisma@7.10.0

    Three packages, one version number. Prisma's CLI, client and driver adapter are released in lockstep; mixing versions produces confusing type errors that look like your fault and are not.

    The adapter needs explaining, because it is new in this generation:

    Package What it is
    prisma The CLI: init, migrate, generate, studio.
    @prisma/client The query API you will call from the model layer.
    @prisma/adapter-mariadb The driver that actually speaks MySQL's wire protocol. Prisma 7 talks to MySQL through this adapter instead of a built-in engine.
    .env — and note it is already gitignored 
    DATABASE_URL="mysql://kinlink:kinlink@127.0.0.1:3306/kinlink"
DATABASE_HOST="127.0.0.1"
DATABASE_PORT=3306
DATABASE_USER="kinlink"
DATABASE_PASSWORD="kinlink"
DATABASE_NAME="kinlink"

    DATABASE_URL is for the CLI, the discrete variables are for the runtime adapter. Yes, that is the same information written twice, and yes, it is annoying — it is a rough edge in this Prisma generation, not a pattern worth copying. The variable names are the pattern worth copying: every secret comes from the environment, and the environment is gitignored.

  3. Initialise Prisma and write the schema

    npx prisma init --datasource-provider mysql --output ../server/generated/prisma

    This creates prisma/schema.prisma, a prisma7.config.ts, and generates the client into server/generated/prisma. Confirm where the generated folder actually landed — the --output path resolves relative to the schema file, not to your shell, which surprises people. If it went somewhere else, fix the output line in the schema.

    prisma/schema.prisma 
    generator client {
  provider = "prisma-client"
  output   = "../server/generated/prisma"
}

datasource db {
  provider = "mysql"
}

enum Gender {
  male
  female
  other
  unknown
}

model Family {
  id        String   @id @default(uuid())
  slug      String   @unique
  name      String
  createdAt DateTime @default(now()) @map("created_at")

  people Person[]

  @@map("families")
}

model Person {
  id          String    @id @default(uuid())
  familyId    String    @map("family_id")
  displayName String    @map("display_name")
  gender      Gender
  birthDate   DateTime? @map("birth_date") @db.Date
  deathDate   DateTime? @map("death_date") @db.Date
  createdAt   DateTime  @default(now()) @map("created_at")
  updatedAt   DateTime  @updatedAt @map("updated_at")

  family Family @relation(fields: [familyId], references: [id], onDelete: Cascade)

  @@index([familyId])
  @@map("people")
}

    Four decisions in that file are worth pausing on.

    @@map and @map. Prisma fields are camelCase; database columns are snake_case. Mapping between them means each side follows its own convention instead of one convention losing. Your code reads displayName, the table says display_name, and the mapping is declared once, here.

    uuid() not autoincrement(). Sequential integers leak information: /api/people/47 tells an attacker you have at least 47 people and invites them to try 48. UUIDs are opaque. For a private family platform this matters.

    onDelete: Cascade. Delete a family, its people go with it. Without this, MySQL refuses the delete and leaves you with rows pointing at nothing. Decide the rule explicitly at design time — every relation needs an answer to "what happens when the parent goes away".

    @@index([familyId]). Every single query in KinLink will filter by family. Without an index, MySQL scans the whole table for each one. This is the first performance decision in the project, and it costs one line.

    A note on names

    Your spec eventually wants given_name, middle_name, surname and display_name. This migration deliberately keeps a single display_name column so that exactly one file has to change today. Splitting the name is a real change, and it will be made the right way — as its own migration, when the People feature needs it. That is how schemas are supposed to evolve.

  4. Run the first migration

    npx prisma migrate dev --name add_family_and_person

    Prisma diffs your schema against the database, writes the SQL it intends to run, applies it, and regenerates the client. Read the migration file it produced before moving on:

    prisma/migrations/<timestamp>_add_family_and_person/migration.sql 
    CREATE TABLE `families` (...);
CREATE TABLE `people` (...);
CREATE INDEX `people_family_id_idx` ON `people`(`family_id`);
ALTER TABLE `people` ADD CONSTRAINT ... FOREIGN KEY (`family_id`) ...

    A migration is not a magic sync. It is a file of SQL, committed to git, that runs once and in order. That is why you can hand the repo to a teammate or a server and get the identical schema. Never edit a migration that has already run anywhere but your own machine — write a new one instead.

    Want to see the tables with your own eyes?

    docker compose exec mysql mysql -ukinlink -pkinlink kinlink -e "DESCRIBE people;"
npx prisma studio

  5. The client, created once

    server/src/config/database.ts 
    import "dotenv/config";
import { PrismaMariaDb } from "@prisma/adapter-mariadb";
import { PrismaClient } from "../../generated/prisma/client.js";

const adapter = new PrismaMariaDb({
  host: process.env.DATABASE_HOST ?? "127.0.0.1",
  port: Number(process.env.DATABASE_PORT ?? 3306),
  user: process.env.DATABASE_USER,
  password: process.env.DATABASE_PASSWORD,
  database: process.env.DATABASE_NAME,
  connectionLimit: 5,
});

export const prisma = new PrismaClient({ adapter });

    One client, one connection pool, created at import time and shared. Creating a new PrismaClient() inside a request handler is a classic production bug: it opens a fresh pool per request until MySQL refuses new connections. connectionLimit: 5 is explicit for the same reason — you want to know your ceiling, not discover it during an outage.

  6. The one file that changes

    Here it is. This is the whole migration as far as your application code is concerned.

    server/src/models/person.model.ts 
    import { prisma } from "../config/database.js";
import type { Person as PrismaPerson } from "../../generated/prisma/client.js";

// The model layer re-exports the ORM's type, so no layer above it has to know
// that Prisma exists. If we swap Prisma for something else in two years, this
// import and these query bodies are the entire blast radius.
export type Person = PrismaPerson;

export async function findAll(): Promise<Person[]> {
  return prisma.person.findMany({ orderBy: { createdAt: "asc" } });
}

    The hand-written interface Person from lesson 01 is gone. That is not laziness — it is the better choice. A type you write by hand can drift from the table; a type the ORM generates from the schema cannot. The model layer's job is to be the only place that trade-off is visible.

    If the import fails

    Open server/generated/prisma/client.ts and look at what it actually exports. Generated code is documentation you are allowed to read, and the export surface of a generated client changes between versions. If the model type has a different name, use that name — and tell me, so I can fix this lesson.

    Now check what did not change: people.service.ts, person.view.ts, people.controller.ts, people.routes.ts, shared/contracts/. Not a character. The view still maps displayName to name, so the browser still receives name even though the column is display_name.

  7. Seed some data

    A hand-written script rather than Prisma's built-in seeding, because the built-in configuration moves between versions and this teaches you more.

    server/src/scripts/seed.ts 
    import "dotenv/config";
import { prisma } from "../config/database.js";

async function main(): Promise<void> {
  const family = await prisma.family.upsert({
    where: { slug: "nguyen" },
    update: {},
    create: { slug: "nguyen", name: "Nguyễn" },
  });

  await prisma.person.deleteMany({ where: { familyId: family.id } });

  await prisma.person.createMany({
    data: [
      {
        familyId: family.id,
        displayName: "Nguyễn Văn An",
        gender: "male",
        birthDate: new Date("1948-03-02"),
        deathDate: null,
      },
      {
        familyId: family.id,
        displayName: "Trần Thị Bình",
        gender: "female",
        birthDate: new Date("1952-07-19"),
        deathDate: null,
      },
    ],
  });

  console.log(`seeded family "${family.slug}" with ${await prisma.person.count()} people`);
}

main()
  .catch((error: unknown) => {
    console.error(error);
    process.exitCode = 1;
  })
  .finally(() => prisma.$disconnect());

    Note upsert for the family and a delete-then-insert for the people. A seed script must be safe to run twice — you will run it dozens of times, and a script that duplicates data every run becomes a script nobody trusts.

    Add the convenience scripts, then run it:

    package.json (scripts, excerpt) 
    "db:up": "docker compose up -d",
"db:down": "docker compose down",
"db:migrate": "prisma migrate dev",
"db:studio": "prisma studio",
"db:seed": "tsx server/src/scripts/seed.ts"
    npm run db:seed
npm run dev

    Refresh localhost:5173. Same two names. Nothing upstream of the model knows anything changed.

  8. Commit

    printf 'node_modules\ndist\n.env\nserver/generated\n' > .gitignore
git add -A
git commit -m "Serve people from MySQL via Prisma, confined to the model layer"
    Generated code is not committed

    server/generated is gitignored and rebuilt by prisma generate. The prisma/migrations folder is the opposite — it is the most important thing in the repo and must always be committed. Generated output is reproducible; migration history is not.

Verify

  • docker compose ps shows MySQL as healthy.
  • git status shows exactly one modified application file: server/src/models/person.model.ts.
  • npm run typecheck passes.
  • curl http://localhost:4000/api/people returns both people.
  • The JSON contains name, not displayName or display_name.

Break it on purpose

  1. Delete a person with raw SQL and refresh the browser — no code change, no restart: 
    docker compose exec mysql mysql -ukinlink -pkinlink kinlink \
  -e "DELETE FROM people WHERE display_name = 'Trần Thị Bình';"
    Then run npm run db:seed to put them back. Say out loud what just happened: the database is the source of truth, and your server holds no state.
  2. Change DATABASE_PASSWORD in .env to something wrong, restart, and call the endpoint. Read what the client receives. Now answer: should that message reach the browser in production? If your answer is no, go and fix errorHandler.ts so the message is generic unless NODE_ENV is development. You just found a real information-disclosure bug, in your own code, in week two.
  3. Add a notes column to Person, run npx prisma migrate dev --name add_notes, read the generated SQL, then delete the column and migrate again. Notice that adding a nullable column is safe and painless, and think about why adding a required one to a table with rows is not.
  4. Do not fix this, just write the answer down. findAll() returns every person in the database — every family's people. That is a data-isolation bug, and in KinLink it is the most serious class of bug there is. Write two sentences: what is the fix, and why does the decision about which family belongs in the service rather than the model? Bring those sentences to me; they are the first half of week three.
