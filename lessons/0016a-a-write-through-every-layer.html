A write through every layer

Every route in KinLink has been a read. Today the server writes a row for the first time — and it does so through the same six layers the reads use, with the same rule: the family comes from the proven request context, never from the body.

Mission: ship KinLink Requires: Lesson 15f References: 02 · 04 · 12 · 13 Practice: Lesson 16f
The win

POST /api/families/:slug/people creates a person in the caller's family and answers 201 with the resource. A bad body is a 400 with a sentence explaining it; a family the caller does not belong to is a 404; an unauthenticated caller is a 401. npm run check:people proves the row lands in the right family and nowhere else.

  2. State the shape on both sides of the wire

    The contract is the one file both programs compile against. Today it grows two types: what a client may send to create a person, and what a client may send to edit one. The second is the first, all fields optional — an edit sends only what changed.

    shared/contracts/person.ts (additions) 
    /** The body of a create: every field the client may set, and nothing else. */
export interface CreatePersonRequest {
  name: string;
  gender: Gender;
  birthDate?: string | null;
  deathDate?: string | null;
}

/** A partial edit: send only the fields that changed. */
export type UpdatePersonRequest = Partial<CreatePersonRequest>;

    Note what is not here: no familyId, no id. The client cannot ask for a person to live somewhere else, because the type gives it no way to say so.

    Add the two names to the server's window on the contract, so the layers below can import them from one place:

  CreatePersonRequest,
  Gender,
  PersonResource,
  UpdatePersonRequest,

  3. The model owns the query — and the scope

    Three writes join findByFamily. Each takes familyId as a required argument, and each takes a Db so a service could compose them in one transaction. The interesting one is update: a Prisma update must name a unique row, so it cannot filter on familyId at the same time. updateMany can, and its count is how the caller learns a person was not theirs.

    server/src/models/person.model.ts 
    import { prisma } from "../config/database.js";
import type { Db } from "./db.js";
import type {
  Gender,
  Person as PrismaPerson,
} from "../../generated/prisma/client.js";

export type Person = PrismaPerson;

/** The columns a create or an edit is allowed to set. */
export interface PersonInput {
  displayName: string;
  gender: Gender;
  birthDate?: Date | null;
  deathDate?: Date | null;
}

// familyId is a required argument. There is no way to call this function
// without saying whose rows you want, which is what makes the isolation bug
// impossible to introduce by accident.
export async function findByFamily(
  familyId: string,
  database: Db = prisma,
): Promise<Person[]> {
  return database.person.findMany({
    where: { familyId },
    orderBy: { createdAt: "asc" },
  });
}

export async function create(
  familyId: string,
  input: PersonInput,
  database: Db = prisma,
): Promise<Person> {
  return database.person.create({
    data: {
      familyId,
      displayName: input.displayName,
      gender: input.gender,
      birthDate: input.birthDate ?? null,
      deathDate: input.deathDate ?? null,
    },
  });
}

/**
 * A scoped update. `updateMany` filters on BOTH id and familyId, so a person
 * from another family matches no row -- and `count` is how the caller learns
 * there was nothing to change, rather than a 500 from an unscoped `update`.
 */
export async function update(
  id: string,
  familyId: string,
  patch: Partial<PersonInput>,
  database: Db = prisma,
): Promise<Person | null> {
  const { count } = await database.person.updateMany({
    where: { id, familyId },
    data: patch,
  });
  if (count === 0) return null;
  return database.person.findUnique({ where: { id } });
}

export async function remove(
  id: string,
  familyId: string,
  database: Db = prisma,
): Promise<boolean> {
  const { count } = await database.person.deleteMany({ where: { id, familyId } });
  return count > 0;
}

  4. The service owns the rule — including the wire's dates

    The database stores a Date; the wire carries a "YYYY-MM-DD" string. Somebody has to translate, and it is not the model (which should not know about JSON) and not the controller (which owns HTTP, not domain shape). It is the service.

    server/src/services/people.service.ts 
    import type { Gender } from "../contracts.js";
import * as personModel from "../models/person.model.js";
import type { Person, PersonInput } from "../models/person.model.js";

/** Forward the call through to the model. The model enforces scoping. */
export async function listPeople(familyId: string): Promise<Person[]> {
  return personModel.findByFamily(familyId);
}

/** A create or an edit as the wire describes it: dates are ISO strings or null. */
export interface NewPerson {
  name: string;
  gender: Gender;
  birthDate?: string | null;
  deathDate?: string | null;
}

export async function addPerson(
  familyId: string,
  input: NewPerson,
): Promise<Person> {
  return personModel.create(familyId, {
    displayName: input.name,
    gender: input.gender,
    birthDate: toDate(input.birthDate),
    deathDate: toDate(input.deathDate),
  });
}

export async function editPerson(
  familyId: string,
  personId: string,
  patch: Partial<NewPerson>,
): Promise<Person | null> {
  const changes: Partial<PersonInput> = {};
  if (patch.name !== undefined) changes.displayName = patch.name;
  if (patch.gender !== undefined) changes.gender = patch.gender;
  // `!== undefined` and not truthiness: sending null is how a date is cleared.
  if (patch.birthDate !== undefined) changes.birthDate = toDate(patch.birthDate);
  if (patch.deathDate !== undefined) changes.deathDate = toDate(patch.deathDate);

  return personModel.update(personId, familyId, changes);
}

export async function removePerson(
  familyId: string,
  personId: string,
): Promise<boolean> {
  return personModel.remove(personId, familyId);
}

/** An ISO date string from the wire as a `Date`, or null for "no date". */
function toDate(value: string | null | undefined): Date | null {
  return value == null || value === "" ? null : new Date(value);
}

  5. Validate at the boundary, then call exactly one service

    A request body is untrusted input from outside the program. The controller is where it stops being unknown and becomes a typed request — so the validation lives here, above the call, and a failure never reaches the database as a 500.

    server/src/controllers/people.controller.ts (top of file) 
    import type { NextFunction, Request, Response } from "express";
import type {
  ApiResponse,
  CreatePersonRequest,
  Gender,
  PersonResource,
  UpdatePersonRequest,
} from "../contracts.js";
import { familyContext } from "../middlewares/family.js";
import {
  addPerson,
  editPerson,
  listPeople,
  removePerson,
} from "../services/people.service.js";
import { toPersonResource } from "../views/person.view.js";

const GENDERS = ["male", "female", "other", "unknown"] as const;

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === "object" && value !== null;
}

function isGender(value: unknown): value is Gender {
  return typeof value === "string" && (GENDERS as readonly string[]).includes(value);
}

/** A `YYYY-MM-DD` string, or a null/"" that means "no date". */
function parseDate(
  value: unknown,
): { ok: true; value: string | null } | { ok: false } {
  if (value === undefined || value === null || value === "") {
    return { ok: true, value: null };
  }
  if (typeof value !== "string" || Number.isNaN(Date.parse(value))) {
    return { ok: false };
  }
  return { ok: true, value };
}

/** Validate a create body, or name the first thing wrong with it. */
function parseCreate(
  body: unknown,
): { input: CreatePersonRequest } | { error: string } {
  if (!isRecord(body)) return { error: "Body must be a JSON object" };

  const { name, gender } = body;
  if (typeof name !== "string" || name.trim() === "" || name.trim().length > 200) {
    return { error: "name must be a non-empty string of at most 200 characters" };
  }
  if (!isGender(gender)) {
    return { error: `gender must be one of ${GENDERS.join(", ")}` };
  }
  const birthDate = parseDate(body.birthDate);
  const deathDate = parseDate(body.deathDate);
  if (!birthDate.ok || !deathDate.ok) {
    return { error: "birthDate and deathDate must be ISO dates or null" };
  }
  return {
    input: {
      name: name.trim(),
      gender,
      birthDate: birthDate.value,
      deathDate: deathDate.value,
    },
  };
}

/** Validate a partial edit: only the fields present are checked. */
function parseUpdate(
  body: unknown,
): { patch: UpdatePersonRequest } | { error: string } {
  if (!isRecord(body)) return { error: "Body must be a JSON object" };

  const patch: UpdatePersonRequest = {};
  if (body.name !== undefined) {
    if (
      typeof body.name !== "string" ||
      body.name.trim() === "" ||
      body.name.trim().length > 200
    ) {
      return { error: "name must be a non-empty string of at most 200 characters" };
    }
    patch.name = body.name.trim();
  }
  if (body.gender !== undefined) {
    if (!isGender(body.gender)) {
      return { error: `gender must be one of ${GENDERS.join(", ")}` };
    }
    patch.gender = body.gender;
  }
  for (const key of ["birthDate", "deathDate"] as const) {
    const value = body[key];
    if (value === undefined) continue;
    const parsed = parseDate(value);
    if (!parsed.ok) return { error: `${key} must be an ISO date or null` };
    patch[key] = parsed.value;
  }
  if (Object.keys(patch).length === 0) {
    return { error: "No editable fields were provided" };
  }
  return { patch };
}

    Then the handlers. Read the first one as the rule for the other two: take the family from familyContext — the fact the middleware already proved — call one service, choose a status.

    server/src/controllers/people.controller.ts (handlers) 
    export async function getFamilyPeople(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    // The controller does not name a family and does not read the session. It asks
    // for the family the request was authorised against -- already proven.
    const { family } = familyContext(req);
    const people = await listPeople(family.id);

    const body: ApiResponse<PersonResource[]> = {
      data: people.map(toPersonResource),
    };

    res.status(200).json(body);
  } catch (error) {
    next(error);
  }
}

export async function createFamilyPerson(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const { family } = familyContext(req);
    const parsed = parseCreate(req.body);
    if ("error" in parsed) {
      res.status(400).json({ message: parsed.error });
      return;
    }

    const person = await addPerson(family.id, parsed.input);

    const body: ApiResponse<PersonResource> = { data: toPersonResource(person) };
    res.status(201).json(body);
  } catch (error) {
    next(error);
  }
}

export async function updateFamilyPerson(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const { family } = familyContext(req);
    // Express 5: a param is `string | string[] | undefined` until narrowed.
    const { personId } = req.params;
    const parsed = parseUpdate(req.body);
    if ("error" in parsed) {
      res.status(400).json({ message: parsed.error });
      return;
    }
    if (typeof personId !== "string") {
      res.status(404).json({ message: "Person not found" });
      return;
    }

    const person = await editPerson(family.id, personId, parsed.patch);
    if (person === null) {
      res.status(404).json({ message: "Person not found" });
      return;
    }

    const body: ApiResponse<PersonResource> = { data: toPersonResource(person) };
    res.status(200).json(body);
  } catch (error) {
    next(error);
  }
}

export async function deleteFamilyPerson(
  req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const { family } = familyContext(req);
    const { personId } = req.params;
    if (typeof personId !== "string") {
      res.status(404).json({ message: "Person not found" });
      return;
    }

    const removed = await removePerson(family.id, personId);
    if (!removed) {
      res.status(404).json({ message: "Person not found" });
      return;
    }

    res.status(204).end();
  } catch (error) {
    next(error);
  }
}

  6. Mount the routes — and notice the check you do not write

    The router is already mounted behind loadFamily, so every handler here runs only after the caller has been proved a member of :slug. That proof is the authorisation. Writing requireRole("member") would be a check that cannot fail — every member is at least a member — so it is left out.

    server/src/routes/family.routes.ts (the people band) 
    familyRouter.get("/people", getFamilyPeople);

// loadFamily proved membership, so no requireRole here: a check that can never
// fail is not a check, it is decoration.
familyRouter.post("/people", createFamilyPerson);
familyRouter.patch("/people/:personId", updateFamilyPerson);
familyRouter.delete("/people/:personId", deleteFamilyPerson);

  7. Make the claim runnable

    A write path is only as good as its scoping, and scoping is exactly the thing a mocked test cannot check. Like the other checks in scripts/, this one talks to a real database, asserts, and exits non-zero when the claim is false.

    server/src/scripts/checkPeople.ts (new) 
    import "dotenv/config";
import { randomUUID } from "node:crypto";
import { prisma } from "../config/database.js";
import * as personModel from "../models/person.model.js";
import { addPerson, listPeople } from "../services/people.service.js";
import { toPersonResource } from "../views/person.view.js";

// Two families. A person written into one must be readable in that one and
// invisible in the other, and the same familyId scope that protects the read
// must protect the write.
async function main(): Promise<void> {
  const suffix = randomUUID().slice(0, 8);
  const mine = await prisma.family.create({
    data: { slug: `probe-people-${suffix}`, name: "People probe" },
  });
  const theirs = await prisma.family.create({
    data: { slug: `probe-elsewhere-${suffix}`, name: "Elsewhere probe" },
  });

  try {
    await addPerson(mine.id, {
      name: "Nguyễn Văn A",
      gender: "male",
      birthDate: "1980-04-12",
      deathDate: null,
    });

    const resources = (await listPeople(mine.id)).map(toPersonResource);
    const elsewhere = await listPeople(theirs.id);
    const first = resources[0];

    console.log(`people in the family:  ${resources.length}`);
    console.log(`name:                  ${JSON.stringify(first?.name)}`);
    console.log(`living (no death date): ${first?.living}`);

    if (resources.length !== 1) {
      throw new Error(`EXPECTED 1 person, got ${resources.length}`);
    }
    if (!first) throw new Error("MISSING: the created person was not listed");
    if (first.name !== "Nguyễn Văn A") {
      throw new Error("NAME: the display name did not round-trip");
    }
    if (!first.living) {
      throw new Error("LIVING: a person with no death date must be living");
    }
    if (elsewhere.length !== 0) {
      throw new Error("LEAK: another family saw this person");
    }
    if (resources.some((row) => "familyId" in row)) {
      throw new Error("LEAK: the family id crossed the view");
    }

    // The scoped write: a person in another family is not updatable or
    // removable, and the answer is "no such row", not a 500.
    const stolen = await personModel.update(first.id, theirs.id, {
      displayName: "stolen",
    });
    if (stolen !== null) {
      throw new Error("LEAK: a cross-family update succeeded");
    }
    const removed = await personModel.remove(first.id, theirs.id);
    if (removed) {
      throw new Error("LEAK: a cross-family delete succeeded");
    }

    console.log("\npeople scoping, view mapping and scoped writes all held");
  } finally {
    await prisma.family.deleteMany({
      where: { id: { in: [mine.id, theirs.id] } },
    });
    await prisma.$disconnect();
  }
}

main().catch((error: unknown) => {
  console.error(error);
  process.exitCode = 1;
});

Break it on purpose — predict first

Decisions carried into the next sittings

  • Who may write a person is a product question, and the default is "any member". Counter-case: deleting a person is destructive, so a stricter rule — requireRole("admin") on DELETE — is defensible. It costs a little client work: the screen would need the caller's role (it is on FamilyResource, from lesson 13) to avoid showing a button the server will refuse. Decide it once, then change the route and the button in the same commit.
  • The resource still hides gender and the dates. PersonResource is { id, name, living }. The create form can send a gender and a birth date; the list cannot show them yet. That is deliberate — a view is a whitelist, and you widen it when a screen needs the field, not before. The profile screen is where this widens.
  • Shape validation lives in the controller for now. It is hand-rolled for exactly two shapes. When a third resource needs the same treatment, that is the moment to adopt a schema validator (Zod) at the boundary — one parser per resource, not one per handler. Not before.
