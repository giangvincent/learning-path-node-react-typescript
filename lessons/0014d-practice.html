Defend it

Why not just handle the 401 in each screen?

Because that is what the baseline was, and it fails the same way twice. InvitesPage turned a 401 into "Failed to load", which is a lie about what happened — the load did not fail, the session ended. And FamilyList had no branch at all, so the app stayed "logged in". A per-screen fix means every future screen must remember, and the failure mode of forgetting is invisible: a page that renders an error instead of a login form. Move it into the transport and the next screen is correct before it is written.

Why a module-level listener and not a React context?

Because the thing that notices — request() — is not a component. A context would force the transport to import React and to be constructed inside the tree, which inverts the dependency: the library would need to know about the UI. A module with a Set of callbacks is the smallest seam that lets a non-React layer publish and a React layer subscribe. The name for this is a notifier (or an event bus), and its cost is honest: it is global state, so it must stay tiny and there must be exactly one of it.

Why must a 401 from login not end the session?

Because it is not about the session. POST /api/auth/login answers 401 for "wrong email or password" — a verdict on what the user typed, which the form renders as "Wrong email or password." If the transport announced on every 401, that verdict would also be broadcast as "your session is gone", which is both false and confusing: the app would flip states in response to a typo. The fix is not a smarter 401 inspector — the status code genuinely does not carry the difference — it is letting the caller, who asked the question, say which question it asked. Hence expectsSession.

The seam only covers what goes through it — what about AcceptPage?

Good catch, and it is in the map: client/src/AcceptPage.tsx is the one component that calls fetch directly instead of going through lib/api.ts. So it is not covered by the announce: an expired session on the accept page still renders "This link doesn't work." That is arguably acceptable — the link really does not work for that visitor right now — but it is the same class of bug, and the cure is the same: route it through a named function in lib/api.ts. A seam protects the traffic that uses it; that is a property to state out loud, not a flaw to hide.

Should useSession be replaced by TanStack Query now?

No — and the trigger is worth naming rather than deferring again. Look at what the client fetches: whoami, families, invitations. All three are read-once per screen, and nothing in the client mutates them. A query cache earns its keep by knowing what to invalidate after a write; with no writes, it is a store whose most valuable feature has nothing to do. Here is the honest comparison:

The trigger: the first screen where a mutation must invalidate a read. That is the next lesson's people screen — add a person, and the list must show them; add a relationship, and the tree must redraw. Adopt it there, and the comparison above stops being a table and becomes a measurement. Two things to say in an interview about why: a cache without invalidation is a place for stale data to hide, and the migration is cheap because of today's work — the transport already owns the envelope and the 401 rule, so swapping the data layer touches neither.

How can "resend this invite" work if the raw token was never stored?

It cannot mean "show me the link again" — that door is closed on purpose. The raw token existed for one HTTP response and was never written down; storing it would mean a plaintext credential at rest, which is exactly what hashing it avoided. So resend means: mint a new credential and kill the old one, in one transaction. The protocol:

  1. New token, new hash, new expiry. Same shape as the original mint, and the raw value leaves in the response body exactly once — the only place that credential will ever exist.
  2. The old invite must die. Otherwise one person accumulates live credentials and every revoked email still works. Expressing "died" is a real schema decision: reusing usedAt hides it from the pending filter, but it conflates claimed with revoked, and the difference is exactly what you want in six months when you ask how many invites were actually accepted. Add revokedAt (its own migration, one thing), and "pending" becomes usedAt: null AND revokedAt: null AND expiresAt > now — three distinct end-states, one definition, still in findPendingByFamily.
  3. One transaction behind lockFamily, with the inviter's role re-read inside the lock. Two concurrent resends would otherwise each mint and each revoke, leaving two live tokens and an emailed link that is already dead — the same race shape as the duplicate-mint in lesson 11, which is why the same lock is the answer. And the role must be re-read because resend is a mint: an owner demoted since the request arrived must not get another credential out.
  4. The granted role is carried over, and re-checked against the inviter's rank. Otherwise resend is an escalation path: mint a member invite, then resend it as owner.
  5. Accept that a retry is not safe. A retried resend mints a second credential and revokes the first, so the link the user was emailed is dead. This is the same non-idempotence lesson 08 recorded for transfers: either the UI never auto-retries, or it needs an idempotency key (week 8's asynchrony thread). Do not quietly retry it.

Worth noticing what that decision does to the other open question: an owner who wants to see revoked invites is asking for "show used invites too" — the exact filter Reference 11 §2 named as the thing that converts a bounded read into an unbounded one, and therefore the change that will one day force pagination. Three lessons, one thread.

Break it on purpose

  1. Remove the sign-in exception. Delete expectsSession: false from login and run npm run check:session. Predicted: two announcements. Measured: Error: EXPECTED exactly 1 announcement, got 2, exit 1. Now a mistyped password would be broadcast as "your session died" — to a user who is on the login screen.
  2. Put familyId back in the view. Add familyId: person.familyId to toPersonResource and run npm run typecheck. Measured: error TS2353: Object literal may only specify known properties, and 'familyId' does not exist in type 'PersonResource', exit 1. Notice this is the opposite of the Prisma blind spot: an annotated return type is checked, a select with a sibling key is not.
  3. Announce on every failure. Change the condition to if (!response.ok) announceSessionEnded(); and run check:session. Predict before measuring: the 500 case starts announcing, so the count is 2 rather than 1 — a server fault now reads as a logout, and the user retypes a correct password into a broken system. This is the most confusing bug in this series' family.
  4. Never unsubscribe. Drop the cleanup from the useEffect in useSession (useEffect(() => { onSessionEnded(...); }, [])). Every remount adds a listener to the same Set, so one 401 ends the session N times. Harmless here — setState is idempotent — and a leak everywhere else. Say why it is harmless this time, because "it works" is not the reason.
  5. Move the check outside include. Move checkSessionEnd.ts to client/scripts/ (beside src, not inside it) and run npm run typecheck. It stays green, and the file is no longer compiled at all — so it can drift from the transport it claims to test, silently. Lesson 05's trap, exactly.

Retrieval practice

Ask your teacher

Ask whether AcceptPage should be moved onto lib/api.ts now, and what else is still bypassing the transport. Ask whether the revokedAt column should be added before or inside the resend build. Ask how to tell a 401 from a 403 on the client when both mean "no", and whether the client should ever render them differently. And ask why the notes claimed a check:mint exists when it does not — because that is a real debt, not a typo.
