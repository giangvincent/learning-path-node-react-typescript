Lesson 03 · Week 3 · about two hours

Ten requests, one pool, two families

Three boundaries that only reveal themselves under pressure: what happens when ten requests meet a pool of five, what your ids leak, and what stops one family from reading another's history.

Mission: ship KinLink Reference: Ids & tenancy Requires: Lesson 02
The win

You will stop treating connectionLimit: 5 as a magic number and start treating it as a queue with a doorway. You will be able to argue both sides of the UUID question and pick one on evidence. And /api/people will stop leaking every family in the database — the fix being where the familyId comes from, not merely that a filter exists.

Part one — the doorway: what connectionLimit really does

You asked what connectionLimit: 5 does when ten requests arrive at once. Rather than describe it, we measured it — ten concurrent queries, each deliberately slow (SLEEP(0.4)), against your pool of five: 

Firing 10 concurrent queries against a pool of 5...

  req 0: waited 487ms
  req 1: waited 487ms
  req 2: waited 487ms
  req 3: waited 493ms
  req 4: waited 497ms
  req 5: waited 890ms      ← waited for a free connection
  req 6: waited 890ms
  req 7: waited 890ms
  req 8: waited 896ms
  req 9: waited 898ms

Wall clock: 898ms
(400ms of work each, pool of 5)

That table is the whole lesson. Requests 0–4 each waited about 487ms — their own 400ms of work plus the ~87ms of connection overhead. Requests 5–9 waited about 890ms: 400ms of their own work, plus 400ms of queueing behind someone else's.

The pool is a doorway with five doors. Ten people arrive. Five walk through. The other five stand in the rain until a door opens. Nobody is rejected — the requests queue. That is why nothing threw an error, and why the wall clock came in at 898ms instead of 400ms.

Why this is your problem and not an abstraction detail

Ten concurrent requests to a family tree is normal — the tree page wants people, relationships, and generations at once. A user on hotel wifi is not an edge case. If your pool is too small, every user gets slower when the server gets busier, which is the exact opposite of what a server is supposed to do.

Choosing the number

Three inputs, and you should be able to name all three in an interview:

  1. MySQL's ceiling. The default max_connections is typically 151. If ten app servers each open a pool of 20, that is 200 — and your database refuses connections it was perfectly happy to accept yesterday. Pool size × instance count must stay under the server's limit.
  2. Whether work blocks. A database call is I/O: your Node process is idle while waiting. That is exactly why you can hold more open connections than threads and stay fine. Your measurement above is the proof — five connections, ten requests, nothing crashed.
  3. Little's Law, which is the honest answer. Concurrency ≈ throughput × latency. At 100 requests/second, each query taking 50ms, you need about 5 connections running to keep up. Five is not arbitrary here — it falls straight out of the arithmetic. Pick the number you can derive, then measure it.
Do not simply raise it

A pool of 500 does not make the server faster. It converts a queue inside your application into a queue inside MySQL, adds memory, and makes a bad query far more damaging — because 500 slow queries now run at once. A larger pool hides the problem you should be fixing.

Part two — what your ids leak

The other thing you asked me to argue: UUIDs versus auto-increment. You are currently on @default(uuid()). Here is the honest case on both sides, because the popular answer is only half right.

Concern Auto-increment UUID
Enumeration Leaks. /api/people/47 confirms you have 47+ people and invites 48. Opaque. Guessing a v4 UUID is hopeless.
Insert speed Faster — the database hands out the next number. Slower; some versions randomise to avoid fragmentation.
Index size 8 bytes, and cache-friendly. 16 bytes for the string form. Larger B-tree, more cache misses.
Sorting Insertion order = id order, so the index stays dense. Random ids fragment the index. UUIDv7 fixes this — time-ordered.
URL Short, memorable, easy to share. Long. 36 characters in every URL.

The security argument only applies to ids you can guess. Here is the nuance almost every explanation gets wrong: UUIDs do not make an endpoint safe. An unguessable id is not authorisation. If GET /api/people/:id does not check that the caller belongs to that person's family, the uuid is irrelevant — an attacker who gets hold of any valid id still reads it. Guessing becomes hard; asking is untouched.

So the real argument is: a UUID buys you a little, for free, and it costs you index size and URL length. Take it, and then do the real work — which is the next section.

The upgrade to know about

UUIDv7 is time-ordered: the first bits are a timestamp, so new ids sort sequentially and the index stays as dense as an auto-increment's, while remaining unguessable. You have the best of both. Note Prisma generates uuid() as v4 — switching to v7 means generating ids in application code rather than asking the database for a default.

Part three — the bug you found

You wrote: "The fix is to list down the people in one family only, not all the person." That is the right destination. It is not yet a fix, because it doesn't say where the family id comes from — and that is the entire security property.

Three ways to scope a query, two of them broken

// BROKEN — the client chooses whose data to read
GET /api/people?familyId=18321796-bfab-4c2a-9959-b17c4b0acb65

// BROKEN — authenticated, but reads the whole table and filters after
const all = await personModel.findAll();
return all.filter(p => p.familyId === req.user.familyId);

// CORRECT — the family comes from the session, and the database does the filtering
GET /api/people
const familyId = req.user.familyId;          // from the session, never the URL
await prisma.person.findMany({ where: { familyId } })

The first lets anyone read anyone by changing a query string. The second works but is worse than useless: it pulls every family's rows across the wire and throws most away, so it scales inversely — it gets slower as the product succeeds. The third is the only one that is both secure and fast.

Why the id must come from the session

If the client can name the family, the client controls the query — and you have moved your authorisation decision somewhere the attacker can edit. The family has to be derived from "who is this person, proven at login". Once auth exists, there is no familyId in any URL. Ever.

On your SOLID answer — you're close, and I'd correct one word

You wrote that putting the decision in the service "is the OOP Design Pattern, which apply SOLID and Isolated code." Separation of concerns is genuinely part of what you hit, so you weren't wrong. But the precise reason is dependency direction, and it matters that you get it right — because this is the question interviewers ask when they want to know whether you understand layers or have just memorised five acronyms.

It is not that the model "shouldn't know about families". The model already knows deeply — it knows the table name, the index, the column mapping. The problem is which question the model is allowed to answer: 

MODEL   answers: "which rows match this familyId?"      ← a fact
SERVICE answers: "which family is this request allowed to see?"   ← a policy

A model that decides policy is a model you cannot reuse safely — from a socket handler, from a nightly job, from an admin tool that has different rules. And a model whose signature is findAll() with no arguments has no way to be scoped, so the bug becomes structurally impossible to write correctly once the signature requires the familyId.

SOLID is a useful vocabulary, and single-responsibility really is nearby. Reach for it when it's accurate. Don't reach for it when the sharper answer is "the model must not depend on the request" — because that sentence survives a follow-up question and the acronym doesn't.

Build it

  1. Scope the query at the database

    server/src/models/person.model.ts 
    import { prisma } from "../config/database.js";
import type { Person as PrismaPerson } from "../../generated/prisma/client.js";

export type Person = PrismaPerson;

// familyId is now a required argument. There is no way to call this
// function without saying whose rows you want, which is what makes the
// isolation bug impossible to introduce by accident.
export async function findByFamily(familyId: string): Promise<Person[]> {
  return prisma.person.findMany({
    where: { familyId },
    orderBy: { createdAt: "asc" },
  });
}
    server/src/services/people.service.ts 
    import * as personModel from "../models/person.model.js";
import type { Person } from "../models/person.model.js";

// NOTE: this is a placeholder. Lesson 04 (authentication) replaces this with
// a value read from the session cookie, so the family id comes from proven
// identity rather than a hardcoded constant. Until then, the endpoint is
// effectively unauthenticated — which is fine for development, and wrong for
// production. Do not deploy with this constant in place.
const CURRENT_FAMILY_ID = "18321796-bfab-4c2a-9959-b17c4b0acb65";

export async function listPeople(familyId: string): Promise<Person[]> {
  return personModel.findByFamily(familyId);
}

export async function listPeopleForCurrentFamily(): Promise<Person[]> {
  return listPeople(CURRENT_FAMILY_ID);
}
    server/src/controllers/people.controller.ts 
    import type { NextFunction, Request, Response } from "express";
import type { ApiResponse, PersonResource } from "../contracts.js";
import { listPeopleForCurrentFamily } from "../services/people.service.js";
import { toPersonResource } from "../views/person.view.js";

export async function getPeople(
  _req: Request,
  res: Response,
  next: NextFunction,
): Promise<void> {
  try {
    const people = await listPeopleForCurrentFamily();
    const body: ApiResponse<PersonResource[]> = {
      data: people.map(toPersonResource),
    };

    res.status(200).json(body);
  } catch (error) {
    next(error);
  }
}

    The controller never names a family. Neither does the view. Only the service does, because only the service knows who is asking.

  2. Prove it, with a second family

    A single-family database cannot demonstrate isolation — there is nothing to leak. Add a rival family, then show it cannot be seen. 

    docker compose exec mysql mysql -ukinlink -pkinlink kinlink -e "
INSERT INTO families (id, slug, name) VALUES
  ('ffffffff-0000-4000-8000-000000000001', 'tran', 'Trần');
INSERT INTO people (id, family_id, display_name, gender) VALUES
  ('ffffffff-0000-4000-8000-000000000002',
   'ffffffff-0000-4000-8000-000000000001', 'Trần Văn Cường', 'male');"
    curl -s http://localhost:4000/api/people

    Two names, not three. The Nguyễn family cannot see the Trần family's man. Now the real test — try to reach him anyway: 

    curl -s "http://localhost:4000/api/people?familyId=ffffffff-0000-4000-8000-000000000001"

    Ignored entirely, because the controller never reads a query string. A feature that ignores you is far better than a feature that can be talked into misbehaving.

  3. Stop leaking internal errors

    Your errorHandler.ts currently returns error.message to the browser unconditionally. Break the database password and you will send the driver, the host, the user and the port straight to whoever caused the error.

    server/src/middlewares/errorHandler.ts 
    import type { ErrorRequestHandler } from "express";
import type { ApiErrorBody } from "../contracts.js";

const isProduction = process.env.NODE_ENV === "production";

export const errorHandler: ErrorRequestHandler = (error, _req, res, _next) => {
  // Never in production: a database error message can contain the host,
  // the username and the query. Log it for you; never send it to them.
  if (!isProduction) console.error(error);

  const body: ApiErrorBody = isProduction
    ? { message: "Internal server error" }
    : { message: error instanceof Error ? error.message : "Unexpected error" };

  res.status(500).json(body);
};

    The rule generalises: log it, don't leak it. A user needs to know their request failed; they do not need your infrastructure's topology.

  4. Commit

    git add -A
git commit -m "Scope person queries to a single family; stop leaking errors in production"

Verify

  • With two families seeded, /api/people returns exactly two names.
  • Passing ?familyId= for the other family changes nothing.
  • grep -rn "findAll" server/src finds no unscoped person query.
  • With a wrong DATABASE_PASSWORD, production mode returns only Internal server error.

Break it on purpose

  1. Give the model a default: findByFamily(familyId: string = ""). Now grep for calls with no argument. What does the signature now permit that it previously made impossible?
  2. Lower connectionLimit to 2 and re-run the concurrency script from the top of this lesson. Predict the new wait times before running it. Then try 50 connections with the same ten queries — what changes, and what does it cost MySQL?
  3. Write the two contrasting calls side by side: one that filters in the database, one that fetches everything and filters in JavaScript. Time both against a table with 50,000 people in ten families. Which one is correct, and which is faster? Notice they are not the same question.
  4. Change findByFamily to accept a Person's id instead of a family id. It typechecks. Now ask: which callers would silently break?
